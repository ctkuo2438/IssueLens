# M2：有證據的 Issue 調查與可編輯草稿

**目前狀態：功能凍結，本輪有限功能驗收通過，可進入收尾；使用者人工審閱仍待確認。** 最新三案皆有最終答案，兩案完成、一案如實揭露部分覆蓋。這不代表生產準確率、所有語意問題已解決，或所有分支皆已真實演練。

本文合併 M2 的功能、操作、Context Builder、品質規則、評估及已知限制。啟動與基本架構只在 [M1](m1.md) 維護；現行證據由 [evidence 證據索引](../evidence/README.md)分類查找；已被後續結果取代的開發期原始輸出不在工作目錄，見[歷史證據索引](#history)。

後續 [M3](m3.md) 已新增 PostgreSQL 分析紀錄保存；本文件的 M2 驗收與當時架構限制保留，不將資料保存改動當成新的模型品質驗收。

<a id="features"></a>
## 目標與已完成功能

M1 解決「讀取一筆 Issue 並顯示分析」；M2 增加比較、分類與補問依據，讓使用者能核對來源、修改草稿再分享。M2 是功能里程碑，目前仍是 Single Agent（單一智能體），不是 Multi-agent 的 Coordinator。

| 畫面／功能 | 用途與可觀察結果 |
| --- | --- |
| Analysis | 整理摘要、已知事實、資訊缺漏與英文回覆草稿。 |
| Similar issues | 顯示同 repo 候選、搜尋範圍、實際讀取與暫定比較。 |
| Labels | 依真實目錄建議最多三個尚未套用的標籤，可查理由及來源。 |
| Templates | 顯示實際取得的範本、欄位與必填／選填／未知狀態。 |
| Sources | 保留工具取得的有界摘錄，供人工核對。 |
| Activity | 顯示查閱、輸入估算、選材、拒絕、修正與停止紀錄。 |
| 可編輯草稿 | 直接修改、複製目前文字、還原模型原稿。 |

<a id="tools"></a>
### 七個唯讀工具

| 工具 | 範圍 |
| --- | --- |
| `get_issue` | 目標 Issue 的本文、狀態、日期、既有標籤與留言數。 |
| `get_issue_comments` | 目標留言，每頁 10 則、最多 5 頁，每則摘錄最多 350 文字 Token。 |
| `get_repo_readme` | 同 repo 預設分支 README，摘錄最多 1,600 文字 Token。 |
| `search_issues` | 同 repo 的標題／本文關鍵字搜尋，排除目標與 PR。 |
| `get_related_issue` | 只讀本次搜尋發現的候選本文，摘錄最多 1,800 文字 Token。 |
| `get_repo_labels` | 同 repo 第一頁有效標籤目錄，保留完整名稱／說明列。 |
| `get_issue_templates` | 同 repo 預設分支 `.github/ISSUE_TEMPLATE` 內最多兩份支援檔案。 |

工具不執行程式、測試或重現，也不套用標籤、留言、關閉 Issue 或合併 PR。模型選搜尋詞、候選及可選背景，程式控制範圍、必要步驟與上限。

<a id="settings"></a>
## 模型與資源設定

在根目錄 `.env` 設定；已設定就保留原檔與 Key，不需要為本次文件整理改動：

```dotenv
OPENAI_MODEL=gpt-5.6
OPENAI_REASONING_EFFORT=medium
AGENT_MAX_ITERATIONS=8
AGENT_MAX_TOOL_CALLS=15
AGENT_RUNTIME_SECONDS=90
AGENT_CONTEXT_TOKENS=24000
AGENT_MAX_CANDIDATES=20
AGENT_MAX_CANDIDATE_READS=5
```

以上六項 Agent 預算都有程式預設值，未寫在 `.env` 也會使用同樣數字。明寫能方便追蹤，不代表每次必須調高。設定由 [config.py](../backend/app/config.py) 讀取，已匯出的環境變數優先於 `.env`。

effort 是推理強度。程式接受 `none`、`low`、`medium`、`high`、`xhigh`、`max`，但不代表每個模型都支援全部選項。未設定時使用 `medium`，與模型預設為 `gpt-5.6` 的做法一致；明確留白時不送 `reasoning`，使用提供者預設；字面 `none` 則是明確指定，兩者不同。M2 評估時「未設定」也代表提供者預設，2026-11-15 為了讓只設定金鑰的安裝版使用評估過的設定而改為 `medium`，見 [M5](m5.md#settings-file)。調查與修正沿用同一設定，變更後重啟後端並建立新分析才生效。

輸出上限是 [agent.py](../backend/app/agent.py) 的 `MAX_OUTPUT_TOKENS=2400`，目前沒有對應 `.env` 選項。這個額度包含推理與可見輸出；若 API 明確回報額度耗盡，保留來源並記錄不完整，不接受截斷答案或執行其中工具。

M2 的評估與驗收都在 `AGENT_CONTEXT_TOKENS=12000` 下進行，本文其他的 12,000 都指當時的預算。2026-11-13 預設改為 24,000，原因與驗證見 [M5](m5.md#context-budget)。

要分清三個數字：24,000 是**單次輸入的本機估算上限**；2,400 是**單次輸出上限**；畫面總 Token 是**整次分析所有模型請求回報用量的累加**。它們也不同於模型原生上下文視窗。換模型不會解除本機預算，15 次邏輯工具也不等於 15 次 GitHub HTTP 請求。

Activity 與新評估報告記錄請求的模型、effort 及輸出額度；報告的 effort 為 `null` 代表未指定，不代表有效強度已確認為 `none`。舊報告不補寫設定。

<a id="required-lookups"></a>
## 留言與最低必要查閱

成功讀取目標後，正常調查在預算內依序檢查：

1. Issue 回報有留言、且尚未有效嘗試第一頁時，指定 `get_issue_comments(page=1)`。
2. 尚未嘗試標籤目錄時，指定 `get_repo_labels`。
3. 尚未搜尋時，指定 `search_issues`；第一次成功但為空，再要求第二個不同查詢。
4. 找到候選、尚未成功取得任何候選本文，也未有效嘗試候選讀取時，指定 `get_related_issue`。

程式只確認兩次查詢不同，不能證明第二次語意更廣。無效參數、錯誤工具或把目標當候選，不算有效查閱；有效工具失敗會保留失敗狀態，不無限強制重試。所有成功讀取的候選，都必須出現在最終引用比較中。

必要查閱優先於預留修正輪數。最低條件就緒且設定至少六輪時，接近上限會停用新工具，保留最多兩輪修正；不增加總輪數。模型在仍被指定必要工具時搶答，會回到調查。若硬預算不足，允許提早用現有證據收尾，明示未讀與未比較。

### 留言狀態由程式計算

[github.py](../backend/app/github.py) 維護 `CommentCheck`，不是讓 GPT 自填是否讀完。

| 狀態 | 意義 |
| --- | --- |
| `not_read` | 尚未有效嘗試頁面讀取；metadata 回報零則也不改成查閱成功。 |
| `empty` | 成功覆蓋的頁鏈為空，沒有下一頁、失敗頁或已知數量矛盾。 |
| `read` | 從第一頁連續讀到最後，沒有下一頁／未恢復失敗，且與已知數量一致。 |
| `partial` | 尚有下一頁、頁碼缺口、部分失敗或數量不一致。 |
| `failed` | 嘗試過但沒有成功頁面，不能推斷沒有留言。 |

`read` 是頁面與數量覆蓋，不保證每則原文完整、模型看過全部摘錄或理解正確。原文截短與 Context Builder 整則省略分開記錄；有界 Sources 也不是完整封存。留言可能在請求間變動，沒有原子快照保證。

成功查無候選、尚未搜尋、搜尋失敗、候選未讀、讀取後證據不足同樣分開記錄。API／報告的 `comment_check`、`similar_issue_check` 與 Activity 可用來核對；最低查閱通過仍不等於語意正確。

<a id="similar-issues"></a>
## 相似 Issue：先搜尋，再讀取比較

`search_issues` 接受一至六個關鍵字，後端固定同 repo、Issue 類型及標題／本文範圍。每次只讀第一頁，預設最多保留 20 個不同候選、嘗試讀取 5 個候選本文；搜尋不完整、還有下一頁、達上限或失敗都保留限制。

候選只代表命中。`get_related_issue` 不接受搜尋未發現的編號，亦不讀候選留言、程式、修正或測試。比較必須引用目標本文及候選本文，搜尋摘要不能代替。

| 暫定關係 | 所需依據 |
| --- | --- |
| `possible_duplicate` | 具體相同症狀與條件；仍未證明根因相同。 |
| `related_but_different` | 目的、行為或失敗條件的實質差異。 |
| `insufficient_evidence` | 已讀雙方，但資訊不足以確認相同或不同。 |

一筆沒提供平台、另一筆寫 Linux，表示前者未知，不能直接列為平台不同。文字詳略、用詞或開關狀態也不能單獨證明不同問題。未完成比較則顯示 `Not compared`，與已比較但證據不足不同。

這是關鍵字搜尋，尚未實作語意檢索。成功空搜尋只能說本輪條件沒有命中；不能宣稱 repo 沒有相關 Issue。成功重複請求可使用本次執行快取，不代表再次發出 HTTP。

<a id="labels"></a>
## 標籤：依目錄推薦並檢查文字一致性

Label 是 repo 用來分類、篩選 Issue 的標記。`get_issue` 只提供已套用標籤；`get_repo_labels` 取得可用名稱、說明與顏色，讀第一頁最多 100 個、排除封存項目。完整名稱／說明列共用約 1,600 文字 Token，放不下整列或還有下一頁時標示部分目錄。

最終建議最多三個，必須來自已載入有效目錄、不與現有標籤或其他建議重複、理由非空，並引用目標及目錄。大小寫比對後使用目錄原本拼法。空清單有效；目錄未讀、讀取失敗、空目錄、查過無適合新標籤、沒有合格答案是不同情況。

### 用途與資訊缺漏

`quality.py` 的 `is_pr_only_label()` 依**說明**辨識有限英文 PR 專用句型，例如 `Pull requests that update Python code`。這不是 `python` 名稱黑名單；共用 Issue／PR、單純提及 PR 或空說明，不會因此排除。

工具保留原目錄與 Sources，另告知模型排除名單；最終驗證再從伺服器目錄檢查。排除用途不讓原本完整的目錄變成部分目錄。通過只表示未命中已知限制，仍不證明主題相關性。

若要推薦資訊缺漏標籤，模型必須說明缺少哪項必要事實、為何阻礙初步調查。想看更多日誌、其他平台或尚未確認根因，本身不足以支持這類標籤。補問可以有用，同時不推薦 `needs-info`。

### 清單與文字一致性

`label_consistency_fields()` 在推薦清單非空時，找出摘要、限制、草稿等欄位中的已知零推薦說法；例如清單有 `bug`，文字卻說 `No label recommendation is made.`。

已補上 `is/are/was/were/has been/have been made`、`being made` 與有限 `currently/now` 變形。`made` 前必須是推薦名詞，避免把「沒有套用標籤到 GitHub」當成「沒有推薦」。已知條件、歸因及具名涵蓋全部推薦的例外另行判斷。

有矛盾時回報欄位並要求有界修正；不偷偷刪文字或標籤。這是一方向、有限英文句型檢查，不能驗證所有數量、反向矛盾或一般語意一致性。名稱、用途與引用合法，也不代表整體判斷正確。

<a id="templates"></a>
## 範本：以實際專案要求協助補問

Issue template 是專案提供給提報者的填寫指引。工具在成功讀取目標後，固定查當前預設分支的 `.github/ISSUE_TEMPLATE`，不接受模型指定其他路徑。

| 限制 | 行為 |
| --- | --- |
| 檔案範圍 | 一般 `.md`、`.yml`、`.yaml`；排除 config、符號連結、子模組與巢狀目錄。 |
| 讀取數量 | 依檔名排序，最多嘗試兩份；一次工具可含一個目錄與兩個檔案 HTTP 請求。 |
| 大小與摘錄 | 每份最多 32 KiB，來源摘錄最多 750 文字 Token。 |
| 打包 | 解析資料與摘錄共用約 2,000 Token，另有最多 400 Token 查詢摘要。 |
| 欄位 | 最多十二個輸入欄位、每組最多六個必填核取選項。 |

PyYAML 只解析資料，拒絕錨點、別名、自訂標籤及過深巢狀；不是完整 GitHub schema 驗證器。YAML 明確 `required: true` 為必填；合法省略旗標為選填，不能辨認則未知。Markdown 標題沒有結構化必填旗標，不能全部視為必填。

只挑適用範本，先查本文／留言是否已有等價資訊；預填範例不是回報者事實。當前範本不證明 Issue 建立時適用同樣要求。目錄不存在是有範圍的成功查詢，失敗與未查閱另列；未涵蓋組織繼承、舊式單檔或其他目錄。

<a id="context-builder"></a>
## Context Builder：在原預算內選材

Context（上下文）是送給模型的指示、工具定義、JSON 回答格式、歷史與證據。[context.py](../backend/app/context.py) 用本機 `o200k_base` 分詞器估算整體輸入，加上 1,024 Token 餘裕；這是估算，不是 API 計費或原生視窗保證。

選材由我們寫的規則決定，不請 GPT 決定保留內容，也沒有摘要模型、資料庫或跨任務記憶。

### 只整理尚未曝光的新結果

1. 完全重複的結果若較省，改指向較早的 `call_id`；短結果可保留。先前省略不會因重讀就變成已看過。
2. 重複搜尋摘錄可由已保留的結構化搜尋欄位代表，覆蓋與錯誤狀態不丟失。
3. 保護目標／候選本文、標籤列、範本解析欄位，以及所有非摘錄 metadata、查閱與錯誤資訊。
4. 需要省空間時，依序整份省略新 README、已有解析欄位的範本原文，再省略低分留言。留言以標題關鍵字交集及作者關聯排序；同分先省略本批較早者。
5. 保留來源 ID、URL、狀態與省略提示；提示比摘錄更長時不省略該摘錄。重要資料仍放不下則明確停止。

已準備曝光的歷史前綴、SDK 工具規劃輸出、推理項目與 `call_id` 配對保持原樣，後來的候選不能回頭擠掉已送出的留言。這讓協定較容易核對，代價是歷史累積後仍可能放不下。

Sources 保存原有工具上限內的摘錄；Activity、限制及 `result.context_builds` 列出省略來源。省略使任務部分完成，無資料損失的重複引用則不單獨增加限制。未抓、失敗、已抓未送、工具原本截短要分清；不能把模型沒看到當成作者沒提供。

後端拒絕以整則未曝光的留言／README 支持事實；範本保留的解析欄位仍能引用。這仍有 metadata 與正文引用粒度的已知限制。

### 事前預留

為避免留言送出後才發現候選放不下，首次曝光前先設定後續空間目標，從同一個 12,000 預算扣除：

| 預留 | 用途 |
| --- | --- |
| 修正 256 Token | 供精簡驗證回饋使用。 |
| 後續基本 512 | 估計下一輪流程成長。 |
| 首筆必要候選再加 2,400 | 原候選摘錄上限 1,800，加 600 估計包裝與引用；必要搜尋仍可能找到候選時也預留。 |
| 標籤／必要搜尋各再加 1,024 | 尚待查閱的結果與流程估值，完成或失敗後釋放。 |

已讀目標、標籤與搜尋都待做時，後續目標通常 4,960；查完標籤後 3,936；找到候選後 2,912。一般規劃最低 512，要求首筆候選讀取前最低 2,400。目標未全達仍可在最低值滿足時繼續。

`future_reserve_target_tokens` 是目標、`future_reserve_tokens` 是實際分配、`future_reserve_minimum_tokens` 是最低值。每個送出請求必須滿足：

```text
estimated_tokens + repair_reserve_tokens + future_reserve_tokens <= budget_tokens
future_reserve_tokens >= future_reserve_minimum_tokens
```

`estimated_tokens` 已含 1,024 餘裕，不重複加入。若最低值仍放不下，取消工具要求，先嘗試保留修正空間的最終回答，必要時再嘗試不含修正預留的輸入；仍放不下就停止。提早收尾／真正答案修正的未來預留為零，異常工具不執行。未讀狀態不會被改成成功空結果。

這些是估值，不是最大工具大小；額外候選、JSON 跳脫、很大 metadata 或不透明推理仍可能超額，不能保證一定有答案。

### 不用 API 的示範

```bash
uv run --locked python scripts/context_demo.py
```

示範使用虛構十則留言、實際本機 tokenizer、2,500 示範預算與短候選的 300 預留，沒有模型／GitHub 請求，也不修改應用設定。可觀察 `sent: false`、`future_reserve_tokens: 300`、候選 `fits: true`、歷史前綴未變，以及十份原始摘錄仍保留。

另有原 12,000 預算的離線模擬：無後續預留時候選讀回估算 13,160 而停止；有預留時提前省略八份留言，最終估算 10,404 並接受模擬答案。這不是模型品質或 API 實際計費紀錄。

<a id="answer-repair"></a>
## 引用與有界答案修正

每輪提供伺服器保存的精確引用配對：標籤需要目標＋目錄，比較需要目標＋候選本文。後端不自動補引用；正確 ID 仍不保證語意支持。

工具規劃回應沿原順序續接完整 SDK 輸出，包括加密推理與工具配對。已允許收尾、卻驗證失敗的無工具答案，則另外保存原文、原因、指紋及有界回饋到 `rejected_answers`，不把它或其推理加進證據歷史。

下一輪從**相同調查輸入檢查點**重新生成完整 JSON，只帶目前精簡回饋，不累加失敗答案。修正使用原先 256 預留，回饋已計入當輪輸入後不再重複預留；所有嘗試仍計入原輪數及時間。

### 調查搶答與答案修正是兩種狀態

| 情況 | 下一輪 |
| --- | --- |
| 仍指定必要工具，模型卻搶先交答案 | 記錄拒絕，維持 `investigation`，繼續必要查閱。 |
| 已允許收尾，文字／引用等驗證失敗 | 進入 `repair`，`tool_choice="none"`，不重新排程留言、標籤、搜尋或候選；未來預留三欄皆為零。 |

Activity 顯示 `Answer repair step ... tools disabled`。異常修正工具直接停止且不執行。未讀／未比較保持未完成；修正不能取得新證據，只能如實修正現有證據的表達。

最新狀態修復有 18 項答案修正離線測試，包含六項新增交界回歸；完整 262 項測試與 Pyright 通過。新三案沒有修正事件，所以不能聲稱最新狀態切換已在那輪真實演練。輸入真的超額、反覆失敗或 API 出錯仍可能無最終答案，不能放寬驗證換取完成。

<a id="drafts"></a>
## 草稿：維護者語氣、來源歸因與編輯

草稿寫給 Issue 作者／貢獻者，直接提出具體下一步，避免 `If you want, I can help ...` 這類助理服務結尾。可以沒有追問；`missing_information=[]` 也有效。

補問前先對照本文與可見留言的等價答案、已嘗試步驟及不適用原因。重現歸給實際執行者，不寫成 Agent 自己測過。Issue 與留言日期可協助歸因歷史計畫，但不證明目前程式或發布狀態。

[quality.py](../backend/app/quality.py) 以有限英文句型攔截已知問題，沿原預算修正或拒絕，不改寫 Sources：

| 檢查 | 範圍與界線 |
| --- | --- |
| 第一人稱重現 | 模型撰寫欄位中的已知正向 `I/we reproduce/replicate` 形式；要求第三人稱歸因。 |
| 留言宣稱 | 已知未讀卻稱不存在、未完整覆蓋卻稱全部看過的形式。 |
| 維護者語氣 | `draft_reply` 的已知助理服務邀請。 |
| 時間歸因 | 草稿未歸因的修復預告、目前能力缺口或版本修復斷言。 |
| 未執行動作 | 草稿第一人稱關閉、指派、套標籤、合併、發布回覆等追蹤器動作；不把關閉資料庫連線當 Issue 動作。 |
| 關閉推成修復 | 草稿已知的關閉／解決並列或因果表達；關閉狀態本身不證明已修復。 |

已知否定、問句、條件與歸因有局部例外，但不驗證歸因真偽。這些規則可能漏判或誤判，尤其不完整涵蓋其他欄位、時態及重複補問；沒有命中不能當成通用語意保證。

### 編輯與複製的保存範圍

草稿直接編輯；`Copy draft` 複製目前文字與換行，`Restore original` 還原模型原稿。切換頁籤保留修改；開始新任務、重新整理或關閉頁面會丟失編輯。刷新能取回原稿的前提是後端任務仍存在。

[page.tsx](../frontend/app/page.tsx) 的 React state 依 job ID 區分 `draftEdit` 與 `copyFeedback`。空字串是合法編輯，純空白不能複製；延遲的複製結果必須符合當時任務與文字，才顯示成功。剪貼簿失敗保留文字並提示手動複製。

編輯、複製、還原不增加模型請求、不回寫後端原稿或評估資料。使用者修改也不重新套用模型原稿檢查，分享前自行核對來源。沒有草稿資料庫、瀏覽器持久儲存或 GitHub 自動發送。

## 練習、優化方向與面試取捨

先做不增加 API 請求的練習，不修改凍結案例或原始報告：

1. 跑 Context 示範，找出省略來源、保留候選與未變的歷史前綴，說明為何 Sources 有資料不代表模型看過。
2. 讀最新 pytest 報告，對照 `partial`、最低查閱檢查的 `false` 及事先驗收協議，分清覆蓋與本輪交付標準。
3. 開啟任一已有網頁結果，將草稿改成兩段，切換頁籤再複製，確認換行；還原後再刷新，觀察編輯保存期限。
4. 比較答案修正測試中的「必要工具前搶答」與「允許收尾後修正」，指出 `phase`、工具選擇及未來預留的差別。

| 設計選擇 | 好處 | 代價／面試可討論的取捨 |
| --- | --- | --- |
| 關鍵字搜尋＋候選本文 | 不需索引，來源與失敗位置容易追蹤。 | 可能漏同義問題；增加讀取又會提高時間與上下文。 |
| 模型判斷＋確定性規則 | 模型解讀語意，程式守住目錄、來源及已知限制。 | 規則有漏判／誤判，格式正確不代表語意正確。 |
| 新結果選材＋固定歷史 | 容易維持工具協定與推理續接。 | 已送內容不能再調整，預留可能提早省略重要留言。 |
| 同證據重新生成 | 不累積整份失敗答案，控制修正成長。 | 重新生成可能改變原本正確欄位，且不能補抓證據。 |
| 固定快照＋真實驗收 | 前者隔離輸入，後者揭露工具與資料變化。 | 小樣本、已知案例與未校準預期都不能估計生產準確率。 |
| 前端編輯與原稿分開 | 無額外模型費用，保留原始輸出的可追溯性。 | 重整會失去編輯，無跨裝置保存。 |

未來可依實際需求評估留言排序、預留估值、引用粒度或範本覆蓋，M2 維持凍結。原始路線圖的下一階段已確認為 [M3：可靠性與持久化](m3.md)，第一小步先完成 PostgreSQL 分析紀錄保存，不重開模型比較。
