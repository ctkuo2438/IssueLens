# M2: Evidence-based issue investigation and editable drafts

M2 adds similar issues, label recommendations, issue templates, context selection, answer repair, and an editable draft to the M1 analysis, so a user can check sources and edit the draft before sharing. It is still a single agent. **Status: frozen.** The limited acceptance on three new cases passed with non-blocking limitations, and user review is pending. One change came after the freeze: the server now reads the issue, its first comments page and the label catalog itself ([Server reads](#server-reads)). The acceptance predates it and has not been rerun; one case was checked live.

Setup is in the [README](../README.md).

## Use

<a id="features"></a>
**Features.** The result shows Analysis (summary, known facts, missing information, and a reply draft), Similar issues, Labels (up to three, never applied), Templates, Sources (bounded excerpts), and Activity (lookups, context selection, rejections, repairs, and stops). The draft can be edited, copied, or restored.

<a id="settings"></a>
**Settings.** Set these in the root `.env`. They are also the code defaults.

```dotenv
OPENAI_MODEL=gpt-5.6
OPENAI_REASONING_EFFORT=medium
AGENT_MAX_ITERATIONS=8
AGENT_MAX_TOOL_CALLS=15
AGENT_RUNTIME_SECONDS=90
AGENT_CONTEXT_TOKENS=24000
AGENT_MAX_CANDIDATES=20
AGENT_MAX_CANDIDATE_READS=5
```

[config.py](../backend/app/config.py) reads them, and exported environment variables take precedence. Restart the backend after a change.

- **Reasoning effort** accepts `none`, `low`, `medium`, `high`, `xhigh`, and `max`, though not every model supports each. Unset means `medium`. Blank sends no `reasoning`, so the provider default applies; `none` is an explicit value. During the M2 evaluation, unset meant the provider default; it changed on 2026-11-15 ([M5](m5.md#settings-file)).
- **`AGENT_CONTEXT_TOKENS`** caps the local estimate of one input. **M2's evaluation and acceptance ran at 12,000**, and every 12,000 below means that budget. The default became 24,000 on 2026-11-13 ([M5](m5.md#context-budget)).
- **`MAX_OUTPUT_TOKENS=2400`** in [agent.py](../backend/app/agent.py) caps one response, reasoning included, and has no `.env` option. A truncated answer is recorded as incomplete and never accepted or acted on.

The on-screen token total sums every model request. None is the model's native window, and 15 logical tool calls are not 15 HTTP requests.

## How it works

The model picks search terms, candidates, and optional background. The code makes the reads that need no choice, and controls scope, required steps, limits, and validation.

<a id="tools"></a>
### Seven read-only tools

| Tool | Scope |
| --- | --- |
| `get_issue` | Target body, state, dates, labels, and comment count. |
| `get_issue_comments` | 10 comments per page, up to 5 pages, 350 text tokens each. |
| `get_repo_readme` | Default-branch README, up to 1,600 text tokens. |
| `search_issues` | Same-repository keyword search over issue titles and bodies. |
| `get_related_issue` | One candidate body found by this run's searches, up to 1,800 text tokens. |
| `get_repo_labels` | First page of the active label catalog. |
| `get_issue_templates` | Up to two files in `.github/ISSUE_TEMPLATE`. |

The tools never run code, tests, or reproductions, and never write to GitHub.

### Server reads

Before the first model request, the server calls `get_issue`, then `get_issue_comments` page 1 if the issue reports comments, then `get_repo_labels`. These reads need no judgment, so they no longer cost a model request each; in the frozen acceptance, three of each run's five or six requests went to them. They are ordinary tool calls: they count toward the 15 tool calls, retry like other lookups, and reach the model as calls with results in its input. If the target issue cannot be read, the run stops before any model request. A replacement Worker skips the reads already in the saved history.

Fewer requests on these reads leave more for optional lookups, and a lookup result that overflows the context budget ends the run without an answer. So a request that leaves the tool choice to the model keeps room for one result as large as a candidate body: it reserves 2,912 tokens and needs at least 2,400. When that room is missing, the model answers from the evidence it has, as when requests are kept for repair, and the run records no limitation because the required checks are done.

### Required lookups

After the server reads, the code requires, in order and within the budget: a search (and a second, different query if the first is empty), and one candidate read if there are candidates. The code checks only that the queries differ. Failed calls keep their status and are not retried endlessly. An early answer sends the run back to investigating. Once these are done, new tools are disabled near the limit so up to two requests remain for repair. If the budget runs short, the run finishes with its evidence and says what it skipped.

The code, not the model, sets `comment_check` to `not_read`, `empty`, `read`, `partial`, or `failed`. `read` means page and count coverage, not that the model saw or understood every comment, and comments can change between requests. `similar_issue_check` separates no search, failure, empty results, unread candidates, and insufficient evidence.

### Similar issues

A search takes one to six keywords and reads only the first page. A run keeps up to 20 candidates and reads up to 5 bodies, never their comments or code. Every body read must appear in a comparison that cites both bodies. Comparisons are tentative: `possible_duplicate` (same symptom and conditions, not proof of the same root cause), `related_but_different`, or `insufficient_evidence`. A detail missing on one side is unknown, not a difference. This is keyword search, not semantic retrieval, so an empty result proves nothing about the repository.

### Labels

The tool keeps complete rows of up to 100 active labels within about 1,600 text tokens, or marks the catalog partial. The answer recommends at most three new labels, each from the catalog, with a reason, citing the target and the catalog. An empty list is valid. [quality.py](../backend/app/quality.py) adds limited English checks: `is_pr_only_label()` excludes labels whose description marks them PR-only, a missing-information label must name the fact that blocks an initial investigation, and `label_consistency_fields()` flags text such as `No label recommendation is made.` beside a non-empty list and asks for a repair rather than deleting anything. The consistency check is one-directional, and none prove relevance.

### Templates

The tool reads only `.github/ISSUE_TEMPLATE` on the default branch: at most two `.md`, `.yml`, or `.yaml` files, 32 KiB each, with excerpts and parsed fields sharing about 2,000 tokens. PyYAML parses data only. YAML `required: true` is required, an omitted flag is optional, and anything else is unknown; Markdown headings carry no required flag. The model is told to use only the matching template and skip what the issue already answers. Today's template may differ from the one in force when the issue was filed, and inherited, legacy, and nested templates are not covered.

<a id="context-builder"></a>
### Context Builder

[context.py](../backend/app/context.py) estimates each whole input with the local `o200k_base` tokenizer plus a 1,024-token margin. It is not billing. Fixed rules, not the model, choose what to send:

- Only new results are trimmed. Sent history, reasoning items, and `call_id` pairs stay unchanged, so a later candidate cannot push out comments already sent.
- Target and candidate bodies, label rows, parsed template fields, metadata, and errors are protected.
- Whole items are omitted in this order: a new README, raw template text that has parsed fields, then low-scoring comments, ranked by keyword overlap with the title and author role.
- Omissions keep their source ID and status, appear in Activity and `result.context_builds`, and make the job partial. Sources still holds them, so a source there was not necessarily seen. Facts citing a source omitted in full are rejected.

Before results are first sent, part of the same budget is reserved so a required candidate still fits later: 256 tokens for repair, 512 for the next turn, 2,400 for the first required candidate, and 1,024 each for pending labels and search. Every request must satisfy:

```text
estimated_tokens + repair_reserve_tokens + future_reserve_tokens <= budget_tokens
future_reserve_tokens >= future_reserve_minimum_tokens
```

If even the minimum does not fit, the run tries a final answer, then one without the repair reserve, then stops. To see the selection without API calls:

```bash
uv run --locked python scripts/context_demo.py
```

### Answer repair

Each turn lists the citation pairs the server accepts, and the backend never adds missing ones. A tool-free answer that fails validation goes to `rejected_answers`, not the evidence history. If a required lookup was pending, the run keeps investigating. Otherwise it enters `repair` with `tool_choice="none"` and regenerates the full JSON from the same input checkpoint plus short feedback, so failed answers do not pile up. Repair stays within the original limits and cannot fetch evidence; a tool call during repair stops the run. Validation is never relaxed to get a completed run.

### Drafts

The draft addresses the issue author in a maintainer's voice, with concrete next steps. The model is told not to ask for what the body or comments already answer. Reproductions are credited to whoever ran them, never to the agent. [quality.py](../backend/app/quality.py) repairs or rejects known English patterns: first-person reproduction, false claims about comment coverage, assistant offers such as `If you want, I can help ...`, unattributed fix or version claims, first-person tracker actions such as closing or labeling, and closure presented as a fix.

`Copy draft` keeps line breaks, and `Restore original` brings back the model's text. [page.tsx](../frontend/app/page.tsx) keeps edits per job: they survive tab switches but not a new job, a refresh, or a closed page. Edits make no model requests, are not saved or rechecked, and are never posted, so check the sources before sharing.

<a id="known-limits"></a>
## Limits

- **PNG `needs-info`:** the PNG case over-recommends `needs-info` in some rounds, so one 5/5 round is not a stable fix.
- **Comment selection:** the rules may keep short comments and omit a key one. In M5, `pallets/flask#6146` at 12,000 omitted the highest-priority maintainer comment ([M5](m5.md#context-budget)).
- **Citation granularity:** rejecting fully omitted sources can block a citation of their metadata, and a correct ID does not prove support.
- **Label and draft semantics:** only known English phrases are checked; relevance, repeated questions, attribution, and version inferences can be wrong.
- **Context reserve:** it makes overruns after a candidate read less likely but guarantees no complete investigation; a real overrun stops the run.
- **Repair state boundary:** only [offline tests](../tests/test_answer_repair.py) cover it; the new cases had no repair, and #4032 was not rerun.
- **Acceptance observations:** HTTPX put investigation unknowns in `missing_information`, and Ruff's rule suggestion and PEP 810 citation could be more careful.
- **Unexercised branches:** the new cases read no template or README, and the live replay bytes were not saved for an audit.
- **Server reads, live:** one case ran twice. OpenAI accepted function calls that the server wrote, which carry no response-item ID, but the three frozen cases were not rerun, so their quality is not compared.
- **Required search reserve:** a forced search keeps only 512 tokens of minimum room, so a large search result could still overflow the budget. Searches come early, when the input is small.
- **Infrastructure:** at the freeze, jobs lived in memory. M3 and M4 later added storage and sign-in; cross-job memory, vector retrieval, multi-agent, and deployment are not done.

Passing the limited acceptance does not close these items.

## Tradeoffs and exercises

- **Keyword search:** no index and easy to trace, but misses issues worded differently.
- **Model plus rules:** code guards catalog and sources, but rules misfire, and valid format is not correct meaning.
- **Fixed history:** keeps the tool protocol and reasoning intact, but sent content cannot shrink, and reserves may drop comments early.
- **Regenerating repairs:** failed answers do not pile up, but correct fields can change.
- **Snapshots plus live runs:** inputs are isolated and real changes show up, but small known samples cannot estimate accuracy.

Exercises: run the Context demo and explain why a source in Sources was not necessarily seen. Compare pytest's `partial` with the protocol, separating coverage from delivery.
