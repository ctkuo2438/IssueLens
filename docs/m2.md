<a id="features"></a>
## Goal and features

M1 reads one issue and shows an analysis. M2 adds grounds for comparison, classification, and follow-up questions, so the user can check the sources and edit the draft before sharing it. M2 is a feature milestone. It is still a single agent, not a multi-agent coordinator.

| Screen / feature | Purpose and observable result |
| --- | --- |
| Analysis | A summary, known facts, missing information, and an English reply draft. |
| Similar issues | Candidates from the same repository, the search scope, what was actually read, and tentative comparisons. |
| Labels | Up to three labels, not yet applied, suggested from the real label catalog, with reasons and sources. |
| Templates | The templates actually fetched, their fields, and whether each is required, optional, or unknown. |
| Sources | Bounded excerpts fetched by the tools, kept for manual checking. |
| Activity | Records of lookups, input estimates, context selection, rejections, repairs, and stops. |
| Editable draft | Edit it directly, copy the current text, or restore the model's original. |

<a id="tools"></a>
### The seven read-only tools

| Tool | Scope |
| --- | --- |
| `get_issue` | The target issue's body, state, dates, existing labels, and comment count. |
| `get_issue_comments` | Comments on the target: 10 per page, up to 5 pages, each excerpt up to 350 text tokens. |
| `get_repo_readme` | The README on the same repository's default branch, with an excerpt of up to 1,600 text tokens. |
| `search_issues` | Keyword search over titles and bodies in the same repository, excluding the target and PRs. |
| `get_related_issue` | Reads only the body of a candidate found by this run's searches, with an excerpt of up to 1,800 text tokens. |
| `get_repo_labels` | The first page of the same repository's active label catalog, keeping complete name/description rows. |
| `get_issue_templates` | Up to two supported files in `.github/ISSUE_TEMPLATE` on the same repository's default branch. |

The tools never run code, tests, or reproductions. They never apply labels, post comments, close issues, or merge PRs. The model chooses search terms, candidates, and optional background. The code controls scope, required steps, and limits.

<a id="settings"></a>
## Model and budget settings

Set these in the root `.env`. If it is already set up, keep the existing file and keys.

```dotenv
OPENAI_MODEL=gpt-5.6
OPENAI_REASONING_EFFORT=medium
AGENT_MAX_ITERATIONS=8
AGENT_MAX_TOOL_CALLS=15
AGENT_RUNTIME_SECONDS=90
AGENT_CONTEXT_TOKENS=24000
AGENT_MAX_CANDIDATES=20
AGENT_MAX_CANDIDATE_READS=5
```

All six agent budgets above have defaults in code, so leaving them out of `.env` gives the same numbers. Writing them out makes them easier to track; it does not mean you must raise them. [config.py](../backend/app/config.py) reads the settings, and exported environment variables take precedence over `.env`.

### Reasoning effort

The code accepts `none`, `low`, `medium`, `high`, `xhigh`, and `max`, but not every model supports every value.

- **Unset:** uses `medium`, the same way the model defaults to `gpt-5.6`.
- **Explicitly blank:** sends no `reasoning`, so the provider default applies.
- **Literal `none`:** an explicit setting. It is not the same as blank.

During the M2 evaluation, unset also meant the provider default. On 2026-11-15 it changed to `medium` so that installed copies with only the keys configured use the evaluated setting; see [M5](m5.md#settings-file). Investigation and repair use the same setting. After a change, restart the backend and start a new analysis for it to take effect.

### Output limit and context budget

The output limit is `MAX_OUTPUT_TOKENS=2400` in [agent.py](../backend/app/agent.py). There is currently no `.env` option for it. The limit covers both reasoning and visible output. If the API explicitly reports that it was exhausted, the run keeps its sources and records the result as incomplete. It does not accept a truncated answer or run tools from it.

M2's evaluation and acceptance all ran with `AGENT_CONTEXT_TOKENS=12000`. Every other 12,000 in this guide refers to that budget of the time. On 2026-11-13 the default changed to 24,000; see [M5](m5.md#context-budget) for the reason and the verification.

Keep three numbers apart:

- 24,000 is the **local estimated limit for one input**.
- 2,400 is the **output limit for one request**.
- The total tokens on screen are **the sum of the usage reported by every model request in the analysis**.

None of them is the model's native context window. Switching models does not lift the local budget, and 15 logical tool calls are not 15 GitHub HTTP requests.

Activity and new evaluation reports record the requested model, effort, and output limit. An effort of `null` in a report means none was specified; it does not confirm that the effective effort was `none`. Older reports were not backfilled with these settings.

<a id="required-lookups"></a>
## Comments and required lookups

After the target is read successfully, a normal investigation checks these in order, within the budget:

1. If the issue reports comments and the first page has not been validly attempted, require `get_issue_comments(page=1)`.
2. If the label catalog has not been attempted, require `get_repo_labels`.
3. If no search has run, require `search_issues`. If the first search succeeds but is empty, require a second, different query.
4. If candidates were found, no candidate body has been fetched successfully, and no candidate read has been validly attempted, require `get_related_issue`.

The code only checks that the two queries differ. It cannot prove the second one is semantically broader. Invalid arguments, the wrong tool, or using the target as a candidate do not count as a valid lookup. A valid tool call that fails keeps its failed status and is not forced to retry without end. Every candidate read successfully must appear in the final cited comparisons.

Required lookups take priority over the requests reserved for repair. Once the minimum checks are done and at least six iterations are configured, new tools are disabled near the limit so that up to two requests remain for repair. This does not add requests. If the model answers early while a required tool is still being requested, the run goes back to investigating. If the hard budget runs short, the run may finish early with the existing evidence and must state what it did not read or compare.

### The code computes comment status

[github.py](../backend/app/github.py) maintains `CommentCheck`. GPT does not fill in whether it read every comment.

| Status | Meaning |
| --- | --- |
| `not_read` | No page read has been validly attempted. Metadata that reports zero comments does not turn this into a successful lookup. |
| `empty` | The successfully covered chain of pages is empty, with no next page, no failed page, and no conflict with a known count. |
| `read` | Read continuously from the first page to the last, with no next page or unrecovered failure, and consistent with the known count. |
| `partial` | A next page remains, or there is a page gap, a partial failure, or a count mismatch. |
| `failed` | Attempted, but no page succeeded. This cannot be taken to mean there are no comments. |

`read` means page and count coverage. It does not guarantee that each comment's text is complete, that the model saw every excerpt, or that it understood them correctly. Truncation of the original text and whole-comment omission by the Context Builder are recorded separately, and the bounded Sources are not a complete archive. Comments can change between requests; there is no atomic snapshot.

Likewise, these are recorded separately: a successful search with no candidates, no search yet, a failed search, unread candidates, and insufficient evidence after reading. Check them with `comment_check` and `similar_issue_check` in the API and reports, and with Activity. Passing the required lookups still does not mean the answer is semantically correct.

<a id="similar-issues"></a>
## Similar issues: search first, then read and compare

`search_issues` accepts one to six keywords. The backend fixes the scope to the same repository, to issues only, and to titles and bodies. Each search reads only the first page. By default a run keeps up to 20 distinct candidates and tries to read up to 5 candidate bodies. An incomplete search, a remaining next page, a reached limit, or a failure is kept as a limitation.

A candidate is only a search hit. `get_related_issue` rejects numbers that the search did not find, and it does not read candidate comments, code, fixes, or tests. A comparison must cite both the target body and the candidate body. A search snippet cannot replace them.

| Tentative relationship | Required grounds |
| --- | --- |
| `possible_duplicate` | Concretely the same symptom and conditions. This still does not prove the same root cause. |
| `related_but_different` | A substantive difference in purpose, behavior, or failure conditions. |
| `insufficient_evidence` | Both sides were read, but the information cannot confirm whether they are the same or different. |

If one issue gives no platform and the other says Linux, the first is unknown. That is not a platform difference. Level of detail, wording, or open/closed state alone does not prove a different problem either. An unfinished comparison shows `Not compared`, which differs from a finished comparison with insufficient evidence.

This is keyword search. Semantic retrieval is not implemented. A successful empty search only means that these conditions found no hits in this run. It cannot claim that the repository has no related issues. A repeated successful request may use this run's cache, so it does not necessarily send another HTTP request.

<a id="labels"></a>
## Labels: recommend from the catalog and check text consistency

A label is a tag that a repository uses to classify and filter issues. `get_issue` provides only the labels already applied. `get_repo_labels` fetches the available names, descriptions, and colors. It reads the first page of up to 100 labels and excludes archived ones. Complete name/description rows share about 1,600 text tokens. If a whole row does not fit or a next page exists, the catalog is marked partial.

The final answer recommends at most three labels. Each one must:

- come from the loaded active catalog;
- not duplicate an existing label or another recommendation;
- have a non-empty reason;
- cite the target and the catalog.

Matching ignores case, and the answer uses the catalog's original spelling. An empty list is valid. These are different cases: an unread catalog, a failed read, an empty catalog, a checked catalog with no suitable new label, and no valid answer.

### Label scope and missing-information labels

`is_pr_only_label()` in `quality.py` recognizes a limited set of English PR-only phrases in the label **description**, such as `Pull requests that update Python code`. It is not a blocklist of names such as `python`. Labels shared by issues and PRs, descriptions that merely mention PRs, and empty descriptions are not excluded by it.

The tool keeps the original catalog and Sources and tells the model the exclusion list separately. Final validation checks again against the server-side catalog. Excluding PR-only labels does not turn a complete catalog into a partial one. Passing this check only means that no known restriction matched. It does not prove topical relevance.

To recommend a missing-information label, the model must say which required fact is missing and why that blocks an initial investigation. Wanting more logs or other platforms, or a root cause that is not yet confirmed, does not support such a label on its own. A follow-up question can be useful without recommending `needs-info`.

### List and text consistency

When the recommendation list is not empty, `label_consistency_fields()` finds known no-recommendation phrases in fields such as the summary, limitations, and draft. For example, the list contains `bug`, but the text says `No label recommendation is made.`

It covers `is/are/was/were/has been/have been made`, `being made`, and a limited set of `currently/now` variants. A recommendation noun must come before `made`, so that "no labels were applied on GitHub" is not read as "no recommendation". Known exceptions for conditions, attribution, and text that names every recommendation are judged separately.

When it finds a contradiction, it reports the fields and asks for a bounded repair. It never silently deletes text or labels. This is a one-directional check of limited English phrases. It cannot verify all counts, the reverse contradiction, or general semantic consistency. Valid names, scope, and citations still do not mean the overall judgment is right.

<a id="templates"></a>
## Templates: ground follow-up questions in the project's real requirements

An issue template is the project's guide for people filing issues. The tool runs only after the target was read successfully, and it always reads `.github/ISSUE_TEMPLATE` on the current default branch. It does not accept another path from the model.

| Limit | Behavior |
| --- | --- |
| File scope | Regular `.md`, `.yml`, and `.yaml` files. Config files, symlinks, submodules, and nested directories are excluded. |
| Read count | Sorted by file name, with at most two attempted. One tool call can make one directory request and two file HTTP requests. |
| Size and excerpt | Up to 32 KiB per file, and up to 750 text tokens per source excerpt. |
| Packing | Parsed data and excerpts share about 2,000 tokens, plus up to 400 tokens of lookup summary. |
| Fields | Up to twelve input fields, and up to six required checkbox options per group. |

PyYAML only parses data. It rejects anchors, aliases, custom tags, and deep nesting. It is not a full GitHub schema validator. In YAML, an explicit `required: true` is required, a validly omitted flag is optional, and anything it cannot recognize is unknown. Markdown headings have no structured required flag, so they cannot all be treated as required.

The model is told to pick only the template that applies and to check first whether the body or comments already contain equivalent information. Prefilled examples are not facts from the reporter. The current template does not prove that the same requirements applied when the issue was created. A missing directory is a successful, scoped lookup; failures and lookups not attempted are listed separately. Templates inherited from the organization, legacy single-file templates, and other directories are not covered.

<a id="context-builder"></a>
## Context Builder: select within the original budget

Context is what is sent to the model: instructions, tool definitions, the JSON answer format, history, and evidence. [context.py](../backend/app/context.py) estimates the whole input with the local `o200k_base` tokenizer and adds a 1,024-token margin. This is an estimate. It is not API billing or a guarantee about the native window.

Rules we wrote decide what to include. GPT is not asked what to keep, and there is no summarization model, database, or cross-job memory.

### Only new results that were not sent yet are trimmed

1. An exact duplicate result is replaced with a pointer to the earlier `call_id` when that is shorter. Short results can be kept. Something omitted earlier does not count as seen just because it was read again.
2. Repeated search excerpts can be represented by the structured search fields already kept, without losing coverage or error status.
3. These are protected: target and candidate bodies, label rows, parsed template fields, and all metadata, lookup, and error information that is not an excerpt.
4. When space is needed, it omits whole items in this order: a new README, then raw template text that already has parsed fields, then low-scoring comments. Comments are ranked by keyword overlap with the title and by author relationship. On a tie, the earlier comment in the batch is omitted first.
5. Source IDs, URLs, status, and an omission note are kept. If the note would be longer than the excerpt, that excerpt is not omitted. If important data still does not fit, the run stops explicitly.

The history prefix already prepared for sending, the SDK tool-planning output, reasoning items, and `call_id` pairs stay unchanged. A later candidate cannot push out comments that were already sent. This makes the protocol easier to check, at the cost that accumulated history may still not fit.

Sources keep the excerpts within the original tool limits. Activity, the limitations, and `result.context_builds` list the omitted sources. An omission makes the job partial; a duplicate reference with no data loss does not add a limitation by itself. Keep these apart: not fetched, failed, fetched but not sent, and truncated by the tool. What the model did not see is not something the author failed to provide.

The backend rejects facts that cite a comment or README that was omitted in full. Parsed template fields that were kept can still be cited. There is still a known limit on citation granularity between metadata and body text.

### Reserving space in advance

To avoid finding out, after comments were sent, that a candidate no longer fits, a target for future space is set before results are first sent. It comes out of the same budget (12,000 during M2):

| Reserve | Purpose |
| --- | --- |
| Repair: 256 tokens | Room for short validation feedback. |
| Base continuation: 512 | Estimated growth of the next turn. |
| Plus 2,400 for the first required candidate | The candidate excerpt limit of 1,800, plus 600 estimated for wrapping and citations. Also reserved while a required search could still find candidates. |
| Plus 1,024 each for labels and the required search | An estimate for pending lookup results and loop growth, released once the lookup is done or has failed. |

After the target is read, with labels and search both pending, the future target is usually 4,960. After labels it is 3,936, and after candidates are found it is 2,912. The minimum is 512 for ordinary planning and 2,400 for the request that requires the first candidate read. If the target cannot be fully met, the run can still continue as long as the minimum is met.

`future_reserve_target_tokens` is the target, `future_reserve_tokens` is the actual allocation, and `future_reserve_minimum_tokens` is the minimum. Every request sent must satisfy:

```text
estimated_tokens + repair_reserve_tokens + future_reserve_tokens <= budget_tokens
future_reserve_tokens >= future_reserve_minimum_tokens
```

`estimated_tokens` already includes the 1,024 margin, so it is not added again. If even the minimum does not fit:

1. The tool requirement is dropped, and the run tries a final answer that keeps the repair reserve.
2. If needed, it tries an input without the repair reserve.
3. If that still does not fit, it stops.

Early finalization and real answer repair have a future reserve of zero, and unexpected tool calls are not run. An unread status is never changed into a successful empty result.

These are estimates, not maximum tool sizes. Extra candidates, JSON escaping, very large metadata, or opaque reasoning can still exceed them, so an answer is not guaranteed.

<a id="answer-repair"></a>
## Citations and bounded answer repair

Each turn provides the exact citation pairs that the server keeps: a label recommendation needs the target plus the catalog, and a comparison needs the target plus the candidate body. The backend does not add missing citations automatically. A correct ID still does not guarantee semantic support.

A tool-planning response continues with the complete SDK output in its original order, including encrypted reasoning and tool pairs. A tool-free answer that was allowed to finish but failed validation is stored separately in `rejected_answers`, with its text, reason, fingerprint, and bounded feedback. Neither it nor its reasoning is added to the evidence history.

The next turn regenerates the full JSON from the **same investigation input checkpoint**. It carries only the current short feedback and does not pile up failed answers. Repair uses the 256-token reserve set aside earlier; once the feedback is counted in that turn's input, it is not reserved again. Every attempt still counts against the original request and time limits.

### Early answers and answer repair are different states

| Situation | Next turn |
| --- | --- |
| A required tool is still being requested, but the model answers early | Records the rejection, stays in `investigation`, and continues the required lookups. |
| Finishing was allowed, but validation failed (text, citations, and so on) | Enters `repair` with `tool_choice="none"`. It does not reschedule comments, labels, search, or candidates. All three future-reserve fields are zero. |

Activity shows `Answer repair step ... tools disabled`. An unexpected tool call during repair stops the run and is not executed. Unread and uncompared items stay incomplete. Repair cannot fetch new evidence; it can only correct how the existing evidence is stated.

The latest state fix has 18 offline answer-repair tests, including six new boundary regressions, and the full suite of 262 tests and Pyright passed. The three new cases had no repair events, so that run cannot be claimed to have exercised the latest state switch for real. A genuinely oversized input, repeated failures, or API errors can still leave no final answer. Validation is not relaxed to get a completed run.

<a id="drafts"></a>
## Drafts: maintainer voice, source attribution, and editing

The draft is written to the issue author and contributors. It states concrete next steps directly and avoids assistant-style service endings such as `If you want, I can help ...`. It may ask no follow-up questions: `missing_information=[]` is valid.

Before asking a follow-up question, the model is told to check the body and visible comments for an equivalent answer, steps already tried, and explanations of why a step does not apply. A reproduction is attributed to whoever actually ran it, never written as if the agent tested it. Issue and comment dates help attribute past plans, but they do not prove the current code or release state.

[quality.py](../backend/app/quality.py) catches known problems with a limited set of English patterns. It repairs or rejects within the original budget and never rewrites Sources:

| Check | Scope and boundary |
| --- | --- |
| First-person reproduction | Known positive `I/we reproduce/replicate` forms in fields the model writes. Requires third-person attribution. |
| Comment claims | Known forms that say unread comments do not exist, or that all comments were seen when coverage is incomplete. |
| Maintainer voice | Known assistant service offers in `draft_reply`. |
| Temporal attribution | Unattributed fix announcements, current capability gaps, or claims that a version fixed something, in the draft. |
| Actions not performed | First-person tracker actions in the draft, such as closing, assigning, labeling, merging, or posting a reply. Closing a database connection is not treated as an issue action. |
| Closure read as a fix | Known phrasing in the draft that pairs closed with resolved or presents closing as the cause of a fix. Closed state alone does not prove a fix. |

Known negations, questions, conditions, and attributions have local exceptions, but whether an attribution is true is not verified. These rules can miss or misfire. In particular, they do not fully cover other fields, tenses, or repeated follow-up questions. No match is not a general semantic guarantee.

### What editing and copying keep

Edit the draft in place. `Copy draft` copies the current text with its line breaks, and `Restore original` restores the model's original. Switching tabs keeps edits. Starting a new job, refreshing, or closing the page loses them. A refresh can bring back the original only if the backend job still exists.

The React state in [page.tsx](../frontend/app/page.tsx) keeps `draftEdit` and `copyFeedback` separate for each job ID. An empty string is a valid edit, but whitespace-only text cannot be copied. A delayed copy result shows success only if it matches the job and text of that moment. If the clipboard fails, the text is kept and the page asks you to copy it manually.

Editing, copying, and restoring make no model requests and do not write back to the backend's original or to evaluation data. User edits are not rechecked with the rules applied to the model's original, so check the sources yourself before sharing. There is no draft database, no persistent browser storage, and no automatic posting to GitHub.

## Exercises and tradeoffs

### Exercises

Start with exercises that make no API requests. Do not change the frozen cases or the raw reports.

1. Run the Context demo. Find the omitted sources, the kept candidate, and the unchanged history prefix, and explain why data in Sources does not mean the model saw it.
2. Read the latest pytest report. Compare `partial`, the `false` from the required-lookup check, and the acceptance protocol set in advance, and separate coverage from this run's delivery standard.
3. Open any existing result in the web app and rewrite the draft as two paragraphs. Switch tabs, then copy it and confirm the line breaks. Restore it, then refresh, and observe how long edits are kept.
4. In the answer repair tests, compare an early answer before the required tools with a repair after finishing was allowed. Point out the differences in `phase`, tool choice, and future reserve.

### Tradeoffs for interview discussion

| Design choice | Benefit | Cost and tradeoff to discuss |
| --- | --- | --- |
| Keyword search plus candidate bodies | No index is needed, and sources and failure points are easy to trace. | Can miss issues described with different words; reading more raises time and context. |
| Model judgment plus deterministic rules | The model interprets meaning; the code guards the catalog, the sources, and known limits. | Rules can miss or misfire, and a correct format does not mean correct meaning. |
| Selecting from new results with a fixed history | Keeps the tool protocol and reasoning continuation intact. | Content already sent cannot be adjusted, and reserves may omit important comments early. |
| Regenerating from the same evidence | Failed answers do not pile up, so repair growth stays under control. | Regeneration can change fields that were correct, and it cannot fetch more evidence. |
| Fixed snapshots plus live acceptance | The first isolates inputs; the second exposes changes in tools and data. | Small samples, known cases, and uncalibrated expectations cannot estimate production accuracy. |
| Frontend edits kept apart from the original | No extra model cost, and the original output stays traceable. | A refresh loses edits, and nothing is saved across devices. |
