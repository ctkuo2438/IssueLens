# M3: Reliability and persistence

With PostgreSQL enabled, a separate background Worker runs the analyses, so restarting only the API does not stop an investigation. If the Worker is interrupted, a new process reads the model and tool state back from a **checkpoint** and continues the same job, and the web page shows its Activity and results at the same URL. Both M3 completion criteria from the original proposal are verified; cross-job Repository Memory is not implemented yet.

## Goal and scope

### Comparison with the original proposal

Pages 6-7 of the original IssueLens proposal put Redis and Celery in the job queue. Redis receives pending jobs, and a Celery Worker runs analyses in the background and handles retries. Page 14 sets the M3 completion criteria: interrupted jobs can recover, and data is persisted.

The local version implements this flow with a PostgreSQL queue and a separate Worker. When the Worker claims a job, the status and the first checkpoint are committed in the same transaction. Both M3 functional criteria are verified:

- A real analysis returns its original result after an API restart. See the [live persistence check](#live-persistence-check).
- Integration tests with a real Worker and PostgreSQL confirm that a replacement Worker continues the same `job_id` and that its retries and Trace can be read back. These tests use simulated model and GitHub responses. See the [Worker restart verification](../evidence/m3/trace.json).

Page 11 also plans a cross-job Repository Memory that saves and updates repo rules, labels, and issue templates. Today the tool cache is scoped to a single analysis. Saving and updating across jobs is not implemented yet.

### Steps

M3 was built in five steps:

1. **Persistence.** Persistence keeps data readable after the process ends. Step 1 stores jobs and results in PostgreSQL and verifies that reopening the web page reads existing records back.
2. **Background Worker.** Step 2 moves the running agent into a background Worker. Deploying or restarting the API then only interrupts HTTP connections for a moment, while the agent's memory and its pending model/tool requests stay in the Worker. PostgreSQL holds both the snapshots and the queue of pending jobs, so a local start needs only the existing database.
3. **Checkpoints.** Step 3 also commits the agent's execution state to PostgreSQL. A replacement Worker reuses the completed model responses, tool results, and source numbers, and continues from the original job's remaining budget. The web page reads the same `JobSnapshot` as before.
4. **Bounded retry.** Step 4 handles temporary failures of external services. Bounded retry lets a single failed model or tool call be retried once, so a brief timeout has a chance to recover, while the original job's count and time budgets cap the cost.
5. **Trace.** Step 5 adds a **Trace** (execution record). With retries and resumption across processes, one analysis can include successes, failures, retries, and interruptions. Querying these attempts by job ID shows where the time went or why the run stopped, and whether retries stayed within the original budget.

The database is already running on this machine, so start the app with the usual commands:

```bash
uv sync --locked
uv run --locked python scripts/dev.py
```

With `DATABASE_URL` and `OPENAI_API_KEY` set, the launcher starts the API, the Worker, and the front end, and prints the API and Worker PIDs.

- If the API exits, the launcher restarts it and keeps the same Worker. After repeated failures, the wait starts at 2 seconds and doubles up to 30 seconds.

- `Ctrl+C` in the launcher stops the API, the Worker, and the front end. On a graceful shutdown the Worker stops running, and PostgreSQL keeps the last committed checkpoint and the jobs waiting to be claimed. After the next start, the Worker can continue within the original job's time budget.

## How it works

### Data flow

Psycopg, the new dependency, is a PostgreSQL driver. It only handles database connections and SQL; we still implement the agent and the persistence flow ourselves. uv and the lock file manage the dependency.

`issuelens_analyses` keeps the `job_id` primary key, a JSONB snapshot, and an update time. JSONB is PostgreSQL's JSON storage type. The `JobSnapshot` format keeps its existing fields: status, creation time, result, sources, usage, rejected-answer audit, limitations, and events. The queue uses the snapshot's `queued` status, and a cancellation request lives in a separate boolean column, `cancel_requested`, on the same row. The index covers only queued and running records.

The same row has a `checkpoint` column: private JSON text used by the Worker. It keeps the original order of the replay items and of the JSON fields, for local token estimates and for the next request. A checkpoint holds:

- the replay items and `call_id` values from model responses;
- the Context Builder state;
- the tool cache and sources;
- answer-repair feedback;
- the model, tool, and time budgets used so far.

`trace` is a separate JSONB column, committed together with the matching snapshot and checkpoint. The result API reads `snapshot`, and the Trace API reads the attempt records and the job status.

| When | What happens |
| --- | --- |
| Create a job | The API commits a `queued` snapshot and returns 202. At most 30 jobs can be queued or running. |
| Claim a job | The Worker resumes jobs that already started first. When it claims a queued job, it commits `running` and the first checkpoint in the same transaction. At most two jobs run at once. |
| Progress | The Worker saves the attempt count before each external call and updates the checkpoint after each model response or tool result. The checkpoint, its Activity, and its Trace are committed together. The API reads the snapshot periodically and sends the events the page has not received yet over SSE (server-sent events). |
| Finish and reconnect | When the Worker commits the final result and Trace, it clears the private checkpoint in the same commit. If a finished result is already stored in the checkpoint, a new Worker can publish it directly. The API resumes from the last event ID the client received and sends the full snapshot with `done`. |
| Cancel | The API cancels a queued job directly. If the job is already running, the API returns 202, and the Worker stops the analysis when it reads the cancellation request and saves the result it has at that point. If the analysis finishes first, the page receives that result. |

The one-hour cache expiry applies to memory mode. In PostgreSQL mode, the 30-job limit counts only active jobs, and historical snapshots are kept.

The API uses a connection pool with up to two connections, and the Worker uses one asynchronous database connection. A PostgreSQL session advisory lock is a cooperative lock held by a connection. Only one Worker per database can hold this lock, so a replacement process can continue only after the old connection releases it. API startup and shutdown manage only the API's own connections.

During claim and cancel, row locks make the state transitions of one job happen in order. Queries use parameters, and progress writes update only rows that are still `running`. See [PostgreSQL 14 row locks and advisory locks](https://www.postgresql.org/docs/14/explicit-locking.html).

### Interruptions and failures

While the API restarts, the web page retries its connection. After the Worker stops, committed model or tool turns can be reused directly.

- If a first call is interrupted before its response is saved, that attempt still counts against the budget. Within the remaining budget, the model starts its next request from the existing evidence, and a pending read-only tool resumes its read with the original `call_id`.
- If the interrupted call was a retry that had already started, that call's retry is treated as used.
- The report's token total adds up the model responses actually received.

Runtime counts from the first claim and includes downtime. After the time limit, the run finishes with the data it has. A cancellation request that has already arrived takes priority.

How the Worker handles stored records when it recovers:

- A `running` job from an older version that has only a public snapshot, or a job whose checkpoint is incompatible with the current settings, keeps its saved data and is marked `cancelled`.
- A record whose stored content the current version can no longer read is marked `failed`. See [Unreadable records](#unreadable-records).
- `queued` jobs are claimed as usual.

A database read failure returns 503, and a missing record returns 404. When the Worker loses its connection, it pauses and reconnects. Other storage errors, for example PostgreSQL refusing to save a value, stop the Worker and report the error. The API publishes only committed results. After the database recovers, the API reconnects automatically, and the Worker reacquires its lock in the same process and handles interrupted and queued records as described above.

### Database reconnects

When PostgreSQL restarts or the network drops, existing connections break. Previously the API had a single connection that never reconnected, so after the database recovered it kept returning 503 until someone restarted the API by hand, and the Worker simply exited. Before a public trial, a short database outage should recover on its own.

- **The API reconnects through a connection pool.** The pool checks each connection before handing it out and discards broken ones. One reconnect attempt lasts at most three seconds, and a later request starts a new attempt, so the next request after the database recovers succeeds without waiting through a long backoff.
  - The pool holds at most two connections. After a restart every idle connection is stale, and the pool waits about 0 seconds and then 1 second between two failed checks. With only two connections, a request can still get a fresh connection within three seconds.
  - During an outage, each database operation waits at most three seconds and then returns 503. Signed-in routes look up the session first and then the analysis, so they take up to about six seconds.
  - Startup still requires a reachable database. The table schema is checked only once, at startup, to avoid competing with writes for locks, so the API must be restarted if the database is recreated.
- **The Worker reconnects only when it loses its connection.** The Worker's exclusive ownership is an advisory lock tied to its connection. When the connection drops, the lock is already released, and continuing could let another Worker process the same job at the same time.
  - So the Worker first suspends its running analyses and closes the connection. Then it reconnects and reacquires the lock at intervals of 1, 2, 4, and 5 seconds, and follows the same recovery flow as at startup, resuming the analyses from their checkpoints.
  - If the connection drops again soon after a reconnect, the interval keeps growing. It starts over from 1 second only after the Worker has run for more than a minute.
  - The Worker does no work before it holds the lock again. This is as safe as restarting the process, but needs no external restart mechanism. The reconnect skips the table check, so it does not compete with API writes for locks.
- **Other storage errors stop the Worker.** An error while the connection is still healthy, for example PostgreSQL refusing to save a value, would happen again after a reconnect. Such errors stop the Worker and show the error, instead of repeatedly suspending other analyses and spending their budgets. The Worker also exits at once if it cannot reach the database at startup or the settings are wrong. If a shutdown during an outage cannot save results, the process exits with an error status.
- **Logs do not contain the connection URL.** The pool logs every failed connection attempt. libpq error messages can repeat parts of the URL, including the password, so these log lines keep only the exception type. Startup also parses the URL first, and a malformed URL returns a sanitized error at once.
- **Silent disconnects are detected.** The client sets TCP keepalive and `tcp_user_timeout`, so a connection whose network path disappeared without a close signal is found dead within tens of seconds. The server side also sets keepalive, so PostgreSQL ends the dead connection and releases the Worker lock it holds. Otherwise a reconnecting Worker could wait for the operating system's limit, which can be hours. A regular, non-superuser account can set these values when it connects. Silent disconnect detection was not verified with a local simulation.

<a id="unreadable-records"></a>
### Unreadable records

After a data model change, old records may no longer match the current format, for example when a field is renamed or fewer values are allowed. When the Worker claims jobs, running records come first. Previously, one unreadable record stopped the Worker, and none of the queued analyses behind it ran.

Now, when the Worker claims a job, or recovers an interrupted job at startup, and the snapshot or Trace fails validation, it changes that record to `failed` in the same transaction:

- The error message says the current version cannot read the record.
- The issue URL and creation time are kept if they are still readable, and the owner does not change.
- The Trace stop reason is `record_incompatible`.
- The original snapshot and Trace are saved in the `incompatible_record` column for later inspection, so they are not overwritten or lost.
- The Worker then claims the next analysis, and the log records the ID of the stopped job.

If the URL cannot be read, the snapshot's `issue_url` is an empty string. The result page then shows no issue link but still shows the failure message. Previously the front end parsed this URL directly, and the whole page failed to load. This was reproduced with headless Chrome and a mock API, and the fix was confirmed the same way.

```bash
ISSUELENS_TEST_DATABASE_URL=postgresql://issuelens@127.0.0.1:5432/issuelens_test \
  uv run --locked python -W error::RuntimeWarning -m unittest discover -s tests -p 'test_persistence.py' -v \
  -k IncompatibleRecordTests -k test_worker_retires -k test_worker_startup_retires
```

Four checks should pass.

- Two offline checks confirm that readable fields are kept, and that invalid URLs, timestamps without a time zone, or non-object content fall back to safe defaults.
- The integration checks confirm that an unreadable queued record is marked `failed`, its original content is saved in `incompatible_record`, an analysis queued after it completes normally, and both the result and Trace APIs can read them. They also confirm that an unreadable interrupted record is marked `failed` when the Worker starts.

### Bounded retry

- **What is retried.** Timeouts, retryable connection errors, temporary HTTP `408`, `500`, `502`, `503`, and `504`, and recognizable temporary rate limits can trigger a retry. Credential, permission, billing/usage quota, and request content errors are handled at once, without a retry. A GitHub `403` needs an explicit rate-limit signal. See [OpenAI error codes](https://developers.openai.com/api/docs/guides/error-codes) and [GitHub rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#exceeding-the-rate-limit).
- **How long it waits.** A retry waits at least one second and respects the service's `Retry-After` and the rate-limit reset time that GitHub provides. If GitHub is known to be rate limited but gives no usable wait hint, the retry waits one minute. If the requested wait is longer than the job's remaining time, the run keeps the failure reason and finishes with the evidence it already has.
- **Budget.** Each retry uses one of the original model or tool calls. The candidate read count is also saved before a candidate body is read. The default limits are still 8 model requests, 15 tool calls, 5 candidate body reads, and 90 seconds. When the last model request slot is used, the run finishes under the existing rule, with tools turned off.
- **Across Workers.** The checkpoint saves the retry reason, the earliest retry time, and the current attempt. A new Worker continues the same `job_id` and decides the next step from the counts and wait time already used. A GitHub wait limit also applies to later requests in the same job. When a tool retry succeeds, the model still receives only one result for the original `call_id`.

If the model runs out of retries, an analysis that already has sources is saved as a partial result. If a tool runs out of retries, that call returns a failed status, and the agent can finish with the evidence it has, within the remaining budget. When the template tool returns a partial result, it keeps the files it read and the coverage limitation. The unit of retry is one model request or one failed tool call.

First run the simulated check below and watch Activity for `Retrying`, successful retries, and budget-exhausted messages. Then use the dedicated database command from the [Worker restart check](#worker-restart-check) to check that a replacement process retries only after the saved time.

```bash
uv run --locked python -W error::RuntimeWarning -m unittest discover -s tests -p 'test_retry.py' -v
```

<a id="trace"></a>
### Trace

With the API running, set `JOB_ID` to the value after `analysis=` in the analysis page URL. Use that ID to query the Trace while the analysis runs or after it finishes.

```bash
JOB_ID=replace-with-job-id
curl -fsS "http://127.0.0.1:8000/api/v1/analyses/${JOB_ID}/trace" |
  uv run --locked python -m json.tool
```

- The response contains `job_id`, the job `status`, the overall `stop_reason`, and `attempts` sorted by `id`. Each attempt has a kind, a name, a running count for its kind, a start time, a duration in milliseconds, and an outcome. Reason fields use categories and messages defined by the server.
- When the original call fails temporarily, `retry_scheduled_for` stores the earliest retry time. A new entry is added only when the retry actually starts, with `is_retry` set to `true` and `retry_of` pointing to the `id` of the failed attempt. When retries or the tool budget run out, the reason appears in the failed attempt's `stop_reason`.
- `duration_ms` is measured with a monotonic clock, from when the attempt is recorded until its result is received and classified. It includes the checkpoint save before the call. Retry waits fall between two attempts. If a replacement Worker finds only the start record of an attempt, that attempt is marked `interrupted` and its duration is `null`.
- Older jobs return their original status, and a job with no saved attempts shows an empty list. A missing job returns 404. In memory mode, the Trace can be queried within the same API process; PostgreSQL provides persistence across processes.

To check it, run the [Worker restart check](#worker-restart-check) command and confirm in the output that the two process tests pass.

## Known limits

- When the Worker is interrupted, model or tool attempts that were not saved yet still count against the budget.
- If publishing a result hits a storage failure, other analyses in the same round that already finished but were not published yet may rerun from their last checkpoint.
- When GitHub content contains a NUL character, PostgreSQL JSONB refuses to save it, and the Worker stops.
- Connection parameters set in the code override parameters of the same name in `DATABASE_URL`.
- Unreadable record handling covers only records the Worker claims. If the API reads an unreadable record that the Worker has not processed yet, it still returns 503.
- The Activity of an unreadable old record does not appear in the new snapshot. The original events are kept in `incompatible_record`.

## Tradeoffs

These are useful topics for interview discussion.

- **PostgreSQL as both queue and snapshot store.** One transaction can commit the job state, and there is one less local service to maintain. The cost is that every progress update rewrites the whole JSONB, and web subscriptions read the database periodically. As load grows, measure these two costs before you consider notification-based wakeups or a separate queue.
- **Retries and checkpoints.** When is a retry worth one call from the original budget, and how long may a service ask the run to wait before it should return a partial result instead? Checkpoints add writes, but they let completed work and the remaining retry state survive a process replacement.
- **External restart versus in-process reconnect.** Compare letting the process stop so something outside restarts it with reconnecting inside the process. Both rely on the same safety rule: once the lock is gone with the connection, do no work until the lock is held again. An in-process reconnect does not depend on an external restart mechanism, so it recovers both under a manual start and on a deployment platform. The cost is that the Worker must handle suspending and reopening itself. The reconnect wait cap is also a tradeoff: a longer cap means fewer attempts during an outage, but a longer wait after the database recovers. Here a failed connection attempt is cheap, so both the API and the Worker use a short cap.
- **Stopping the queue versus isolating one record.** Stopping makes sure the problem gets noticed, but one record affects every user. Isolating lets other jobs continue, but the original data must be saved separately and logged so the problem is not ignored. This is the dead-letter pattern common in message queues.
- **Trace storage.** Compare committing a bounded record in the same row as the checkpoint with creating a separate row for each attempt. The first reuses the existing write and reads a whole job in one query, but every write updates the whole Trace. To diagnose performance bottlenecks later, you can measure checkpoint time and external request time separately.
