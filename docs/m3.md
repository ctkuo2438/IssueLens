# M3 可靠性與持久化

啟用 PostgreSQL 後，分析由獨立的**背景 Worker** 執行。只重啟 API 時，Worker 繼續調查。Worker 中斷時，新程序能從 **Checkpoint（執行檢查點）** 讀回模型與工具狀態，接續原本的任務。網頁使用相同網址查詢 Activity 與結果。

## 對照原始提案

原始《IssueLens》提案第 6–7 頁將 Redis + Celery 放在 Job Queue。Redis 接收待處理的任務，Celery Worker 在背景執行分析並處理重試。第 14 頁的 M3 完成標準是任務中斷可恢復、資料可保存。

本機版用 PostgreSQL 佇列與獨立 Worker 實現這個流程。領取任務時，狀態與初始 Checkpoint 在同一筆交易提交。兩項 M3 功能標準均已驗證。真實分析在 API 重啟後能讀回原本的結果。使用真實 Worker 與 PostgreSQL 的整合測試也確認，替換 Worker 後可接續相同的 `job_id` 並查回重試與 Trace。整合測試的模型和 GitHub 回應使用模擬資料。[真實分析保存](#第一步的真實分析保存驗收) · [Worker 重啟驗證](../evidence/m3/verification/trace.json)

第 11 頁另規劃跨任務的 Repository Memory，用來保存並更新 repo 規則、標籤與 Issue 範本。目前工具快取以單筆分析為範圍。跨任務的保存與更新仍待實作。

## 保存分析、分離 Worker 與控制失敗恢復

持久化（Persistence）讓資料在程序結束後仍可讀取。第一步將任務與結果存入 PostgreSQL，驗證重新開啟網頁時能讀回既有紀錄。

第二步把執行中的 Agent 移到背景 Worker。這樣部署或重啟 API 時，只會暫時中斷 HTTP 連線，Agent 的記憶體和正在等待的模型／工具請求仍留在 Worker。PostgreSQL 同時保存快照和待執行的佇列，本機啟動只需要現有資料庫。

第三步把 Agent 的執行狀態也提交到 PostgreSQL。換一個 Worker 後，可以沿用已完成的模型回應、工具結果和來源編號，並從原任務的剩餘預算繼續。網頁照常讀取既有的 `JobSnapshot`。

第四步處理外部服務的暫時性失敗。**有界重試**允許單次失敗的模型或工具呼叫補送一次，讓短暫逾時有機會恢復，同時由原任務的次數與時間預算限制成本。

第五步加入 **Trace（執行紀錄）**。已有重試與跨程序接續後，同一次分析可能包含成功、失敗、補送與中斷。用任務 ID 查詢這些嘗試，可以定位耗時或停止原因，也能核對補送是否使用了原本的預算。

## 實作與資料流

新增的 Psycopg 是 PostgreSQL 驅動程式，只負責資料庫連線與 SQL；Agent 與保存流程仍由我們實作。依賴由 uv 與鎖定檔管理。

`issuelens_analyses` 沿用 `job_id` 主鍵、JSONB 快照與更新時間。JSONB 是 PostgreSQL 的 JSON 儲存型別。`JobSnapshot` 格式沿用既有欄位，包含狀態、建立時間、結果、來源、用量、拒絕答案稽核、限制與事件。佇列使用快照的 `queued` 狀態，取消請求存在同一列的獨立布林欄位 `cancel_requested`。索引只包含排隊與執行中的紀錄。

同一列的 `checkpoint` 是 Worker 使用的私有 JSON 文字欄位，保留原本的重播項目順序與 JSON 欄位順序，供本機 Token 估算與下一輪請求使用。檢查點包含模型回應的重播項目與 `call_id`、Context Builder 狀態、工具快取與來源、答案修正回饋，以及已用的模型、工具和時間預算。`trace` 是獨立的 JSONB 欄位，與對應快照及檢查點一次提交。結果 API 讀取 `snapshot`，Trace API 讀取嘗試紀錄與任務狀態。

| 時點 | 動作 |
| --- | --- |
| 建立任務 | API 提交 `queued` 快照後回傳 202。最多 30 筆排隊或執行中的任務。 |
| 領取任務 | Worker 優先接續已執行的任務。領取排隊任務時，在同一個交易提交 `running` 和第一份檢查點。最多同時執行兩筆。 |
| 更新進度 | Worker 在外部呼叫前保存嘗試計數，收到模型回應或工具結果後更新檢查點。檢查點、對應的 Activity 與 Trace 一起提交。API 定期讀取快照，用 SSE（伺服器推送事件）傳送網頁尚未收到的事件。 |
| 完成與重連 | Worker 提交最終結果與 Trace 時，一起清除私有檢查點。若完成結果已存入檢查點，新 Worker 可直接發布它。API 從最後收到的事件編號接續，以 `done` 送出完整快照。 |
| 取消 | API 直接取消排隊中的任務。若任務已在執行，API 回傳 202，Worker 讀到取消請求後停止分析並保存當下結果。若分析先完成，網頁會收到該結果。 |

API 使用最多四條連線的連線池（connection pool），Worker 使用一條非同步資料庫連線。PostgreSQL session advisory lock 是由連線持有的協作鎖。同一個資料庫只允許一個 Worker 持有此鎖，替換程序要等舊連線釋放後才能接續。API 啟動和關閉只管理自己的連線。

領取與取消時，列鎖讓同一筆任務的狀態轉換依序完成。查詢使用參數，進度寫入只更新仍為 `running` 的列。[PostgreSQL 14 列鎖與協作鎖](https://www.postgresql.org/docs/14/explicit-locking.html)

### 中斷與失敗如何呈現

API 重啟期間，網頁會重試連線。Worker 停止後，已提交的模型或工具回合可直接重用。若首次呼叫在保存回應前中斷，那次嘗試仍計入預算。模型會在額度內從原證據開始下一次請求，等待中的唯讀工具則可用原 `call_id` 接續讀取。若中斷的是已開始的補送，該呼叫的重試機會視為用完。報表的 Token 總量累計已取得的模型回應。

執行時間從第一次領取開始計算，包含停機時間。超時後以已有資料收尾。已收到的取消請求優先處理。舊版只有公開快照的 `running` 任務，或檢查點與現行設定不相容的任務，會保留已保存資料並標為 `cancelled`。`queued` 任務可照常領取。

資料庫讀取故障回傳 503，找不到紀錄時回傳 404。Worker 失去連線時會暫停並重新連線；其他儲存錯誤，例如存檔內容已無法驗證，會停止 Worker 並回報。API 只會發布已提交的結果。資料庫恢復後，API 自動重連，Worker 在程序內重新取得鎖，依上面的方式處理中斷與排隊紀錄。

### 資料庫斷線與恢復

PostgreSQL 重啟或網路中斷時，既有連線會中斷。先前 API 只有一條連線且不會重連，資料庫恢復後仍持續回傳 503，直到手動重啟 API；Worker 則直接退出。公開試用前，短暫的資料庫中斷應能自行恢復。

- **API 用連線池重連。** 連線池在每次取用前檢查連線，丟棄已斷開的連線。一次重連嘗試最多持續三秒，之後的請求會發起新的嘗試，所以資料庫恢復後的下一次請求就能成功，不必等長時間的退避。連線池最多兩條連線：重啟後閒置的連線都已失效，連線池在兩次失敗的檢查之間會等約 0 秒和 1 秒，兩條連線才能在三秒內換到新連線。停機期間，每次資料庫操作最多等三秒後回傳 503；登入後的路由會先查工作階段再查分析，最多約六秒。啟動時仍要求資料庫可連線。資料表結構只在啟動時確認一次，避免和寫入競爭鎖，所以資料庫被重建時需要重啟 API。
- **Worker 只在失去連線時重連。** Worker 的獨佔權是綁在連線上的 advisory lock，連線中斷時鎖已釋放，此時繼續執行可能與另一個 Worker 同時處理同一筆任務。Worker 因此先暫停執行中的分析並關閉連線，再以 1、2、4、5 秒的間隔重新連線並取得鎖，接著沿用啟動時的恢復流程，從檢查點接續分析。重連後很快又斷線時，間隔會接著加長；持續運作一分鐘以上才重新從 1 秒開始。重新取得鎖之前不做任何工作，安全性和重啟程序相同，但不需要外部的重啟機制。重連時略過資料表確認，避免和 API 的寫入競爭鎖。
- **其他儲存錯誤會停止 Worker。** 連線仍正常時的錯誤，例如存檔內容已無法驗證，或 PostgreSQL 拒絕某個值，重連後會再次發生。這類錯誤會停止 Worker 並顯示錯誤，避免反覆暫停其他分析、消耗它們的預算。啟動時連不上資料庫或設定錯誤也會直接結束，停機期間的關閉若無法保存結果，程序以錯誤狀態結束。
- **log 不含連線網址。** 連線池會記錄每次連線失敗。libpq 的錯誤訊息可能重複網址內容，包括密碼，所以這些 log 只保留例外型別。啟動時也先解析網址，格式錯誤直接回傳已清理的錯誤。
- **偵測無聲的斷線。** 用戶端設定了 TCP keepalive 與 `tcp_user_timeout`，網路路徑消失、卻沒收到關閉訊號的連線，會在數十秒內判定失效。伺服器端也設定了 keepalive，讓 PostgreSQL 結束失效的連線並釋放它持有的 Worker 鎖；否則重連的 Worker 可能要等作業系統的上限，長達數小時。一般帳號可在連線時設定這些值。這項沒有在本機模擬驗證。

```bash
ISSUELENS_TEST_DATABASE_URL=postgresql://issuelens@127.0.0.1:5432/issuelens_test \
  uv run --locked python -W error::RuntimeWarning -m unittest discover -s tests -p 'test_persistence.py' -v \
  -k test_malformed_database_url -k test_unreachable_database -k test_pool_log_filter -k WorkerRecoveryTests \
  -k test_api_store_recovers -k test_api_recovers_promptly -k test_api_pool_full -k test_a_store_cannot \
  -k test_worker_store_fails -k test_worker_reconnect -k test_worker_stops_on
```

十五項檢查應通過，約需 25 秒。七項離線檢查確認：格式錯誤的網址立即失敗且不寫 log；無法連線時，啟動在數秒內失敗，log 只有例外型別；Worker 只在失去連線時重連，快速重複的斷線會繼續加長間隔，鎖仍被占用時會再試，其他儲存錯誤與關閉時的儲存失敗會停止 Worker。整合檢查確認：伺服器切斷連線後，下一次讀取即成功；連線池滿載後切斷，第一個請求仍在三秒內成功；停機 15 秒後恢復，三秒內讀取成功；Worker 在分析執行中失去連線，同一個程序重新取得鎖，從檢查點完成同一筆分析；Worker 重連時，即使有寫入占用資料表，也不必等鎖；存檔內容無法驗證時，Worker 停止而不重連。整合檢查會切斷測試資料庫的所有連線，並暫時禁止新連線，請只用專用的 `_test` 資料庫。若中途強制停止測試，可連到 `postgres` 資料庫執行 `ALTER DATABASE issuelens_test ALLOW_CONNECTIONS true` 恢復。

練習時用 `scripts/dev.py` 啟動後，執行 `pg_ctl -D .local/postgres stop -m fast`。`curl http://127.0.0.1:8000/api/v1/health` 仍可回應，查詢分析則回傳 503，啟動器終端會顯示 `Reconnecting to PostgreSQL`。依[本機設定](#本機設定與啟動)重新啟動資料庫後，原分析網址會恢復，Worker 在五秒內印出 `IssueLens Worker is ready.`。

Worker 中斷時，尚未保存的模型或工具嘗試仍計入預算。發布結果遇到儲存失敗時，同一輪其他已結束、尚未發布的分析可能從上一個檢查點重新執行。一筆存檔內容無法驗證的紀錄會讓 Worker 停止，排隊中的分析在處理該筆紀錄前不會執行。程式設定的連線參數會覆蓋 `DATABASE_URL` 中同名的參數。

面試可比較「讓程序停止再由外部重啟」與「在程序內重連」。兩者的安全前提相同：鎖隨連線消失後，重新取得鎖之前不能做任何工作。程序內重連不依賴外部的重啟機制，手動啟動或部署平台都能恢復，代價是 Worker 要自己處理暫停與重開。重連的等待上限也是取捨：上限越長，停機期間的嘗試越少，資料庫恢復後卻要等越久。這裡一次失敗的連線成本很低，所以 API 與 Worker 都採用短上限。

一小時的快取期限適用於記憶體模式。PostgreSQL 模式的 30 筆上限只計算活動任務，歷史快照持續保留。

## 有界重試

- 逾時、可重送的連線錯誤、暫時性 HTTP `408`、`500`、`502`、`503`、`504`，以及可辨識的暫時限流可觸發補送。憑證、權限、帳務／用量額度和請求內容錯誤會直接處理。GitHub 的 `403` 需要有明確的限流訊號。[OpenAI 錯誤碼](https://developers.openai.com/api/docs/guides/error-codes) · [GitHub 限流規則](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#exceeding-the-rate-limit)
- 補送至少等一秒，並遵守服務的 `Retry-After` 和 GitHub 提供的限流重設時間。GitHub 已知限流但沒有可用的等待提示時，等候一分鐘。若要求的等待超過剩餘任務時間，保留失敗原因並用已取得的證據收尾。
- 每次補送占用原本的模型或工具次數。讀候選本文前也會先保存候選讀取次數。預設上限仍是 8 次模型請求、15 次工具呼叫、5 次候選本文讀取和 90 秒。用到最後一格模型額度時，沿用原規則收尾，工具關閉。
- Checkpoint 保存補送原因、可重送時間和當前嘗試。新 Worker 接續同一個 `job_id`，並依已用的次數和等待時間判斷下一步。GitHub 的等待限制也會套用到同一任務的後續請求。工具補送成功時，模型仍只收到原 `call_id` 的一份結果。

若模型用完重試機會，已有來源的分析會保存為部分結果。工具用完重試機會時，該呼叫會回傳失敗狀態，Agent 可依剩餘預算用已有證據收尾。範本工具回傳部分結果時，會保留讀到的檔案與涵蓋範圍限制。重試以模型請求和失敗的工具呼叫為邊界。

可以先執行下面的模擬檢查，觀察 Activity 中的 `Retrying`、重試成功與額度耗盡訊息。再用 [Worker 重啟驗收](#怎麼驗收-worker-重啟) 的專用資料庫指令，檢查替換程序是否在已保存的時間之後才補送。

```bash
uv run --locked python -W error::RuntimeWarning -m unittest discover -s tests -p 'test_retry.py' -v
```

## Trace

啟動 API 後，將分析頁網址中 `analysis=` 後面的值填入 `JOB_ID`，用同一個 ID 查詢分析執行中或完成後的 Trace。

```bash
JOB_ID=replace-with-job-id
curl -fsS "http://127.0.0.1:8000/api/v1/analyses/${JOB_ID}/trace" |
  uv run --locked python -m json.tool
```

- 回應包含 `job_id`、任務 `status`、整體 `stop_reason` 與按 `id` 排序的 `attempts`。每筆嘗試有種類、名稱、該類累計次數、開始時間、毫秒耗時與結果。原因欄位使用服務端定義的分類和訊息。
- 原呼叫暫時失敗時，`retry_scheduled_for` 保存最早可補送的時間。真正開始補送時才新增一筆，`is_retry` 為 `true`，`retry_of` 指回失敗嘗試的 `id`。耗盡重試或工具額度時，可在失敗嘗試的 `stop_reason` 看到原因。
- `duration_ms` 用單調時鐘從開始計入嘗試到收到並判定結果，包含呼叫前的 Checkpoint 保存。重試等待發生在兩筆嘗試之間。若接手時只有開始紀錄，該筆會標為 `interrupted`，耗時為 `null`。
- 舊任務可查到原狀態，沒有保存過的嘗試會顯示空清單。找不到任務時回傳 404。記憶體模式可在同一個 API 程序內查詢，跨程序保存由 PostgreSQL 提供。

可以先跑 [Worker 重啟驗收](#怎麼驗收-worker-重啟) 的命令，在輸出確認兩個程序測試通過。練習時先查詢一筆分析，按 `kind` 分別找出最慢的模型與工具嘗試。若有補送，再用 `retry_of` 找到原失敗及其排定時間。既有分析的查詢只讀取資料庫。

面試可比較把有上限的紀錄和 Checkpoint 同列提交，與為每筆嘗試建立獨立資料列。前者可共用既有寫入並用一次讀取查完整任務，代價是每次寫入都要更新整份 Trace。若日後要診斷效能瓶頸，可再拆量 Checkpoint 與外部請求耗時。
