# M3: Reliability and persistence

With PostgreSQL configured, a separate Worker runs analyses and stores them as snapshots, so an API restart does not stop them. If the Worker is interrupted, a replacement resumes the job from its last **checkpoint** within the original budgets. M3 is complete: recovering interrupted jobs and persisting data are both verified.

## Use

<a id="setup"></a>
### Setup

This machine has a PostgreSQL 14.15 cluster in `.local/postgres` (ignored by git) on `127.0.0.1:5432`, with the role `issuelens`, local trust authentication, and the `issuelens` and `issuelens_test` databases for the app and tests. It does not start at boot. Add this to the root `.env`:

```dotenv
DATABASE_URL=postgresql://issuelens@127.0.0.1:5432/issuelens
```

A blank `DATABASE_URL` keeps analyses in memory, and an unreachable configured database fails startup. Start the app as usual:

```bash
uv sync --locked
uv run --locked python scripts/dev.py
```

The launcher starts the API, the Worker, and the front end. It restarts an exited API and keeps the Worker, waiting 2 seconds and doubling up to 30 after repeated failures. A Worker exit, from a configuration error, a storage error other than a lost connection, or a stop request, stops everything. After `Ctrl+C`, jobs and checkpoints stay in PostgreSQL.

To run the API and the Worker on their own, run these from the project root and `npm run dev` from `frontend/`:

```bash
uv run --locked python -m backend.app.worker
uv run --locked uvicorn --factory backend.app.main:create_app --host 127.0.0.1 --port 8000 --timeout-graceful-shutdown 2
```

After a reboot, start the database from the project root:

```bash
pg_ctl -D .local/postgres -l .local/postgres.log \
  -o "-h 127.0.0.1 -p 5432 -k $PWD/.local/postgres-socket" start
```

Check its status or stop it:

```bash
pg_ctl -D .local/postgres status
pg_ctl -D .local/postgres stop -m fast
```

In `curl http://127.0.0.1:8000/api/v1/health`, `storage` should be `postgresql`.

**New environment.** Create the cluster with the PostgreSQL tools installed and the port free:

```bash
mkdir -p .local/postgres-socket
initdb -D .local/postgres -U issuelens -A trust --encoding=UTF8 --locale=C
pg_ctl -D .local/postgres -l .local/postgres.log \
  -o "-h 127.0.0.1 -p 5432 -k $PWD/.local/postgres-socket" start
createdb -h 127.0.0.1 -p 5432 -U issuelens issuelens
createdb -h 127.0.0.1 -p 5432 -U issuelens issuelens_test
```

An existing PostgreSQL needs only a dedicated database. Never use trust authentication in a public deployment.

## How it works

PostgreSQL replaces the proposal's Redis and Celery queue and stores the snapshots.

**Records.** Each analysis is one `issuelens_analyses` row with the public `JobSnapshot` as JSONB, a `cancel_requested` flag, a private `checkpoint`, a `trace`, and `incompatible_record`. The checkpoint holds the model replay items and `call_id` values, Context Builder state, tool cache, sources, repair feedback, and budgets used.

**Flow.** The API commits a `queued` snapshot and returns 202, with at most 30 active jobs. The Worker runs at most two jobs, started ones first. A claim commits `running` with the first checkpoint, each model or tool result commits the checkpoint, Activity, and Trace together, and the final commit clears the checkpoint. The API streams new events over SSE from the client's last event ID. A running job stops when the Worker reads its cancel request.

**Locks.** The Worker holds a PostgreSQL session advisory lock tied to its connection, so one Worker runs per database, and a replacement starts only after the old connection releases it. Row locks order claim and cancel.

**Interruptions.** A replacement reuses committed turns, and a pending read-only tool resumes with its original `call_id`. An interrupted call still counts against the budget, and runtime includes downtime. A `running` job without a compatible checkpoint keeps its data and becomes `cancelled`.

**Database reconnects.** The API pool checks connections before use and caps a reconnect attempt at three seconds, so the first request after recovery succeeds. The Worker's lock goes with its connection, so on a lost connection it suspends its analyses, reconnects with waits of 1 to 5 seconds, and resumes only once it holds the lock again. Other storage errors would recur, so they stop the Worker. Pool logs keep only the exception type, since libpq messages can contain the password. TCP keepalives catch silently dropped connections.

**Unreadable records.** If a snapshot or Trace no longer validates, the Worker marks the record `failed` with the stop reason `record_incompatible`, keeps its readable fields and owner, saves the original in `incompatible_record`, and moves on.

**Bounded retry.** Timeouts, connection errors, HTTP `408`, `500`, `502`, `503`, `504`, and temporary rate limits get one retry per failed call, which uses one of the original 8 model requests or 15 tool calls. Credential, permission, quota, and request errors fail at once. The wait honors `Retry-After` and GitHub's reset time; a wait past the job's 90-second deadline ends the run with its evidence. The checkpoint keeps retry state for a replacement Worker. A model out of retries leaves a `partial` result if sources exist.

**Trace.** It has the job `status` and `stop_reason`, and each attempt's kind, name, start time, `duration_ms`, and outcome. A retry's `retry_of` points to the failed attempt, and an attempt cut off by a Worker stop is `interrupted`. In memory mode, it lives only in the API process.

## Limits

- Cross-job Repository Memory is not implemented.
- Unsaved attempts still count against the budget after a Worker stop.
- A storage failure while publishing can rerun other unpublished results from their checkpoints.
- GitHub text with a NUL character is refused by JSONB and stops the Worker.
- In an outage, each database call waits up to three seconds before 503, about six on signed-in routes. A recreated database needs an API restart.
- Silent disconnect detection was not verified locally.
- Connection parameters set in code override the same names in `DATABASE_URL`.
- The API returns 503 for an unreadable record until the Worker claims it, and its old Activity stays only in `incompatible_record`.
- Draft edits live in page memory, so a refresh restores the original draft.

## Tradeoffs and exercises

- **PostgreSQL as the queue:** one service and one transaction, but each update rewrites the JSONB and subscriptions poll.
- **In-process reconnect versus external restart:** neither works without the lock; reconnecting needs no restarter but must suspend itself.
- **Isolating a bad record:** the dead-letter pattern keeps the queue moving but must keep the original.
- **Trace in the checkpoint row:** one write and one query, but each write rewrites the Trace.

**Exercise.** Run the API and the Worker separately, as in [Setup](#setup). When Activity shows `Finished get_issue`, press `Ctrl+C` in the Worker terminal and start it again. The page should show `Resumed from a checkpoint`. This calls the real model and GitHub.
