# M1：本機 Issue 調查應用程式

M1 已完成從 GitHub Issue URL 到網頁分析的基本流程。本文件統一說明啟動、架構、操作與 M1 驗證；目前程式另包含 [M2 調查功能](m2.md)及 [M3 PostgreSQL 保存](m3.md)。

## 目標與範圍

MVP（Minimum Viable Product，最小可行產品）是能走完主要使用流程的最小版本。M1 把模型呼叫與工具往返接成可操作的本機產品：貼上公開 Issue 網址，由 Agent 選擇工具、取得資料，再顯示附來源的分析與英文回覆草稿。

核心 Agent 循環由我們自行實作，使用一般 OpenAI Python SDK，不依賴 Agent 框架。

## 環境與啟動

需要 Python 3.13 以上、uv、Node.js 20.9 以上與 npm。Python 依賴由 `uv.lock` 固定；前端依賴由 `frontend/package-lock.json` 固定。

在專案根目錄執行：

```bash
uv sync --locked
```

第一次使用、且尚未建立 `.env` 時，才複製範例；已有設定就保留原檔：

```bash
cp .env.example .env
```

在本機填入 `OPENAI_API_KEY`。現行應用程式使用下列模型設定，完整預算說明見 [M2 設定](m2.md#settings)：

```dotenv
OPENAI_API_KEY=your-api-key
OPENAI_MODEL=gpt-5.6
OPENAI_REASONING_EFFORT=medium
GITHUB_TOKEN=
```

`GITHUB_TOKEN` 可留空，公開 Issue 可匿名讀取，但 GitHub API 額度較低；有設定時後端才附上憑證。這不代表目前版本已提供私人 Repository 的完整支援。Key 只由後端讀取，不能放進前端或提交到版本控制。

啟動應用程式：

```bash
uv run --locked python scripts/dev.py
```

啟動器會同時啟動兩個服務；第一次缺少前端依賴時，先執行 `npm ci`。

| 服務 | 位址 | 用途 |
| --- | --- | --- |
| Next.js 前端 | <http://127.0.0.1:3000> | 輸入 Issue、查看結果與編輯草稿。 |
| FastAPI 後端 | <http://127.0.0.1:8000/docs> | 執行 Agent、GitHub 工具及任務 API。 |

在啟動器終端按 `Ctrl+C`，會一起停止它啟動的程序。修改 Python 或 `.env` 後需要重新啟動。記憶體模式會清除任務。資料庫模式的啟動與 API 獨立重啟見 [M3](m3.md#本機設定與啟動)。

若連接埠已被占用，先確認是哪個程序：

```bash
lsof -nP -iTCP:3000 -sTCP:LISTEN
lsof -nP -iTCP:8000 -sTCP:LISTEN
```

輸出的 PID 是程序編號。優先回到原啟動終端按 `Ctrl+C`；若該終端已找不到，確認程序屬於本專案後，再用 `kill PID` 正常停止，將 `PID` 換成實際數字。

## 操作與成功標準

1. 開啟前端，貼上公開 GitHub Issue URL，或點選 `Try an example`。
2. 按下 `Analyze issue` 才開始真實 GitHub 與模型 API 請求；只填入網址不會呼叫模型。
3. Activity 應顯示實際模型請求、工具執行與停止原因。它是操作紀錄，不展示模型內部思考。
4. Analysis 顯示摘要、已知事實、缺少資訊與英文草稿；無合格最終答案時，保留已取得來源與未完成原因。
5. 打開 `S1` 等來源標記，核對原始 GitHub 頁面；Sources 顯示本次取得的有界摘錄。
6. 重新整理應接回仍存在的同一筆任務，不應建立第二筆分析。

目前版本另有 Similar issues、Labels、Templates，以及草稿編輯／還原功能，操作見 [M2 功能](m2.md#features)。Sources 保留的摘錄可能被截短，或因輸入選材未送給模型；應一起看 Activity 與限制。

## 架構與資料流

Frontend（前端）是 Next.js／TypeScript 網頁；Backend（後端）是 FastAPI 伺服器。前端透過 Next.js 的同源 API 代理連到後端，瀏覽器不用取得 API Key。

Agent loop（智能體循環）依序執行：模型決定下一個工具 → Python 驗證並執行 → 結果回傳模型 → 繼續調查或產生答案。模型選擇動作，程式掌握執行權與資源上限。

M1 最初提供三個唯讀工具；現行 M2 共七個，完整清單見 [工具表](m2.md#tools)。

| M1 工具 | 讀取範圍 |
| --- | --- |
| `get_issue` | 目標 Issue 的本文、狀態、既有標籤等資料。 |
| `get_issue_comments` | 目標留言，每頁最多 10 則、最多 5 頁。 |
| `get_repo_readme` | 同一 Repository 預設分支的 README。 |

工具綁定使用者提交的目標，不能讓模型任意切換 Repository 或提供 HTTP 位址。外部內容只作為證據，不執行其中指令。

Structured output（結構化輸出）要求模型回傳指定 JSON，Pydantic 定義欄位，後端再檢查來源與業務規則。來源 ID 只在成功取得資料後建立。ID 正確只能證明來源存在，仍需核對內容是否支持結論。

## 任務 API 與保存範圍

分析需要多次請求，因此建立任務先回傳 HTTP 202 與 `job_id`，再由網頁追蹤進度。

| API | 用途 |
| --- | --- |
| `POST /api/v1/analyses` | 建立分析任務。 |
| `GET /api/v1/analyses/{job_id}` | 取得目前狀態與結果。 |
| `GET /api/v1/analyses/{job_id}/events` | 透過 SSE 接收事件。 |
| `DELETE /api/v1/analyses/{job_id}` | 取消任務。 |

SSE（Server-Sent Events）是伺服器持續推送事件給網頁的連線。網址中的 `analysis` 參數保存任務編號，重連使用事件編號避免重複顯示。

M1 原先由 `asyncio` 與程序內記憶體管理任務，預設同時執行 2 筆、最多保存 30 筆。已結束任務在建立滿 1 小時後可被清除；容量不足時可能更早移除舊結果。記憶體模式下，後端重啟會失去任務，多 Worker 也不共享記憶體。

以上是 M1 的程序內任務設計。現行 M3 的 PostgreSQL 模式已能保存快照、排隊並由獨立 Worker 執行。`DATABASE_URL` 留白時使用上述記憶體模式。[M3 可靠性與持久化](m3.md)

## 循環、預算與停止

預設每案最多 8 次模型請求、15 次邏輯工具、90 秒；單次輸入的本機估算上限為 12,000 Token。接近上限時嘗試用現有證據收尾，不能繼續增加工具來突破限制。

Token 是模型處理文字的單位。本機估算與 API 實際回報可能不同；單次輸入上限也不同於整次任務累加的輸入與輸出用量。

長內容、工具失敗、省略或預算停止會保留限制，任務可能標為 `partial`。`completed` 表示執行取得合格輸出且沒有已記錄限制，不代表語意已經人工驗收。現行 Context Builder 與答案修正詳見 [M2](m2.md#context-builder)。

## 檢查與 M1 驗證紀錄

離線測試使用模擬 GitHub／模型回應，不需要 Key，也不衡量真實模型品質：

```bash
uv run --locked python -W error::RuntimeWarning -m unittest discover -s tests -q
pyright --pythonpath .venv/bin/python backend evaluation scripts
npm --prefix frontend run typecheck
npm --prefix frontend run build
```

Pyright 命令使用環境中已有的型別檢查器；依賴一律由 uv 管理。上述命令檢查的是目前程式，不會重建 M1 當時版本。

M1 當時完成 25 項離線測試、Pyright、TypeScript 與 Next.js 正式建置。另在瀏覽器對 `pallets/flask#6146` 執行一次真實分析：3 次模型請求、2 次工具、5 個來源，約 6.58 秒；模型讀了 Issue 與留言，沒有讀 README。

當時另核對重新整理接回任務、來源、複製與窄螢幕版面。[M1 驗證紀錄](../evidence/m1/verification.json)與[實際畫面](../evidence/m1/live-analysis.jpg)保留原始觀察。這是一筆功能連線檢查，不是品質或效能基準；M2 的後續測試數與驗收不回填到這筆紀錄。 其他證據由[總索引](../evidence/README.md)查找。

## 練習與設計取捨

練習：完成一筆分析後，記下 Activity 實際執行的工具；選一項已知事實，開啟來源檢查是否支持它。再於同一任務重新整理，觀察任務編號與結果是否保留。

自行實作循環的好處是資料流、工具執行權與停止條件清楚；代價是需要自己處理協定、錯誤及驗證。先用程序內任務能快速走通產品，代價是無法重啟恢復或跨伺服器共享。

面試可討論：自主選工具提高適應性，也增加成本與不可預測性，因此要同時設計預算、可觀察紀錄與來源核對。結果保存與任務恢復有不同需求，不能只因使用資料庫就宣稱可以接續執行。後續已實作 [M2 調查功能](m2.md)與 [M3 第一小步的結果保存](m3.md)。
