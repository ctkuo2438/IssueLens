# M1: Local issue investigation app

M1 is complete. It delivers the basic flow from a GitHub issue URL to an analysis in the web page. This guide covers setup, usage, architecture, and the M1 verification. The current code also includes the [M2 investigation features](m2.md) and [M3 PostgreSQL persistence](m3.md).

## Goal and scope

An MVP (minimum viable product) is the smallest version that can complete the main user flow. M1 connects model calls and tool round trips into a working local product: you paste a public issue URL, the agent chooses tools and fetches data, and the page shows a cited analysis and a draft reply in English.

We implement the core agent loop ourselves on the ordinary OpenAI Python SDK, without an agent framework.

## Setup and start

You need Python 3.13 or later, uv, Node.js 20.9 or later, and npm. `uv.lock` pins the Python dependencies, and `frontend/package-lock.json` pins the frontend dependencies.

From the repository root, run:

```bash
uv sync --locked
```

Copy the example only on first use, when `.env` does not exist yet. If you already have settings, keep your file:

```bash
cp .env.example .env
```

Set `OPENAI_API_KEY` locally. The current app uses the model settings below. See [M2 settings](m2.md#settings) for the full budget description.

```dotenv
OPENAI_API_KEY=your-api-key
OPENAI_MODEL=gpt-5.6
OPENAI_REASONING_EFFORT=medium
GITHUB_TOKEN=
```

`GITHUB_TOKEN` can stay blank. Public issues can be read anonymously, but with a lower GitHub API limit. The backend sends the credential only when it is set. Private repositories are not supported: since [M4](m4.md#public-repos-only), a run with a token refuses any repository that GitHub does not report as public. Only the backend reads the keys. Do not put them in the frontend or commit them to version control.

Start the app:

```bash
uv run --locked python scripts/dev.py
```

The launcher starts two services. On the first run, when the frontend dependencies are missing, it runs `npm ci` first.

| Service | Address | Purpose |
| --- | --- | --- |
| Next.js frontend | <http://127.0.0.1:3000> | Enter an issue, view results, and edit drafts. |
| FastAPI backend | <http://127.0.0.1:8000/docs> | Runs the agent, the GitHub tools, and the job API. |

Press `Ctrl+C` in the launcher terminal to stop every process it started. Restart after you change Python code or `.env`. In memory mode, a restart clears the jobs. For starting in database mode and restarting the API on its own, see [M3](m3.md#setup).

### If a port is already in use

First find out which process holds it:

```bash
lsof -nP -iTCP:3000 -sTCP:LISTEN
lsof -nP -iTCP:8000 -sTCP:LISTEN
```

The PID in the output is the process ID. Prefer going back to the original launcher terminal and pressing `Ctrl+C`. If you cannot find that terminal, confirm that the process belongs to this project, then stop it normally with `kill PID`, replacing `PID` with the actual number.

## Use the app

Follow these steps and check the expected result at each one:

1. Open the frontend and paste a public GitHub issue URL, or select `Try an example`.
2. Select `Analyze issue`. Only then do the real GitHub and model API requests start. Filling in a URL alone does not call the model.
3. Activity should show the actual model requests, tool runs, and the stop reason. It is an operation log and does not show the model's internal reasoning.
4. Analysis shows the summary, known facts, missing information, and an English draft. When there is no valid final answer, it keeps the sources already fetched and the reason the run did not finish.
5. Open a source marker such as `S1` to check the original GitHub page. Sources shows the bounded excerpts fetched in this run.
6. Refresh the page. It should reconnect to the same job if that job still exists, and should not create a second analysis.

The current version also has Similar issues, Labels, Templates, and draft editing and restore. See [M2 features](m2.md#features) for how to use them. Excerpts kept in Sources may be truncated, or may not have been sent to the model because of input selection, so read them together with Activity and the limitations.

## How it works

### Architecture and data flow

The frontend is a Next.js and TypeScript web page. The backend is a FastAPI server. The frontend reaches the backend through a same-origin API proxy in Next.js, so the browser never needs the API key.

The agent loop runs these steps in order:

1. The model chooses the next tool.
2. Python validates the call and runs it.
3. The result goes back to the model.
4. The model continues investigating or produces an answer.

The model chooses the actions. The program keeps control of execution and of the resource limits.

M1 started with three read-only tools. The current M2 has seven. See the [tool table](m2.md#tools) for the full list.

| M1 tool | What it reads |
| --- | --- |
| `get_issue` | The target issue's body, state, existing labels, and similar data. |
| `get_issue_comments` | Comments on the target, up to 10 per page and up to 5 pages. |
| `get_repo_readme` | The README on the default branch of the same repository. |

Tools are bound to the target the user submitted. The model cannot switch to another repository or supply an HTTP address. External content is used only as evidence, and instructions in it are never executed.

Structured output requires the model to return a specified JSON shape. Pydantic defines the fields, and the backend then checks the sources and business rules. A source ID is created only after data is fetched successfully. A valid ID proves only that the source exists. You still need to check whether its content supports the conclusion.

### Job API and what is kept

An analysis takes several requests, so creating a job first returns HTTP 202 and a `job_id`. The page then tracks the progress.

| API | Purpose |
| --- | --- |
| `POST /api/v1/analyses` | Create an analysis job. |
| `GET /api/v1/analyses/{job_id}` | Get the current status and result. |
| `GET /api/v1/analyses/{job_id}/events` | Receive events over SSE. |
| `DELETE /api/v1/analyses/{job_id}` | Cancel the job. |

SSE (Server-Sent Events) is a connection over which the server keeps pushing events to the page. The `analysis` parameter in the page URL keeps the job ID, and reconnects use the event ID to avoid showing an event twice.

M1 originally managed jobs with `asyncio` and in-process memory:

- By default it ran 2 jobs at a time and kept at most 30.
- A finished job can be cleared once 1 hour has passed since it was created. When capacity runs short, old results may be removed sooner.
- In memory mode, a backend restart loses the jobs, and multiple worker processes do not share memory.

That was the M1 in-process job design. The current M3 PostgreSQL mode saves snapshots, queues jobs, and runs them in an independent Worker. A blank `DATABASE_URL` selects the memory mode above. See [M3: Reliability and persistence](m3.md).

### Loop, budgets, and stopping

By default, each case is limited to 8 model requests, 15 logical tool calls, and 90 seconds. The local estimate of a single model input is capped at 24,000 tokens (12,000 during the M2 evaluation). Near a limit, the agent tries to finish with the evidence it has. It cannot add more tool calls to get past the limit.

A token is the unit of text a model processes. The local estimate may differ from what the API reports. The single-input limit is also different from the total input and output usage summed over the whole job.

Long content, tool failures, omissions, or a budget stop are recorded as limitations, and the job may be marked `partial`. `completed` means the run produced valid output with no recorded limitation. It does not mean a human has reviewed the meaning. See [M2](m2.md#context-builder) for the current Context Builder and answer repair.

## Checks and the M1 verification record

The offline tests use simulated GitHub and model responses. They need no keys and do not measure real model quality:

```bash
uv run --locked python -W error::RuntimeWarning -m unittest discover -s tests -q
pyright --pythonpath .venv/bin/python backend evaluation scripts
npm --prefix frontend run typecheck
npm --prefix frontend run build
```

The Pyright command uses the type checker already present in your environment. All dependencies are managed by uv. These commands check the current code. They do not rebuild the M1 version.

At the time, M1 passed 25 offline tests, Pyright, TypeScript, and the Next.js production build. One real analysis of `pallets/flask#6146` also ran in the browser: 3 model requests, 2 tool calls, 5 sources, and about 6.58 seconds. The model read the issue and its comments, not the README.

The same check also confirmed that refreshing reconnects to the job, and checked the sources, copying, and the narrow-screen layout. The [M1 verification record](../evidence/m1/verification.json) and the [screenshot](../evidence/m1/live-analysis.jpg) keep the original observations. This was one functional connectivity check, not a quality or performance benchmark. Later M2 test counts and acceptance results are not backfilled into this record. Find other evidence through the [evidence index](../evidence/README.md).

## Tradeoffs (interview discussion)

Writing the loop ourselves keeps the data flow, control of tool execution, and stop conditions clear. The cost is that we handle the protocol, errors, and validation ourselves. In-process jobs let the product work end to end quickly. The cost is that jobs cannot survive a restart or be shared across servers.

Letting the model choose tools makes it more adaptable, but also adds cost and unpredictability. Budgets, an observable log, and source checks therefore have to be designed together. Saving results and resuming jobs have different requirements: using a database alone does not justify claiming that a job can resume. Later work implemented the [M2 investigation features](m2.md) and [result persistence in the first M3 step](m3.md).
