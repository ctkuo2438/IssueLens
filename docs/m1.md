# M1: Local issue investigation app

M1 is complete. It delivers the web app's basic flow: paste a public GitHub issue URL, and an agent with read-only tools returns a cited analysis and an English draft reply.

## Use

<a id="setup"></a>
### Setup and start

You need Python 3.13 or later, uv, Node.js 20.9 or later, and npm. From the repository root, run these. Skip the copy if `.env` already exists.

```bash
uv sync --locked
cp .env.example .env
```

Set `OPENAI_API_KEY`. [M2 settings](m2.md#settings) covers the rest.

```dotenv
OPENAI_API_KEY=your-api-key
OPENAI_MODEL=gpt-5.6
OPENAI_REASONING_EFFORT=medium
GITHUB_TOKEN=
```

Unless PostgreSQL is running, clear `DATABASE_URL` so analyses stay in memory. Without `GITHUB_TOKEN`, public issues are read anonymously, at a lower API limit. Only the backend reads the keys. Keep them out of the frontend and version control.

Start the app. The launcher first runs `npm ci` if frontend dependencies are missing.

```bash
uv run --locked python scripts/dev.py
```

In memory mode it starts the frontend at <http://127.0.0.1:3000> and the API at <http://127.0.0.1:8000/docs>. `Ctrl+C` in its terminal stops everything it started. Restart after changing Python code or `.env`; in memory mode, this clears the jobs. For database mode, see [M3](m3.md#setup).

If a port is in use, these commands find its process. Stop it with `Ctrl+C` in its launcher, or with `kill PID` once you confirm it is this project's.

```bash
lsof -nP -iTCP:3000 -sTCP:LISTEN
lsof -nP -iTCP:8000 -sTCP:LISTEN
```

### Run an analysis

Paste a public issue URL or select `Try an example`, then select `Analyze issue`. Only that calls the real GitHub and model APIs. Activity lists the model requests, tool runs, and stop reason. Analysis shows the summary, known facts, missing information, and draft. Without a valid answer, it keeps the sources and stop reason. Source markers such as `S1` link to GitHub. Refreshing reconnects to the same job while it exists. [M2 features](m2.md#features) covers the other tabs.

## How it works

The Next.js page calls the FastAPI backend through a same-origin proxy, so the browser never needs the API key.

**Agent loop.** The model picks a tool, Python validates and runs it, and the model reads the result and continues or answers. The model chooses; the program controls execution and limits. [agent.py](../backend/app/agent.py) implements this on the plain OpenAI Python SDK.

**Tools.** M1 had three read-only tools: `get_issue`, `get_issue_comments`, and `get_repo_readme`. M2 has [seven](m2.md#tools). Tools are bound to the submitted target, so the model cannot switch repositories or supply a URL. Instructions in GitHub content are never executed.

**Answers.** The model returns JSON in a Pydantic schema, which the backend checks against the sources and business rules. Source IDs exist only for successful fetches.

**Jobs.** An analysis takes several requests, so `POST /api/v1/analyses` returns HTTP 202 and a `job_id`. The page reads `GET /api/v1/analyses/{job_id}`, follows `/events` under that path over SSE (Server-Sent Events), and cancels with `DELETE`. The `analysis` URL parameter keeps the job ID, and reconnects use the event ID to skip events already shown. In memory mode, `asyncio` runs 2 jobs at a time and keeps at most 30. Finished jobs may be cleared after an hour, or sooner when capacity runs short.

**Budgets.** Each case defaults to 8 model requests, 15 logical tool calls, 90 seconds, and an estimated 24,000 tokens per model input (12,000 during the M2 evaluation). Near a limit, the agent answers with what it has. Recorded limitations, such as long content, tool failures, omissions, or a budget stop, may make the job `partial`. `completed` means valid output with no recorded limitation ([Context Builder](m2.md#context-builder)).

## Verification

These offline checks simulate GitHub and the model, need no keys, and do not measure model quality. They test the current code, not the M1 version. Pyright must be installed separately.

```bash
uv run --locked python -W error::RuntimeWarning -m unittest discover -s tests -q
pyright --pythonpath .venv/bin/python backend evaluation scripts
npm --prefix frontend run typecheck
npm --prefix frontend run build
```

## Limits

- In memory mode, a restart loses the jobs, and separate worker processes do not share them.
- Private repositories are not supported: with a token, a run refuses any repository GitHub does not report as public ([M4](m4.md#public-repos-only)).
- A valid source ID proves the source exists, not that it supports the claim. Sources excerpts may be truncated or never sent to the model.
- Activity is an operation log, not the model's reasoning, and `completed` is not human review.
- Token counts are local estimates and may differ from the API's. The per-input cap is not total job usage.

## Tradeoffs and exercises

- **Own loop:** clear data flow, tool control, and stopping, but we own the protocol, errors, and validation.
- **In-process jobs:** quick end to end, but lost on restart and not shared across servers.
- **Model-chosen tools:** adaptable but costly and unpredictable, so budgets, logs, and source checks go together.
- **Saving versus resuming:** a database alone does not make a job resumable.

Exercise: check one known fact against its source, then refresh and confirm that the job is kept.
