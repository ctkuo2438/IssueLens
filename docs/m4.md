# M4: Public trial

M4 prepares IssueLens for a public trial. It adds opt-in GitHub sign-in, ties each analysis to a GitHub account ID, limits how many analyses each account can have in progress, refuses non-public repositories when the server has a GitHub token, keeps anonymous login requests out of the database, and turns malformed GitHub responses into tool failures. The live two-account check with real GitHub sign-in has not been run, and the public-repository guard has not been tested with a real private repository.

## GitHub sign-in and access to analyses

Before public use, the backend needs to know who created each analysis. GitHub OAuth is a sign-in flow in which GitHub confirms the account's identity. IssueLens uses the numeric account ID that GitHub returns, so users can still find their analyses after they rename their GitHub account.

After sign-in, the browser carries a random IssueLens session identifier in an `HttpOnly` cookie. The backend stores a hash of the identifier with the account in PostgreSQL. A session lasts at most eight hours and is revoked immediately on sign-out. GitHub's access token is used to get the account identity, while the analysis tools keep using the server's `GITHUB_TOKEN` setting. See [GitHub OAuth flow](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps) and [GitHub user API](https://docs.github.com/en/rest/users/users#get-the-authenticated-user).

When a job is created, the backend takes the account ID from the session and writes it to PostgreSQL with the job. Reading the result, subscribing to progress, reading the Trace, and cancelling all compare that ID:

- You can open your own analyses as usual.
- Another account's analysis and an analysis that does not exist both return 404.
- Where sign-in is enabled, a request without sign-in gets 401.

When the three OAuth settings are blank, the app uses the original local mode, which can read historical analyses that are not tied to an account. An analysis tied to an account is read by that account in sign-in mode.

## Local setup

In GitHub, create an OAuth App under **Settings > Developer settings > OAuth apps**. Set the homepage URL to `http://127.0.0.1:3000` and the callback URL to `http://127.0.0.1:3000/api/v1/auth/github/callback`. After you get the Client ID and Client Secret, add the settings below to your local `.env`, and keep the PostgreSQL connection from the M3 setup. See [registering an OAuth App](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/creating-an-oauth-app) and [M3 database setup](m3.md#setup).

```dotenv
GITHUB_OAUTH_CLIENT_ID=your-client-id
GITHUB_OAUTH_CLIENT_SECRET=your-client-secret
GITHUB_OAUTH_CALLBACK_URL=http://127.0.0.1:3000/api/v1/auth/github/callback
```

Open the site from the same browser origin as the callback URL. For example, when the callback uses `127.0.0.1`, open the site at `http://127.0.0.1:3000`. Use HTTPS for a remote callback.

```bash
uv run --locked python scripts/dev.py
```

The page should show **Sign in with GitHub**. After sign-in, it shows your GitHub username, and you can create analyses.

## Two-account check

Sign in as account A and account B in two separate browser profiles, then:

1. Create one analysis in each and keep its URL. Reopening your own URL should show the result.
2. Swap the URLs. Both sides should show that the analysis was not found.
3. Open the original URL with the original account again and confirm that the result is still there.

Creating an analysis calls the GitHub and model APIs. This live check with real GitHub sign-in has not been run.

### Interview tradeoff

Database-backed sessions: every request has to check that the session is still valid, which costs one extra database read. In return, sign-out revokes the session immediately. For the first usage limit of the public trial, see [Per-account job limit](#per-account-limit).

<a id="public-repos-only"></a>
## Analyze public repositories only

With `GITHUB_TOKEN` set, GitHub answers according to the token's permissions. If the token can read the operator's private repositories, any signed-in user who submits a private issue URL gets its content in their analysis. IssueLens therefore uses two layers of protection (defense in depth).

### Layer 1: a token that reads only public repositories

Create a token in GitHub under **Settings > Developer settings > Personal access tokens > Fine-grained tokens**:

- Choose your own account as the resource owner.
- Choose **Public repositories** for repository access.
- Add no other permissions.
- Set an expiration date.

This kind of token cannot read private repositories. Its only purpose is to raise the limit from 60 requests per hour per IP to 5,000 requests per hour per account. All tokens of the same account share this limit. Do not use a classic token with the `repo` scope. See [creating a fine-grained token](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#creating-a-fine-grained-personal-access-token).

After you set it, run the command below. It prints only the status and the limit. On success it shows `status: 200 | core limit: 5000`.

```bash
uv run --locked python -c "
import httpx
from dotenv import dotenv_values
token = dotenv_values('.env').get('GITHUB_TOKEN') or ''
r = httpx.get('https://api.github.com/rate_limit', headers={'Authorization': f'Bearer {token}'})
print('status:', r.status_code, '| core limit:', r.json().get('resources', {}).get('core', {}).get('limit'))
"
```

### Layer 2: the analysis confirms that the repository is public

The program cannot tell which kind of token the operator chose. When a token is set, the analysis calls `GET /repos/{owner}/{repo}` before it reads any issue data. The check is part of the agent run (`AgentRun._confirm_public_repository`), so it runs in the Worker and also in memory mode, including the MCP server. It continues only when GitHub explicitly reports `private: false` and a visibility of `public`.

The result is saved in the checkpoint, so a replacement Worker does not check again. If the checkpoint still holds a cooldown that GitHub requested, the cooldown limits only the later reads: those reads are recorded as limitations like any other tool failure, and the evidence already fetched is kept.

Any response that depends on the repository itself and is not explicitly public counts as not public:

- private
- internal
- a missing field
- a malformed response
- not found
- a rename redirect (301)
- a refusal that is not rate limiting (403)

They all share one message and the `repository_not_public` stop reason. If rename or refusal responses had different messages, a signed-in user could compare them to learn which private repositories exist.

Only failures unrelated to the repository are recorded as `repository_check_failed`: a rejected token (401), a connection failure, and a transient error that still fails after the retry. For a transient error or a cooldown that GitHub requests, the check waits within the job's remaining time and then retries once. The check is read-only and repeatable. If a job is interrupted before the check confirms, the resumed job checks again, so the retry does not need to be written to the checkpoint.

Neither stop calls the model, and the job error shows the matching message. The result also contains no repository evidence or model output, including data restored from a checkpoint. Only the budget already used is kept.

The server runs this lookup. It is not one of the seven tools, uses no tool budget, and is not listed as an attempt in the Trace. It is skipped when no token is set, because anonymous requests cannot read private data anyway, and skipping it saves the anonymous limit. The tool layer has one more gate: with a token, `GitHubTools` refuses every other read until the repository is confirmed public, so a new call path cannot skip the check either.

### Verification

```bash
uv run --locked python -W error::RuntimeWarning -m unittest discover -s tests -p 'test_repository_access.py' -v
```

The 14 offline checks cover the responses above, the retry, cooldown waits, anonymous mode, resuming, handling of restored evidence, the tool-layer gate, and the job error messages. Breaking each fix one at a time makes the matching check fail. The full offline regression suite passed 318 tests, with 15 PostgreSQL checks skipped because no test database was set, and Pyright passed on the changed files. This has not been checked with a real private repository. See the [offline checks](../tests/test_repository_access.py).

A later review found a problem when an analysis already confirmed public resumed and met a cooldown longer than the job's remaining time. The old code still went through the cooldown wait before the visibility check, so the run counted as a failed check, cleared the evidence already fetched, and stopped. An analysis that was never interrupted would keep its evidence and finish. Now a confirmed result is reused directly.

The 14th check simulates an interruption after reading the issue, partway through reading the comments, with 600 seconds of cooldown left at resume. Source S1 is kept, an answer is produced, and no GitHub request is sent during the cooldown. Restoring the old order makes this check fail. The full offline regression suite passed 342 tests, with 28 PostgreSQL checks skipped, and Pyright passed.

### Exercise

Replace the URL in the command above with `https://api.github.com/repos/<owner>/<private-repo>` and print only `r.status_code`. With a token that reads only public repositories, you should see `404`, which means the first layer blocks the private repository.

### Limits

- Each analysis with a token makes one extra GitHub request. The result is not cached across jobs, so a repository that turns private does not keep an old confirmation.
- If a repository turns private during an analysis that was already confirmed, it is not checked again.
- When the retry still fails, you need to create a new analysis. No model quota has been spent at that point.

### Interview tradeoff

Protection in configuration versus protection in code. Relying only on token permissions is the least work, but safety then depends on the operator configuring it correctly. The code check costs one extra request but does not depend on configuration. With both layers, a mistake in either one does not by itself cause a leak.

<a id="per-account-limit"></a>
## Per-account job limit

All users share one queue: at most 30 queued or running analyses, and the Worker runs two at a time. Before this change, one account could fill the whole queue, so no one else could create an analysis, and it could also use up the shared model quota.

In sign-in mode, each account can have at most two queued or running analyses at the same time:

- A third one gets 429 with a message that the limit is reached. The user can create another after one of them finishes or is cancelled.
- The Worker runs only two at a time anyway, so queuing more from one account would only mean waiting.
- This check runs in the same database transaction as the site-wide limit of 30 and is ordered by the same advisory lock, so several API processes creating analyses at once cannot exceed the limit.
- When both limits are full, the account limit is reported first, because the user can wait for their own analyses to finish.
- `Settings.max_active_per_account` sets the limit. The default is 2.
- Local mode has no accounts and applies only the site-wide limit.

### Verification

```bash
ISSUELENS_TEST_DATABASE_URL=postgresql://issuelens@127.0.0.1:5432/issuelens_test \
  uv run --locked python -W error::RuntimeWarning -m unittest discover -s tests -p 'test_*.py' -v \
  -k test_each_account_keeps -k test_separate_api_connections
```

Three checks should pass:

- The two-account integration check confirms that after account A creates two analyses, the third gets 429, account B can still create one, and after A cancels a queued analysis, A can create another.
- The other two confirm that when two API connections create analyses for the same account at the same time, only one succeeds, that local creation without an account is not affected, and that the site-wide limit still works.

Removing the account check, or changing it to count analyses across all accounts, makes the matching check fail. The full regression suite passed 338 tests, 26 of them against a real PostgreSQL, and Pyright passed. Model and GitHub responses were simulated.

### Exercise

Sign in to different accounts in two browser profiles. In one, create three analyses in a row and look at the error message for the third. Then create one from the other account. This calls the real GitHub and model APIs.

### Limits

This limits only how many analyses are in progress at once, not the total per day: an account can keep creating new analyses after earlier ones finish. The limit counts GitHub accounts, so one person with several accounts gets more quota.

### Interview tradeoff

Compare three kinds of usage limit:

- A concurrency limit keeps one account from filling the queue. It only needs a count at creation time.
- A rate limit (for example, a token bucket) controls the number of requests over a period of time.
- A budget limit directly caps the model tokens or cost each account can use per day.

This step adds the concurrency limit first, because it directly protects other users' ability to queue analyses. A daily limit has to wait for real trial usage, so that its value can be based on the usage seen.

## Anonymous requests do not write to the database

`/api/v1/auth/github/login` can be called without signing in. Previously, each call wrote one login-request row to PostgreSQL and cleaned up expired rows with a full table scan. In a test against a temporary database, one client wrote 300 rows in 0.3 seconds. Sustained calls would keep growing the table and the cleanup cost, take up the only two database connections the API has, and slow down every user.

Now the login state, the PKCE verifier, and the analysis ID to return to after sign-in are all kept in HttpOnly cookies that last ten minutes, and `/login` no longer touches the database. When GitHub redirects to the callback:

1. The backend confirms that the state in the URL matches the cookie.
2. It reads once by primary key to confirm that this login has not been used yet. If it has, the backend refuses and does not exchange a token with GitHub again.
3. Only after GitHub confirms the identity does it record this login in `issuelens_used_logins`, in the same transaction that creates the session. The primary key is unique, so even when two callbacks pass the read check at the same time, only one can create a session.

This table grows only with successful sign-ins. Expired rows are removed through the expiry index when a session is created.

GitHub's documentation says only that an authorization code expires after ten minutes. It does not say whether a code can be used only once. IssueLens therefore guarantees on its own that each login can be used only once, and does not rely on undocumented GitHub behavior. The PKCE verifier sits in an HttpOnly cookie in the user's own browser, where page scripts cannot read it. Someone who intercepts the authorization code does not have this cookie and cannot exchange the code for a token.

### Verification

```bash
ISSUELENS_TEST_DATABASE_URL=postgresql://issuelens@127.0.0.1:5432/issuelens_test \
  uv run --locked python -W error::RuntimeWarning -m unittest discover -s tests -p 'test_auth.py' -v
```

Eight checks should pass. The three new ones confirm that:

- after 20 `/login` calls without sign-in, the row counts of every login table are unchanged;
- after a successful sign-in, replaying the callback is refused even with the state and verifier cookies set back, and no token is exchanged with GitHub again;
- when two sessions for the same login are created at the same time, only one succeeds.

Before the fix, the first check failed because 20 rows were added. Removing the uniqueness handling or the read check on purpose makes the matching check fail. The full regression suite passed 340 tests, 28 of them against a real PostgreSQL, and Pyright passed.

### Exercise

Open the browser's developer tools, select **Sign in with GitHub**, and look under Application > Cookies for `issuelens_oauth_state` and `issuelens_oauth_verifier`. After sign-in completes, these two cookies are cleared and only `issuelens_session` remains.

### Limits

- This does not include per-IP rate limiting. The callback can still be called in large numbers, and each call exchanges a token with GitHub. A reverse proxy in the deployment usually limits this kind of traffic.
- `issuelens_oauth_requests` in older databases is no longer used, and its contents are left as they were. Once you confirm you do not need it, you can remove it in `psql` with `DROP TABLE issuelens_oauth_requests;`.
- A sign-in that is in progress during the upgrade fails once. Sign in again.

### Interview tradeoff

How to handle unauthenticated traffic. The best protection is to keep it away from expensive resources, rather than to add a cap afterward. Here the state of a login attempt stays on the client first, and the server writes data only after GitHub confirms the identity. The cost is one extra primary-key read in the callback, and login state spread across three cookies.

## GitHub response format checks

Of the seven tools, the ones for comments, templates, search, and related issues already checked the response format. `get_issue`, `get_repo_readme`, and `get_repo_labels` read fields directly. On a format mismatch, Python's `KeyError`, `TypeError`, or `AttributeError` was not a tool error. It escaped the agent, and the whole analysis stopped with "Check server configuration". For example, when the labels API returned an object instead of a list, the issue evidence already read was still there, but no answer was produced, and the earlier model requests were wasted. Two cases that match [GitHub's issue response schema](https://docs.github.com/en/rest/issues/issues#get-an-issue) also stopped the analysis: `user` being `null`, and `labels` items being strings instead of objects.

Now these three tools also check the format first. On a mismatch they raise a tool error, such as `GitHub returned invalid label data.`, and follow the existing tool failure path: the failure is recorded as a limitation and the analysis continues.

- When `user` is `null`, the author shows as `(unknown)`. GitHub usernames cannot contain parentheses, so it cannot be mistaken for a real account.
- A label given as a string is used directly as the label name.
- When the target issue cannot be read, the analysis cannot continue. The job stops at `target_issue_unavailable`, and the error message now says that no issue evidence was found.

### Verification

```bash
uv run --locked python -W error::RuntimeWarning -m unittest discover -s tests -p 'test_github_payloads.py' -v
```

Six checks should pass:

- Three tool-level checks cover 26 malformed formats across the three tools. Each one is a tool error and leaves no evidence or label catalog behind.
- A fourth confirms that a `null` author and string labels, which the schema allows, can be read.
- Two job-level checks confirm that a malformed labels response still lets the analysis produce an answer from the existing evidence, and that a malformed issue makes the job report that no issue evidence was found.

Before the fix, all six checks failed. The full offline regression suite passed 348 tests, with 28 PostgreSQL checks skipped, and Pyright passed. GitHub and model responses were simulated.

### Exercise

Add `[{"name": "bug", "color": "zzz"}]` to the label cases in `tests/test_github_payloads.py`. The color format is handled by Pydantic validation in `RepositoryLabel`. Observe which error it raises and how the agent records it as a tool failure.

### Interview tradeoff

Compare checking each format at the boundary with catching every exception where tools run. The second stops every crash with one line, but it also disguises bugs in our own code as external data errors, which makes them hard to find later. This step chooses the first: errors in external data become explicit tool failures, and errors in our own code are still recorded by the job layer as `unexpected_error`.
