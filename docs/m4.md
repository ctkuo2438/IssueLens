# M4: Public trial

M4 prepares IssueLens for a public trial: opt-in GitHub sign-in, per-account ownership and job limits, a public-repositories-only guard, login state outside the database, and response format checks. The live two-account sign-in check and a real private repository test have not been run.

## Use

Sign-in needs the [web app](../README.md#run-the-web-app) with [PostgreSQL](m3.md#setup) and `DATABASE_URL`.

### GitHub sign-in

Create an [OAuth App](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/creating-an-oauth-app) under **Settings > Developer settings > OAuth apps** with the homepage URL `http://127.0.0.1:3000` and the callback URL `http://127.0.0.1:3000/api/v1/auth/github/callback`. Add its Client ID and Client Secret to `.env`:

```dotenv
GITHUB_OAUTH_CLIENT_ID=your-client-id
GITHUB_OAUTH_CLIENT_SECRET=your-client-secret
GITHUB_OAUTH_CALLBACK_URL=http://127.0.0.1:3000/api/v1/auth/github/callback
```

Open the site from the callback's origin. A remote callback needs HTTPS. Start the app with `uv run --locked python scripts/dev.py`, and the page shows **Sign in with GitHub**. Blank OAuth settings keep local mode.

### Server GitHub token

Create a [fine-grained token](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#creating-a-fine-grained-personal-access-token) under **Settings > Developer settings > Personal access tokens** for your own account, with **Public repositories** access, no other permissions, and an expiration date. It only raises GitHub's rate limit. Do not use a classic `repo` token. On success this prints `status: 200 | core limit: 5000`:

```bash
uv run --locked python -c "
import httpx
from dotenv import dotenv_values
token = dotenv_values('.env').get('GITHUB_TOKEN') or ''
r = httpx.get('https://api.github.com/rate_limit', headers={'Authorization': f'Bearer {token}'})
print('status:', r.status_code, '| core limit:', r.json().get('resources', {}).get('core', {}).get('limit'))
"
```

## How it works

### Sign-in and ownership

GitHub [OAuth](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps) confirms the account, and ownership uses its numeric ID, which survives renames. Tools still use `GITHUB_TOKEN`, not the OAuth token. An `HttpOnly` cookie carries a random session identifier, PostgreSQL stores its hash, and the session ends after eight hours or at sign-out.

The result, progress, Trace, and cancel routes check the job's account ID. Another account's analysis returns 404, like a missing one, and no sign-in returns 401. Local mode reads only unowned analyses.

<a id="public-repos-only"></a>
### Public repositories only

A token that reads private repositories could expose them to any signed-in user. A code check backs up the public-only token (defense in depth).

With a token, `AgentRun._confirm_public_repository` calls `GET /repos/{owner}/{repo}` before any issue read, in every mode, including the MCP server. Only `private: false` with visibility `public` passes.

- `repository_not_public`: private, internal, a missing field, a malformed response, not found, 301, or a non-rate-limit 403. One shared message keeps responses from revealing which private repositories exist.
- `repository_check_failed`: a rejected token (401), a connection failure, or a transient error that outlasts one retry within the job's time.

Neither stop calls the model or keeps repository evidence, even from a checkpoint. A resumed job reuses a saved confirmation. The check is not a tool or Trace attempt, uses no tool budget, and is skipped without a token. `GitHubTools` refuses other reads until it passes.

### Per-account job limit

One account could fill the shared queue of 30 queued or running analyses, which the Worker runs two at a time. In sign-in mode, an account's third active analysis gets 429 until one finishes or is cancelled. The count shares the site-wide limit's transaction and advisory lock, so parallel API processes cannot exceed it. `Settings.max_active_per_account` sets it (default 2). Local mode keeps only the site-wide limit.

### Login state outside the database

Anonymous calls to `/api/v1/auth/github/login` used to write a database row each. Now the state, PKCE verifier, and return analysis ID live in `HttpOnly` cookies for ten minutes, and `/login` skips the database.

The callback checks the state cookie and refuses a login already in `issuelens_used_logins` without contacting GitHub. After GitHub confirms the identity, the login is recorded in the new session's transaction, and a unique key lets one racing callback win. GitHub does not document single-use codes, so IssueLens enforces it. An intercepted code cannot be exchanged without the verifier cookie.

### GitHub response format checks

`get_issue`, `get_repo_readme`, and `get_repo_labels` read fields unchecked, so a `KeyError` or `TypeError` failed the whole analysis, even on a `null` user or string labels that [GitHub's schema](https://docs.github.com/en/rest/issues/issues#get-an-issue) allows. Now they validate first, like the other four tools, and a mismatch becomes a limitation. A `null` user reads as `(unknown)`, never a real username, and a string label is the name. An unreadable target issue stops at `target_issue_unavailable`.

## Limits

- With a token, each analysis makes one extra, uncached GitHub request, and a repository that turns private mid-analysis is not rechecked.
- If the visibility retry fails, create a new analysis. No model quota was spent.
- The account limit caps work in progress, not daily use, and several GitHub accounts get more.
- There is no per-IP rate limiting, and each callback exchanges a token with GitHub. A reverse proxy usually limits this.
- Older databases keep an unused `issuelens_oauth_requests` table, which `DROP TABLE issuelens_oauth_requests;` removes.
- A sign-in in progress during the upgrade fails once.

## Tradeoffs and exercises

- **Token permissions versus a code check:** configuration is free but trusts the operator, and the check costs a request. Together, one mistake alone does not leak.
- **Concurrency versus rate or budget limits:** concurrency needs one count and protects the queue. A daily budget waits for real usage.
- **Unauthenticated traffic:** keep it off expensive resources, for one primary-key read and three cookies.
- **Boundary checks versus a broad `except`:** a broad catch disguises our bugs as bad GitHub data. Ours still end as `unexpected_error`.
