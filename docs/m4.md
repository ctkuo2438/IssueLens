# M4 公開試用

## GitHub 登入與分析存取權限

公開使用前，後端需要知道誰建立了每筆分析。GitHub OAuth 是由 GitHub 確認帳號身分的登入流程。IssueLens 使用 GitHub 回傳的數字帳號 ID，讓使用者改名後仍能查回原有分析。

登入後，瀏覽器以 `HttpOnly` cookie 攜帶 IssueLens 工作階段的隨機識別值。後端把識別值的雜湊與帳號存在 PostgreSQL，工作階段最長八小時，登出時立即撤銷。GitHub 的授權權杖用於取得帳號身分，分析工具沿用伺服器端的 `GITHUB_TOKEN` 設定。[GitHub OAuth 流程](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps) · [GitHub 帳號 API](https://docs.github.com/en/rest/users/users#get-the-authenticated-user)

建立任務時，後端從工作階段取得帳號 ID，和任務一起寫入 PostgreSQL。查詢結果、訂閱進度、讀取 Trace 及取消時，都會比對該 ID。自己的分析可照常開啟。另一帳號的分析和不存在的分析都回傳 404。已啟用登入的環境中，未登入會收到 401。

三個 OAuth 設定留白時使用原本的本機模式，可查詢尚未綁定帳號的歷史分析。綁定帳號的分析由對應帳號在登入模式查詢。

## 本機設定

在 GitHub 的 **Settings → Developer settings → OAuth apps** 建立一個 OAuth App，首頁填入 `http://127.0.0.1:3000`，回呼網址填入 `http://127.0.0.1:3000/api/v1/auth/github/callback`。取得 Client ID 和 Client Secret 後，在本機 `.env` 加入以下設定，並保留 M3 設定的 PostgreSQL 連線。[GitHub 註冊說明](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/creating-an-oauth-app) · [M3 資料庫設定](m3.md#本機設定與啟動)

```dotenv
GITHUB_OAUTH_CLIENT_ID=your-client-id
GITHUB_OAUTH_CLIENT_SECRET=your-client-secret
GITHUB_OAUTH_CALLBACK_URL=http://127.0.0.1:3000/api/v1/auth/github/callback
```

使用和回呼網址相同的瀏覽器來源。例如回呼填 `127.0.0.1` 時，從 `http://127.0.0.1:3000` 開啟網站。遠端回呼使用 HTTPS。

```bash
uv run --locked python scripts/dev.py
```

畫面應顯示 **Sign in with GitHub**。登入後會顯示 GitHub 帳號名稱，並可建立分析。

## 只分析公開 Repo

設定 `GITHUB_TOKEN` 後，GitHub 會依權杖的權限回應。若權杖能讀取營運者的私有 repo，任何登入者送出私有 issue 網址，內容就會進入他的分析結果。IssueLens 因此使用兩層防護（defense in depth）。

**第一層：權杖只讀公開 repo。** 在 GitHub 的 **Settings → Developer settings → Personal access tokens → Fine-grained tokens** 建立權杖。Resource owner 選自己的帳號，Repository access 選 **Public repositories**，不加其他權限，並設定到期日。這種權杖讀不到私有 repo，用途只是把額度從每個 IP 每小時 60 次提高到每個帳號每小時 5,000 次，同一帳號的權杖共用這個額度。不要使用勾選 `repo` scope 的 classic token。[建立 fine-grained token](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#creating-a-fine-grained-personal-access-token)

設定後執行下列命令。它只印出狀態與額度，成功時顯示 `status: 200 | core limit: 5000`。

```bash
uv run --locked python -c "
import httpx
from dotenv import dotenv_values
token = dotenv_values('.env').get('GITHUB_TOKEN') or ''
r = httpx.get('https://api.github.com/rate_limit', headers={'Authorization': f'Bearer {token}'})
print('status:', r.status_code, '| core limit:', r.json().get('resources', {}).get('core', {}).get('limit'))
"
```

**第二層：Worker 先確認 repo 公開。** 程式無法確認營運者選了哪種權杖。設定權杖時，Worker 在讀取任何 issue 資料前先查詢 `GET /repos/{owner}/{repo}`，GitHub 明確回報 `private: false` 且 visibility 為 `public` 才繼續。確認結果存入檢查點，替換 Worker 後不再重查。

凡是取決於 repo 本身、又不是明確公開的回應，都視為不公開：私有、internal、缺少欄位、格式錯誤、找不到、改名轉址（301），以及非限流的拒絕（403）。它們共用同一則訊息和 `repository_not_public` 停止原因。若改名或拒絕回應有不同訊息，登入者就能比對出哪些私有 repo 存在。

只有與 repo 無關的失敗才記為 `repository_check_failed`，包括權杖被拒（401）、連線失敗，以及補送後仍失敗的暫時性錯誤。暫時性錯誤與 GitHub 要求的冷卻時間在任務剩餘時間內等待後補送一次。這個檢查唯讀、可重複，Worker 中斷後接續時會重查，所以補送不必寫入檢查點。兩種停止都不會呼叫模型，任務錯誤會顯示對應訊息。結果也不含任何 repo 證據或模型輸出，連同從檢查點還原的資料在內，只保留已用的預算。

這項查詢由伺服器執行，不屬於七個工具，不占工具預算，也不列入 Trace 的嘗試。未設定權杖時跳過，因為匿名請求本來就讀不到私有資料，也能保留匿名額度。工具層另有一道關卡：使用權杖時，repo 確認公開前，`GitHubTools` 拒絕其他讀取，新的呼叫入口也無法略過檢查。

```bash
uv run --locked python -W error::RuntimeWarning -m unittest discover -s tests -p 'test_repository_access.py' -v
```

13 項離線檢查涵蓋上述各種回應、補送、冷卻等待、匿名模式、接續、還原證據的處理、工具層關卡與任務錯誤訊息。把各項修正逐一改壞時，對應的檢查都會失敗。完整離線回歸 318 項通過，15 項 PostgreSQL 檢查因未設定測試資料庫而略過，Pyright 檢查變更檔案通過。尚未用真實私有 repo 驗收。[離線檢查](../tests/test_repository_access.py)

練習時，把上面命令的網址換成 `https://api.github.com/repos/<帳號>/<私有 repo>`，並只印出 `r.status_code`。使用只讀公開 repo 的權杖時應看到 `404`，代表第一層已擋住私有 repo。

每筆設定權杖的分析多一次 GitHub 請求，結果不跨任務快取，避免 repo 轉為私有後仍沿用舊的確認。已確認的分析途中若 repo 改為私有，不會重查。補送仍失敗時，需要重新建立分析，這時尚未花費模型額度。

面試可討論設定層與程式層防護的取捨。只靠權杖權限最省事，但安全取決於營運者是否設定正確。程式檢查多一次請求，卻不依賴設定。兩層並用時，任一層出錯都不會直接造成外洩。

## 兩個帳號驗收

用兩個獨立的瀏覽器設定檔分別登入帳號 A 和 B。各建立一筆分析並保留網址，重新開啟自己的網址應可看到結果。交換網址後，兩邊都應顯示找不到分析。再用原帳號開啟原網址確認結果仍在。建立分析會呼叫 GitHub 和模型 API。

以下整合測試使用真實 PostgreSQL、FastAPI 和 Worker，GitHub 登入回應與分析內容使用測試資料。

```bash
ISSUELENS_TEST_DATABASE_URL=postgresql://issuelens@127.0.0.1:5432/issuelens_test \
  uv run --locked python -W error::RuntimeWarning -m unittest discover -s tests -p 'test_auth.py' -v
```

兩個測試身分均可取得自己的結果、進度及 Trace。交叉讀取與取消均回傳 404。測試也涵蓋登出撤銷、新 API 實例讀回工作階段、GitHub 改名後仍可查詢，以及本機歷史分析的存取。[整合測試](../tests/test_auth.py)

兩個隔離的 Chrome 工作階段也經由正式建置的 Next.js、FastAPI 和 PostgreSQL 完成模擬登入與分析。兩邊能看自己的草稿，開啟對方網址會顯示找不到分析，登出後原網址回傳 401。完整回歸 304 項通過，包含 15 項真實 PostgreSQL 檢查。Pyright 與 Next.js 正式建置通過。真實 GitHub 登入可在設定 OAuth App 後按上面的流程驗收。

面試可討論資料庫工作階段的取捨。每次查詢需要確認工作階段是否有效，代價是多一次資料庫讀取，優點是登出後能立刻撤銷登入。公開試用的第一個用量限制見[每個帳號的任務上限](#每個帳號的任務上限)。

## 每個帳號的任務上限

所有使用者共用一個佇列：最多 30 筆排隊或執行中的分析，Worker 一次執行兩筆。先前一個帳號就能排滿整個佇列，讓其他人無法建立分析，也可能耗盡共用的模型額度。

登入模式下，每個帳號最多同時有兩筆排隊或執行中的分析。第三筆會收到 429，訊息說明已達上限，等其中一筆結束或取消後即可再建立。Worker 一次也只執行兩筆，一個帳號排更多只是在等待。這項檢查和全站的 30 筆上限在同一筆資料庫交易中進行，並由同一個 advisory lock 排序，多個 API 程序同時建立也不會超過上限。兩項同時已滿時，先回報帳號上限，因為使用者可以等自己的分析結束。上限由 `Settings.max_active_per_account` 設定，預設為 2。本機模式沒有帳號，只套用全站上限。

```bash
ISSUELENS_TEST_DATABASE_URL=postgresql://issuelens@127.0.0.1:5432/issuelens_test \
  uv run --locked python -W error::RuntimeWarning -m unittest discover -s tests -p 'test_*.py' -v \
  -k test_each_account_keeps -k test_separate_api_connections
```

三項檢查應通過。兩個帳號的整合檢查確認：帳號 A 建立兩筆後，第三筆收到 429；帳號 B 仍可建立；A 取消一筆排隊中的分析後，可以再建立一筆。另外兩項確認，兩條 API 連線同時替同一個帳號建立時只有一筆成功，沒有帳號的本機建立不受影響，全站上限也照常生效。把帳號檢查拿掉，或改成計算所有帳號的數量時，對應的檢查都會失敗。完整回歸 338 項通過，其中 26 項使用真實 PostgreSQL，Pyright 通過。模型與 GitHub 回應均為模擬。

練習時用兩個瀏覽器設定檔登入不同帳號，在其中一個連續建立三筆分析，觀察第三筆的錯誤訊息，再從另一個帳號建立一筆。這會呼叫真實的 GitHub 與模型 API。

這只限制同時進行中的數量，不限制一天內的總量：一個帳號可以在分析結束後持續建立新的分析。上限以 GitHub 帳號計算，同一個人使用多個帳號就能取得更多額度。

面試可比較三種用量限制。同時上限防止單一帳號占滿佇列，實作只需在建立時計數；頻率限制（例如 token bucket）控制一段時間內的請求次數；預算上限直接限制每個帳號每天可用的模型 token 或費用。這次先做同時上限，因為它直接保護其他使用者能排入分析。每日上限要等實際試用後，依用量決定合理的數值。

## 未登入的請求不寫入資料庫

`/api/v1/auth/github/login` 不需要登入就能呼叫。先前每次呼叫都會在 PostgreSQL 寫入一列登入請求，並以全表掃描清理過期資料。用暫時的資料庫實測，一個用戶端 0.3 秒就寫入 300 列。持續呼叫會讓資料表與清理成本不斷增加，佔滿 API 僅有的兩條資料庫連線，拖慢所有使用者。

現在登入過程的 state、PKCE verifier 與登入後要回到的分析 ID 都放在 HttpOnly cookie，有效期十分鐘，`/login` 不再碰資料庫。GitHub 導回 callback 時，後端先確認網址上的 state 與 cookie 相同，再用主鍵讀取一次，確認這次登入還沒用過，用過就拒絕，不會再向 GitHub 交換權杖。向 GitHub 確認身分之後，才在建立工作階段的同一筆交易中，把這次登入記入 `issuelens_used_logins`。主鍵唯一，兩個 callback 同時通過讀取檢查時，也只有一個能建立工作階段。這張表只隨成功的登入成長，過期資料會在建立工作階段時依到期時間的索引清除。

GitHub 文件只說明授權碼十分鐘後失效，沒有說明是否只能使用一次。因此「同一次登入只能使用一次」由 IssueLens 自己保證，不依賴 GitHub 的未公開行為。PKCE verifier 放在使用者自己瀏覽器的 HttpOnly cookie，網頁程式讀不到；攔截到授權碼的人沒有這個 cookie，就無法換到權杖。

```bash
ISSUELENS_TEST_DATABASE_URL=postgresql://issuelens@127.0.0.1:5432/issuelens_test \
  uv run --locked python -W error::RuntimeWarning -m unittest discover -s tests -p 'test_auth.py' -v
```

八項檢查應通過。新增的三項確認：20 次未登入的 `/login` 呼叫後，所有登入相關資料表的列數不變；登入成功後，就算把 state 與 verifier cookie 都設回去重放 callback，也會被拒絕，且不會再向 GitHub 交換權杖；兩個同一次登入的工作階段同時建立時，只有一個成功。修正前，第一項會因新增 20 列而失敗。刻意拿掉唯一性處理或讀取檢查時，對應的檢查會失敗。完整回歸 340 項通過，其中 28 項使用真實 PostgreSQL，Pyright 通過。

練習時在瀏覽器開啟開發者工具，點 **Sign in with GitHub** 後，到 Application → Cookies 查看 `issuelens_oauth_state` 與 `issuelens_oauth_verifier`。完成登入後，這兩個 cookie 會被清除，只留下 `issuelens_session`。

這不包含依 IP 的頻率限制。callback 仍可能被大量呼叫，每次都會向 GitHub 交換權杖，這類流量通常由部署時的 reverse proxy 限制。舊資料庫中的 `issuelens_oauth_requests` 已不再使用，內容保留原樣；確認不需要後，可以在 `psql` 執行 `DROP TABLE issuelens_oauth_requests;` 移除。升級時正在進行的登入會失敗一次，重新登入即可。

面試可討論如何處理未驗證的流量。最好的防護是讓它碰不到昂貴的資源，而不是事後加上上限。這裡把登入嘗試的狀態先放在用戶端，等 GitHub 確認身分之後，伺服器才寫入資料。代價是 callback 多一次主鍵讀取，以及登入狀態要分散在三個 cookie。
