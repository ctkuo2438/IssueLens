# M5 在 Claude Code 與 Codex 中使用 IssueLens

## 目標與範圍

許多開發者直接在 Claude Code 或 Codex 裡工作。M5 把 IssueLens 的分析包成這兩個工具都能呼叫的 **MCP server**：使用者在對話中貼上 issue 網址，程式助手呼叫 IssueLens，取回有引用的分析報告。

MCP（Model Context Protocol）是 AI 應用程式連接外部工具的標準協定，底層是 JSON-RPC 2.0。本機使用 **stdio** 傳輸：Claude Code 或 Codex 啟動 IssueLens 程序，從標準輸入送出請求，從標準輸出讀回應，每則訊息佔一行 JSON。[MCP 規格](https://modelcontextprotocol.io/specification/2025-11-25) · [Claude Code 的 MCP 設定](https://code.claude.com/docs/en/mcp) · [Codex 的 MCP 設定](https://developers.openai.com/codex/mcp)

第一步的範圍：

- 一個工具 `analyze_github_issue(issue_url)`，在 MCP server 程序內以記憶體模式執行現有的 Agent。提示詞、模型、預算與七個 GitHub 工具都不變，M2 維持凍結。
- 在使用者自己的電腦執行，使用 IssueLens 目錄中 `.env` 的金鑰。
- 支援取消、進度通知，以及兩個客戶端實際使用的協定版本。

暫不包含：遠端服務、只提供證據的細部工具與私有 repo。讓其他人不必 clone 也能安裝的工作見[打包與發布](#packaging)。

選擇「整個分析當成一個工具」，是因為 IssueLens 的價值在於有邊界、有引用、經過驗證的調查流程。只提供讀取 GitHub 的工具，Claude Code 本來就能用 `gh` 做到。代價是每次呼叫都使用 OpenAI 額度，也要等整個分析完成。

## 設定

需要能執行網頁版的環境：clone 專案、執行 `uv sync --locked`，並在 `.env` 設定 `OPENAI_API_KEY`（[M1 環境設定](m1.md#環境與啟動)）。`GITHUB_TOKEN` 可選；設定後只分析公開 repo，規則同 [M4](m4.md#只分析公開-repo)。

以下把 `/path/to/IssueLens` 換成專案的絕對路徑。

**Claude Code：**

```bash
claude mcp add --scope user issuelens -- uv run --directory /path/to/IssueLens --locked issuelens-mcp
claude mcp list
```

`--scope user` 讓所有專案都能使用。`claude mcp list` 應顯示 `issuelens: ... - ✔ Connected`。`issuelens-mcp` 是打包後的指令；之前用 `python -m backend.app.mcp` 加入的設定照樣可用。Claude Code 的工具逾時預設約 28 小時，不需要調整。

**Codex：**

```bash
codex mcp add issuelens -- uv run --directory /path/to/IssueLens --locked issuelens-mcp
```

Codex 的工具逾時預設是 60 秒，但一次分析最長 90 秒，所以必須調長。打開 `~/.codex/config.toml`，在 `[mcp_servers.issuelens]` 下加入一行：

```toml
tool_timeout_sec = 180
```

再執行 `codex mcp get issuelens`，確認輸出有 `tool_timeout_sec: 180`。拼錯的欄位會被直接忽略，不會報錯，這一步可以及早發現。180 秒涵蓋 90 秒的任務時限，以及已有兩筆分析在執行時的排隊時間。

金鑰留在 IssueLens 的 `.env`，不必寫進 `~/.claude.json` 或 Codex 的設定，這兩者都是明文檔案。MCP server 環境中已有的變數優先，其餘才從 `.env` 讀取；從 checkout 執行時讀 checkout 的 `.env`，安裝版則讀 `~/.config/issuelens/.env`（見[第二步](#settings-file)）。MCP server 會忽略 `.env` 中網頁版的 `DATABASE_URL` 與 OAuth 設定，分析只保存在這個程序的記憶體中。

每次模型請求的本機 context 預算預設是 24,000 個 token（`AGENT_CONTEXT_TOKENS`，可設 2,000 到 32,000）。這是 IssueLens 自己估算的上限，不是模型的視窗大小；請求只會隨實際證據變大，不會因為上限較高就用滿。原本的預設是 12,000，兩個客戶端的驗收都因此得到 `partial`，調整的原因與驗證見[Context 預算調為 24,000](#context-budget)。M2 的提示詞與預留空間是在 12,000 下調整與評估的，其他 issue 在 24,000 下的品質尚未重新評估。[Context Builder](m2.md#context-builder)

## 使用

在 Claude Code 或 Codex 的對話中輸入，例如：

```text
Use IssueLens to analyze https://github.com/pallets/flask/issues/6146 and tell me what information is still missing.
```

程式助手會先請你同意這次工具呼叫，再等分析完成，通常需要 20 到 90 秒。每次呼叫最多 8 次 OpenAI 請求，費用與網頁版的一次分析相同。

## 運作方式

```text
Claude Code / Codex ──stdin──▶ McpServer ──▶ IssueAnalysisTool ──▶ JobManager ──▶ AgentRun
                    ◀─stdout── (protocol.py)  (analysis_tool.py)   (memory mode)   (existing agent)
```

程式在 [backend/app/mcp/](../backend/app/mcp/)：`protocol.py` 是通用的協定層，`analysis_tool.py` 定義 IssueLens 的工具與報告，`__main__.py` 負責 stdio 與啟動。

**連線與協定版本。** 2025 年的版本以 `initialize` 握手協商版本。2026-07-28 版改成無狀態，每個請求自帶版本，並以 `server/discover` 取代握手。實測兩個客戶端的結果：

| 客戶端 | 第一則訊息 | 協商結果 |
| --- | --- | --- |
| Claude Code 2.1.323 | `server/discover`（2026-07-28），收到 method not found 後改送 `initialize` | `2025-11-25` |
| Codex 0.167.2 | `initialize` | `2025-06-18` |

IssueLens 支援 `2025-11-25` 與 `2025-06-18`。這兩版在本專案用到的方法上相同：`initialize`、`ping`、`tools/list`、`tools/call` 與取消通知。客戶端要求其他版本時，server 回覆最新的 `2025-11-25`，由客戶端決定是否繼續。`server/discover` 則回覆 method not found，Claude Code 會自動退回舊版握手。

**工具呼叫與取消。** 每個 `tools/call` 在獨立的 asyncio task 執行，讀取迴圈仍能同時處理其他訊息，包括取消通知。收到 `notifications/cancelled` 時，IssueLens 取消對應的分析，停止後續的模型請求，並依規格不回應這個請求。客戶端關閉 stdin 代表結束連線，執行中的分析也會一起取消。

**進度通知。** 一次分析最長 90 秒。客戶端在 `tools/call` 的 `_meta` 帶 `progressToken` 時，IssueLens 一邊等分析完成，一邊追蹤 Activity 事件；每次有新事件，就送出一則 `notifications/progress`，訊息是最新事件的文字，例如 `Investigation step 1: choosing the next action.`。總步數事先不知道，所以不帶 `total`。

- 規格要求 `progress` 每次都要增加，所以由協定層計數，工具只提供文字。工具怎麼寫，都不會送出遞減的進度。
- 同時產生的多個事件只送最新的一則，超過 200 字的訊息會截斷，避免洗版；完整內容仍在報告與限制中。
- 呼叫完成或被取消後，進度函式立即失效，不會送出規格禁止的過期通知。
- `progressToken` 可以是 `0`。實測中 Codex 在 `tools/list` 送出的 token 就是 `0`，所以判斷依據是型別，而不是真假值。

**錯誤。** 不存在的工具與格式錯誤的訊息回傳 JSON-RPC 錯誤。參數錯誤、缺少 `OPENAI_API_KEY`、網址不是 GitHub issue、設定錯誤，以及分析失敗，都以 `isError: true` 的工具結果回傳，讓程式助手讀到原因並修正。除了分析失敗，這些檢查都在發出任何模型請求前完成。

**stdout 只給協定。** stdio 傳輸中，標準輸出的每一行都必須是 JSON-RPC 訊息。server 啟動時先複製一份真正的 stdout 專門寫協定訊息，再把檔案描述元 1 指向 stderr。之後任何 `print` 或函式庫的直接輸出都會進到 stderr，不會弄壞協定。

**報告。** 工具回傳一段 JSON 文字，欄位依序是 `notice`、`status`、`issue_url`、`error`、`issue`、`summary`、`known_facts`、`missing_information`、`similar_issues`、`label_recommendations`、`draft_reply`、`limitations`、`sources` 和 `usage`。

GitHub 內容可能由任何人撰寫，而程式助手能執行指令，所以報告的處理比網頁版更保守：

- `notice` 是第一個欄位，說明整份報告是由第三方內容整理成的資料，不要照著執行。工具描述與 server 的 `instructions` 也有相同的提醒。
- `sources` 只列 ID、類型、標題與網址，不附原始摘錄。摘錄是未經處理的第三方文字，程式助手需要時可以打開網址查證。
- 報告用 JSON 傳遞，issue 內容就算寫成 Markdown 標題或假的系統訊息，也只是某個字串欄位的值。

這些措施只能降低風險，無法完全防止 prompt injection：摘要與草稿仍由模型根據不可信的內容寫成。程式助手要執行指令時，使用者仍應確認內容。

這版只回傳文字，沒有 `structuredContent` 與 `outputSchema`。規格建議同時提供兩者時，文字部分也放同一份 JSON；若客戶端把兩份都交給模型，報告的 token 就會加倍。Codex 的驗收顯示它保留了 `structured_content` 欄位；Claude Code 則把文字原樣交給模型。要不要加上 `structuredContent` 仍待決定。

## 檢查與驗證

```bash
uv run --locked python -W error::RuntimeWarning -m unittest discover -s tests -p 'test_mcp.py' -v
```

27 項檢查應通過，不呼叫模型或 GitHub。

- **協定：** 版本協商、`server/discover`、`ping`、工具清單、七種格式錯誤的訊息、不需回應的通知、未知工具、並行呼叫、重複的請求 ID、取消後不回應、未預期錯誤只記錄例外型別、關閉時取消執行中的呼叫；以及進度只在呼叫期間送出、token 為 `0` 也有效、無效的 token 不送進度、取消後不再送進度。
- **工具：** 報告欄位與順序、`notice`、只有來源網址而沒有摘錄、五種無效參數、缺少金鑰與設定錯誤、私有 repo 的失敗報告、取消呼叫時分析一併取消；以及進度跟著 Activity 前進、分析開始前的錯誤不送進度、長訊息會截斷。模擬的模型與 GitHub 會立即完成，所有事件會合併成一則，所以進度檢查讓假模型在回應前先讓出一次執行權，模擬網路等待。除了私有 repo 的檢查會先查詢 GitHub，這些錯誤都不會發出模型請求。
- **設定：** 忽略網頁版的資料庫與登入設定；不合法的設定會變成工具錯誤，而不是讓 server 無法啟動。
- **子程序：** 透過真實的管道完成握手、列出工具、呼叫工具，並在關閉 stdin 後正常結束；另一項確認 `print` 與直接寫入檔案描述元 1 的內容都進到 stderr。子程序不讀取 `.env`，也沒有任何憑證。

把取消、移除摘錄、stdout 轉向、取消後不回應、並行執行、版本協商與金鑰檢查逐一改壞時，對應的檢查都會失敗；進度的停止、token 判斷、遞增計數、轉送與截斷也一樣。完整離線回歸 375 項通過，28 項 PostgreSQL 檢查略過，Pyright 通過。

真實客戶端的連線也已確認。兩者都使用暫存目錄中的設定，沒有修改使用者自己的設定檔，也沒有執行分析。Claude Code 的 `claude mcp list` 顯示已連線；Codex 在沒有憑證的工作階段中完成握手並取得工具清單，接著它自己的模型請求因未授權而失敗。加入進度通知後，Claude Code 的健康檢查仍顯示已連線。[客戶端連線驗證](../evidence/m5/verification/client-handshake.json)

兩個客戶端的真實分析見下兩節。尚未驗證：兩者的互動介面如何顯示進度、預設權限模式下 Claude Code 的核准畫面、從 Claude Code 取消呼叫、超過 Codex 逾時的行為，以及 Windows。

| 協定版本 | 先送 2026-07-28 的 `server/discover`，收到 `-32601` 後改用 `initialize`，協商出 `2025-11-25` |

## Context 預算調為 24,000

兩次驗收都在 12,000 下省略了 S5，也就是維護者最新、最可能是決定的留言。用這個 issue 的真實留言量過之後，原因有兩個：

- **預算太緊。** 每次請求固定要放提示詞 1,997、工具定義 830、回答格式 608 與估算餘裕 1,024 個 token，再加上最多 5,216 的預留空間。預留最多的那幾次請求，12,000 扣掉這些只剩約 2,300 可以放對話與證據。
- **省略規則選錯對象。** Context Builder 從優先度最低的留言開始省略，但每省略一則要加上約 90 token 的提示，比摘錄還長時就不省略。S2 到 S4 都只有 36 到 49 個 token，結果唯一「省得下來」的是優先度最高（21）的 S5，只省了約 90 個 token。這是離線把真實留言交給 Context Builder 重跑確認的，沒有呼叫模型。

所以把預設改成 24,000，省略規則先不動（M2 凍結）。2026-11-13（UTC）用 MCP server 的設定載入與同一個工具類別，在程序內實際跑了一次同一個 issue：

| 項目 | 12,000（Claude Code） | 24,000 |
| --- | --- | --- |
| 狀態 | `partial` | `completed` |
| 省略的摘錄 | S5 | 無 |
| 被引用的來源 | 5 個 | 7 個，包含 S5 |
| IssueLens 用量 | 6 次請求、25,823 個 token | 6 次請求、25,874 個 token |
| 時間 | 約 22 秒 | 約 23 秒 |

- 摘要、第二個標籤 `discussion` 與草稿都反映了 S5：維護者覺得供應商連結像廣告而猶豫，也提到 Cloudflare 的規模與清單上其他平台相當，捐款頁不保證任何回報。這幾點已對照留言原文，但不是使用者的人工審閱。
- 用量幾乎相同。上限是天花板，小 issue 的請求不會因此變大；這次含預留空間的最大請求是 11,130 個 token。
- 這個數字其實也在 12,000 之內：這次兩次搜尋都沒有找到候選 issue，而 Claude Code 那次的搜尋找到兩個，路徑不同。所以 12,000 對這個 issue 剛好在邊緣，24,000 留下約 12,900 的空間；單憑這次不能說 12,000 一定失敗。
- 值得人工審閱時注意：草稿請報告者提出中立的收錄標準，這是模型自己的建議，維護者沒有要求；`discussion` 的理由來自 S5，引用卻只有 S1 和 S6。
- 檢查點的簽章包含這個預算，所以 12,000 下中斷的分析在新的 Worker 會標為無法接續，這是 M3 對任何設定變更的既有行為。

報告內容尚未經使用者人工審閱。[驗收摘要](../evidence/m5/verification/context-budget-24000/20261113T220623Z/summary.json)／[IssueLens 報告](../evidence/m5/verification/context-budget-24000/20261113T220623Z/report.json)／[每次請求的 context](../evidence/m5/verification/context-budget-24000/20261113T220623Z/context-builds.json)

## 打包與發布

目標是讓其他人不必 clone 這個 repo，只要有 `uv` 和自己的 OpenAI 金鑰，一行指令就能把 IssueLens 加進 Claude Code 或 Codex。分五步進行：

| 步驟 | 內容 | 狀態 |
| --- | --- | --- |
| 1. 打包 | build system 與 `issuelens-mcp` 指令 | 完成 |
| 2. 金鑰與設定 | 不再依賴 checkout 裡 `.env` 的位置 | 完成 |
| 3. 乾淨環境驗收 | 只用 `uvx` 安裝，接上兩個客戶端並實際分析一次 | 未開始 |
| 4. 使用說明 | README 的英文安裝說明 | 未開始 |
| 5. 發布 | GitHub repo、授權條款、`v0.1.0` | 未開始；授權條款與公開範圍由使用者決定 |

### 第一步：打包

原本 `pyproject.toml` 設了 `package = false`，uv 只安裝依賴，不把專案本身當成套件，所以只能從 checkout 用 `python -m` 執行。這一步加上三樣東西：

- **建置後端 `uv_build`：** uv 內建，不必另外安裝建置工具。程式碼在根目錄的 `backend/`，不在 `src/` 底下，所以用 `module-root = ""` 指定位置。
- **指令入口 `issuelens-mcp`：** `[project.scripts]` 讓安裝後多出一個可以直接執行的指令，對應 `backend.app.mcp.__main__:main`。
- **單一版本來源：** 回報給客戶端的 `serverInfo.version` 改從安裝後的套件資訊讀取，只需要維護 `pyproject.toml` 的 `version`。

`backend/` 底下的任何檔案都會被打包，所以 `source-exclude` 排除 `.env` 與 `.env.*`，就算不小心放進去也不會發布。uv 對 wheel 也套用同一份排除規則。

`uv sync` 現在以 editable 模式安裝專案：site-packages 只放指向原始碼的連結，改程式不必重裝；從 checkout 執行時仍讀取根目錄的 `.env`，網頁版、Worker 與測試的行為不變。

檢查方式：

```bash
out=$(mktemp -d)
uv build --out-dir "$out"
python3 -m zipfile -l "$out"/issuelens-0.1.0-py3-none-any.whl
```

成功時 wheel 只有 `backend/` 的程式碼與 `issuelens-0.1.0.dist-info/`，共 31 個檔案，`entry_points.txt` 裡有 `issuelens-mcp`；sdist 只多了 `README.md` 與 `pyproject.toml`。沒有 `.env`、evidence、tests 或前端。

2026-11-15 的驗證：在全新的暫存 HOME、只有系統 PATH、沒有任何金鑰的環境中，用 `uvx --from <wheel> issuelens-mcp` 安裝並啟動。uv 安裝了 38 個套件（快取約 126 MB），握手協商出 `2025-11-25`，版本 `0.1.0`，也列出了 `analyze_github_issue`。呼叫工具時回傳缺少金鑰的錯誤，沒有發出模型或 GitHub 請求。在 scratch 複本放進 `backend/.env` 與 `backend/app/.env.local`，兩者都沒有進入 wheel 或 sdist；同樣放進去的 `notes.txt` 則被打包。離線測試 342 項通過、28 項略過，Pyright 通過。[打包驗證](../evidence/m5/verification/packaging.json)

這時缺少金鑰的錯誤訊息仍要求設定「IssueLens checkout 的 `.env`」，但安裝版沒有 checkout，所以接著處理第二步。

<a id="settings-file"></a>
### 第二步：金鑰與設定

安裝版要先決定金鑰放在哪裡。最直覺的做法是讓使用者在 shell 設定 `OPENAI_API_KEY`，但兩個客戶端傳給 MCP server 的環境並不相同。用一個只記錄變數**名稱**的探測 server 實測，結果如下：

| 客戶端 | 預設傳給 server 的變數 | 其他傳法 |
| --- | --- | --- |
| Claude Code 2.1.323 | shell 的全部變數，名稱含 `KEY`、`TOKEN`、`SECRET` 的也會傳 | `claude mcp add -e NAME=value`，值存在 Claude Code 設定中 |
| Codex 0.169.0 | 只有 `HOME`、`PATH`、`USER` 等 9 個 | `env = { NAME = "value" }` 把值寫進 `config.toml`；`env_vars = ["NAME"]` 從 shell 傳入指定的變數 |

所以在 shell 設定的金鑰，Claude Code 收得到，Codex 預設收不到。兩邊都會傳 `HOME`，因此安裝版改讀家目錄下的檔案：

1. MCP server 環境中已有的變數優先，與網頁版「已匯出的環境變數優先於 `.env`」相同。
2. 其餘從**一個** `.env` 檔讀取：`backend/` 旁邊有 `pyproject.toml` 就是 checkout，讀 checkout 的 `.env`；否則是安裝版，讀 `~/.config/issuelens/.env`。
3. 不使用 `XDG_CONFIG_HOME`。Codex 不會傳這個變數，若使用者設定了它，兩個客戶端會讀到不同的檔案。

這樣金鑰不必寫進任何客戶端的設定檔，兩個客戶端讀到的也是同一份。缺少金鑰時，錯誤訊息會指出要編輯的檔案，例如 `Set OPENAI_API_KEY in ~/.config/issuelens/.env or in the MCP server's environment`。家目錄顯示成 `~`，因為這段文字會交給客戶端的模型，不需要帶上帳號名稱。

建議用 `chmod 600 ~/.config/issuelens/.env`，只讓自己讀取。

2026-11-15 的驗證：以暫存 HOME 和 `uvx --from <wheel>` 啟動安裝版，設定檔裡放的是假金鑰，工具呼叫則使用 PR 網址，會在發出任何請求前被拒絕，所以不會產生費用。

| 情況 | 工具說明中的預算 | 工具呼叫結果 |
| --- | --- | --- |
| 沒有設定檔 | 8 次請求 | 缺少金鑰，訊息指向 `~/.config/issuelens/.env` |
| 設定檔有假金鑰與 `AGENT_MAX_ITERATIONS=3` | 3 次 | 通過金鑰檢查，回報網址錯誤 |
| 同一份檔案，環境另設 `AGENT_MAX_ITERATIONS=5` | 5 次 | 環境變數優先 |
| 從 checkout 執行 `issuelens-mcp` | 8 次 | 仍讀 checkout 的 `.env` |

新增三項離線檢查：checkout 讀自己的 `.env`、安裝版讀使用者設定檔且環境變數優先，以及錯誤訊息只顯示 `~`。把「安裝版仍讀套件旁的 `.env`」「訊息顯示完整家目錄」「設定檔覆蓋環境變數」逐一改壞，對應的檢查都會失敗。

另外，`test_reasoning_settings.py` 原本有兩項檢查用沒有 `pyproject.toml` 的暫存資料夾模擬 checkout。新規則把它當成安裝版，其中一項因此去讀真實家目錄下的設定檔而失敗；現在暫存資料夾都會放一個空的 `pyproject.toml`。離線測試 345 項通過、28 項略過，Pyright 通過。[設定驗證](../evidence/m5/verification/settings.json)

## 限制

- 預設 24,000 token 的 context 預算只在一個 issue 上驗證過；M2 的評估與驗收是在 12,000 下做的。證據很多的 issue 請求會更大，比較可能碰到 90 秒的任務時限。
- Context Builder 在預算緊時，可能因為較短的留言省不下空間，反而省略優先度最高的留言。規則屬於凍結的 M2，尚未修正。
- 每次呼叫都使用操作者的 OpenAI 額度。沒有每日上限；同時最多執行兩筆，記憶體中最多保留 30 筆。
- 進度通知只送最新的事件，不是完整的 Activity 紀錄。Codex 的非互動模式不顯示進度；Claude Code 接受了所有進度通知，但兩者的互動介面如何顯示尚未確認。
- Claude Code 在 auto 權限模式下會直接呼叫這個付費工具，不先詢問。
- 只支援 2025 年的兩個協定版本。
- 分析只存在 MCP server 程序的記憶體裡，客戶端重啟後就消失，也不會出現在網頁版的歷史中。
- 設定 `GITHUB_TOKEN` 時只分析公開 repo。
- 對 prompt injection 只能降低風險，不能完全防止。
- 套件最上層的名稱是 `backend`。用 `uvx` 安裝時每個工具有獨立環境，不會衝突；這個專案不上 PyPI，所以沿用這個名稱。
- 環境變數的傳法只測過從終端機啟動的 Claude Code 與 Codex。從 IDE 或桌面 app 啟動時的環境，以及 Windows 的家目錄與 Codex 預設變數，都尚未確認。
- 安裝時會連網頁版與 PostgreSQL 的依賴一起裝。MCP server 用不到其中一部分，啟動時仍會載入 `psycopg`。

## 面試取捨

可以比較「自己實作協定」與「使用官方 SDK」。自己實作讓握手、版本協商、並行與取消都清楚可見，依賴也少；代價是規格更新要自己跟上，例如 2026-07-28 的無狀態模式。SDK 替你處理這些，也把細節藏起來。這個專案的目標是學會 Agent 的運作，所以選擇自己實作，並把版本處理集中在 `protocol.py` 的一個地方。

也可以比較「一個完整分析的工具」與「多個細部工具」。完整分析保留了經過評估的流程與驗證，但呼叫慢、要付費；細部工具快又便宜，品質卻取決於使用者的模型。

打包時可以比較「沿用 `backend` 這個名稱」與「改名為 `issuelens`」。沿用不必改動 215 處引用，網頁版的 `backend/`、`frontend/` 結構也不變；代價是套件名稱太通用，只適合裝在獨立的環境。改名較正規，但改動範圍大；這個專案透過 GitHub 安裝、不上 PyPI，所以沿用。

金鑰的位置也有取捨：寫進客戶端設定（`-e` 或 `env`）最簡單，但值會以明文存在兩個不同的設定檔；只靠 shell 環境變數，Codex 預設收不到；使用者層級的設定檔多一個要建立的檔案，但兩個客戶端共用同一份，也不會出現在客戶端設定裡。
