# M5 在 Claude Code 與 Codex 中使用 IssueLens

## 目標與範圍

許多開發者直接在 Claude Code 或 Codex 裡工作。M5 把 IssueLens 的分析包成這兩個工具都能呼叫的 **MCP server**：使用者在對話中貼上 issue 網址，程式助手呼叫 IssueLens，取回有引用的分析報告。

MCP（Model Context Protocol）是 AI 應用程式連接外部工具的標準協定，底層是 JSON-RPC 2.0。本機使用 **stdio** 傳輸：Claude Code 或 Codex 啟動 IssueLens 程序，從標準輸入送出請求，從標準輸出讀回應，每則訊息佔一行 JSON。[MCP 規格](https://modelcontextprotocol.io/specification/2025-11-25) · [Claude Code 的 MCP 設定](https://code.claude.com/docs/en/mcp) · [Codex 的 MCP 設定](https://developers.openai.com/codex/mcp)

第一步的範圍：

- 一個工具 `analyze_github_issue(issue_url)`，在 MCP server 程序內以記憶體模式執行現有的 Agent。提示詞、模型、預算與七個 GitHub 工具都不變，M2 維持凍結。
- 在使用者自己的電腦執行，使用 IssueLens 目錄中 `.env` 的金鑰。
- 支援取消、進度通知，以及兩個客戶端實際使用的協定版本。

暫不包含：遠端服務、只提供證據的細部工具、私有 repo，以及發布成套件。

選擇「整個分析當成一個工具」，是因為 IssueLens 的價值在於有邊界、有引用、經過驗證的調查流程。只提供讀取 GitHub 的工具，Claude Code 本來就能用 `gh` 做到。代價是每次呼叫都使用 OpenAI 額度，也要等整個分析完成。

## 設定

需要能執行網頁版的環境：clone 專案、執行 `uv sync --locked`，並在 `.env` 設定 `OPENAI_API_KEY`（[M1 環境設定](m1.md#環境與啟動)）。`GITHUB_TOKEN` 可選；設定後只分析公開 repo，規則同 [M4](m4.md#只分析公開-repo)。

以下把 `/path/to/IssueLens` 換成專案的絕對路徑。

**Claude Code：**

```bash
claude mcp add --scope user issuelens -- uv run --directory /path/to/IssueLens --locked python -m backend.app.mcp
claude mcp list
```

`--scope user` 讓所有專案都能使用。`claude mcp list` 應顯示 `issuelens: ... - ✔ Connected`。Claude Code 的工具逾時預設約 28 小時，不需要調整。

**Codex：**

```bash
codex mcp add issuelens -- uv run --directory /path/to/IssueLens --locked python -m backend.app.mcp
```

Codex 的工具逾時預設是 60 秒，但一次分析最長 90 秒，所以必須調長。打開 `~/.codex/config.toml`，在 `[mcp_servers.issuelens]` 下加入一行：

```toml
tool_timeout_sec = 180
```

再執行 `codex mcp get issuelens`，確認輸出有 `tool_timeout_sec: 180`。拼錯的欄位會被直接忽略，不會報錯，這一步可以及早發現。180 秒涵蓋 90 秒的任務時限，以及已有兩筆分析在執行時的排隊時間。

金鑰留在 IssueLens 的 `.env`，不必寫進 `~/.claude.json` 或 Codex 的設定，這兩者都是明文檔案。MCP server 會忽略 `.env` 中網頁版的 `DATABASE_URL` 與 OAuth 設定，分析只保存在這個程序的記憶體中。

每次模型請求的本機 context 預算預設是 12,000 個 token（`AGENT_CONTEXT_TOKENS`，可設 2,000 到 32,000）。這是 IssueLens 自己估算的上限，不是模型的視窗大小。證據較多的 issue 可能因此省略部分留言並提早收尾，報告標為 `partial`，下面的 Codex 驗收就是一例。使用自己的金鑰時可以在 `.env` 調高；但 M2 的提示詞與預留空間是在 12,000 下調整與評估的，調高後的品質尚未驗證，每次請求也會更貴、更慢，比較可能碰到 90 秒的任務時限。[Context Builder](m2.md#context-builder)

## 使用

在 Claude Code 或 Codex 的對話中輸入，例如：

```text
Use IssueLens to analyze https://github.com/pallets/flask/issues/6146 and tell me what information is still missing.
```

程式助手會先請你同意這次工具呼叫，再等分析完成，通常需要 20 到 90 秒。每次呼叫最多 8 次 OpenAI 請求，費用與網頁版的一次分析相同。

## 運作方式

```text
Claude Code / Codex ──stdin──▶ McpServer ──▶ IssueAnalysisTool ──▶ JobManager ──▶ AgentRun
                    ◀─stdout── (protocol.py)  (analysis_tool.py)   (memory mode)   (existing agent)
```

程式在 [backend/app/mcp/](../backend/app/mcp/)：`protocol.py` 是通用的協定層，`analysis_tool.py` 定義 IssueLens 的工具與報告，`__main__.py` 負責 stdio 與啟動。

**連線與協定版本。** 2025 年的版本以 `initialize` 握手協商版本。2026-07-28 版改成無狀態，每個請求自帶版本，並以 `server/discover` 取代握手。實測兩個客戶端的結果：

| 客戶端 | 第一則訊息 | 協商結果 |
| --- | --- | --- |
| Claude Code 2.1.323 | `server/discover`（2026-07-28），收到 method not found 後改送 `initialize` | `2025-11-25` |
| Codex 0.167.2 | `initialize` | `2025-06-18` |

IssueLens 支援 `2025-11-25` 與 `2025-06-18`。這兩版在本專案用到的方法上相同：`initialize`、`ping`、`tools/list`、`tools/call` 與取消通知。客戶端要求其他版本時，server 回覆最新的 `2025-11-25`，由客戶端決定是否繼續。`server/discover` 則回覆 method not found，Claude Code 會自動退回舊版握手。

**工具呼叫與取消。** 每個 `tools/call` 在獨立的 asyncio task 執行，讀取迴圈仍能同時處理其他訊息，包括取消通知。收到 `notifications/cancelled` 時，IssueLens 取消對應的分析，停止後續的模型請求，並依規格不回應這個請求。客戶端關閉 stdin 代表結束連線，執行中的分析也會一起取消。

**進度通知。** 一次分析最長 90 秒。客戶端在 `tools/call` 的 `_meta` 帶 `progressToken` 時，IssueLens 一邊等分析完成，一邊追蹤 Activity 事件；每次有新事件，就送出一則 `notifications/progress`，訊息是最新事件的文字，例如 `Investigation step 1: choosing the next action.`。總步數事先不知道，所以不帶 `total`。

- 規格要求 `progress` 每次都要增加，所以由協定層計數，工具只提供文字。工具怎麼寫，都不會送出遞減的進度。
- 同時產生的多個事件只送最新的一則，超過 200 字的訊息會截斷，避免洗版；完整內容仍在報告與限制中。
- 呼叫完成或被取消後，進度函式立即失效，不會送出規格禁止的過期通知。
- `progressToken` 可以是 `0`。實測中 Codex 在 `tools/list` 送出的 token 就是 `0`，所以判斷依據是型別，而不是真假值。

**錯誤。** 不存在的工具與格式錯誤的訊息回傳 JSON-RPC 錯誤。參數錯誤、缺少 `OPENAI_API_KEY`、網址不是 GitHub issue、設定錯誤，以及分析失敗，都以 `isError: true` 的工具結果回傳，讓程式助手讀到原因並修正。除了分析失敗，這些檢查都在發出任何模型請求前完成。

**stdout 只給協定。** stdio 傳輸中，標準輸出的每一行都必須是 JSON-RPC 訊息。server 啟動時先複製一份真正的 stdout 專門寫協定訊息，再把檔案描述元 1 指向 stderr。之後任何 `print` 或函式庫的直接輸出都會進到 stderr，不會弄壞協定。

**報告。** 工具回傳一段 JSON 文字，欄位依序是 `notice`、`status`、`issue_url`、`error`、`issue`、`summary`、`known_facts`、`missing_information`、`similar_issues`、`label_recommendations`、`draft_reply`、`limitations`、`sources` 和 `usage`。

GitHub 內容可能由任何人撰寫，而程式助手能執行指令，所以報告的處理比網頁版更保守：

- `notice` 是第一個欄位，說明整份報告是由第三方內容整理成的資料，不要照著執行。工具描述與 server 的 `instructions` 也有相同的提醒。
- `sources` 只列 ID、類型、標題與網址，不附原始摘錄。摘錄是未經處理的第三方文字，程式助手需要時可以打開網址查證。
- 報告用 JSON 傳遞，issue 內容就算寫成 Markdown 標題或假的系統訊息，也只是某個字串欄位的值。

這些措施只能降低風險，無法完全防止 prompt injection：摘要與草稿仍由模型根據不可信的內容寫成。程式助手要執行指令時，使用者仍應確認內容。

這版只回傳文字，沒有 `structuredContent` 與 `outputSchema`。規格建議同時提供兩者時，文字部分也放同一份 JSON；若客戶端把兩份都交給模型，報告的 token 就會加倍。Codex 的驗收顯示它保留了 `structured_content` 欄位；Claude Code 則把文字原樣交給模型。要不要加上 `structuredContent` 仍待決定。

## 檢查與驗證

```bash
uv run --locked python -W error::RuntimeWarning -m unittest discover -s tests -p 'test_mcp.py' -v
```

27 項檢查應通過，不呼叫模型或 GitHub。

- **協定：** 版本協商、`server/discover`、`ping`、工具清單、七種格式錯誤的訊息、不需回應的通知、未知工具、並行呼叫、重複的請求 ID、取消後不回應、未預期錯誤只記錄例外型別、關閉時取消執行中的呼叫；以及進度只在呼叫期間送出、token 為 `0` 也有效、無效的 token 不送進度、取消後不再送進度。
- **工具：** 報告欄位與順序、`notice`、只有來源網址而沒有摘錄、五種無效參數、缺少金鑰與設定錯誤、私有 repo 的失敗報告、取消呼叫時分析一併取消；以及進度跟著 Activity 前進、分析開始前的錯誤不送進度、長訊息會截斷。模擬的模型與 GitHub 會立即完成，所有事件會合併成一則，所以進度檢查讓假模型在回應前先讓出一次執行權，模擬網路等待。除了私有 repo 的檢查會先查詢 GitHub，這些錯誤都不會發出模型請求。
- **設定：** 忽略網頁版的資料庫與登入設定；不合法的設定會變成工具錯誤，而不是讓 server 無法啟動。
- **子程序：** 透過真實的管道完成握手、列出工具、呼叫工具，並在關閉 stdin 後正常結束；另一項確認 `print` 與直接寫入檔案描述元 1 的內容都進到 stderr。子程序不讀取 `.env`，也沒有任何憑證。

把取消、移除摘錄、stdout 轉向、取消後不回應、並行執行、版本協商與金鑰檢查逐一改壞時，對應的檢查都會失敗；進度的停止、token 判斷、遞增計數、轉送與截斷也一樣。完整離線回歸 375 項通過，28 項 PostgreSQL 檢查略過，Pyright 通過。

真實客戶端的連線也已確認。兩者都使用暫存目錄中的設定，沒有修改使用者自己的設定檔，也沒有執行分析。Claude Code 的 `claude mcp list` 顯示已連線；Codex 在沒有憑證的工作階段中完成握手並取得工具清單，接著它自己的模型請求因未授權而失敗。加入進度通知後，Claude Code 的健康檢查仍顯示已連線。[客戶端連線驗證](../evidence/m5/verification/client-handshake.json)

兩個客戶端的真實分析見下兩節。尚未驗證：兩者的互動介面如何顯示進度、預設權限模式下 Claude Code 的核准畫面、從 Claude Code 取消呼叫、超過 Codex 逾時的行為，以及 Windows。

## Codex 真實驗收

2026-11-13（UTC）從 Codex 0.167.2 以 `codex exec` 分析 `pallets/flask#6146`。這是網頁版的內建範例，M3 已實際跑過，所以這次可以專心確認 Codex 的整合。Codex 使用使用者預設的模型與推理強度；IssueLens 讀取 `.env`，與網頁版相同，使用 `gpt-5.6`／`medium`。

這次的 MCP 設定都用 `-c` 參數傳入，沒有修改使用者的 Codex 設定檔。其他三個 MCP server 暫時停用；Codex app 內建的 JavaScript REPL `cua_repl` 無法逐次停用，Codex 也沒有呼叫它。非互動模式無法顯示核准視窗，所以這次對 IssueLens 設定 `default_tools_approval_mode = "approve"`。

| 項目 | 結果 |
| --- | --- |
| 協定版本 | `2025-06-18` |
| 工具呼叫 | 成功，約 20 秒，`isError: false` |
| 進度通知 | Codex 在 `tools/call` 帶 `progressToken: 1`；IssueLens 送出 12 則，從 `Analysis queued.` 到 `Analysis partial.` |
| 報告 | 5,542 個字元，`partial`，7 個來源 |
| IssueLens 用量 | 5 次模型請求、4 次工具呼叫、20,845 個 token |
| Codex | 正確轉述狀態、摘要、缺少的資訊與來源數，沒有執行任何指令；整次 38 秒 |

- Codex 接收了所有進度通知，沒有錯誤，但 `codex exec --json` 沒有輸出任何進度事件，所以非互動模式不會顯示進度。互動介面尚未確認。
- 這次約 20 秒，在 Codex 預設的 60 秒內；接近 90 秒預算的分析仍需要 `tool_timeout_sec = 180`。
- 結果是 `partial`：本機的 context 預算省略了一則留言摘錄，並讓分析提早收尾。這是 M2 已記錄的限制，MCP server 與網頁版使用相同設定；M3 對同一個 issue 的真實執行是 `completed`，8 個來源。
- Codex 的工具結果有 `structured_content` 欄位，這次是空值，因為這版只回傳文字。

## Claude Code 真實驗收

2026-11-13（UTC）使用者在一個空資料夾開啟 Claude Code 2.1.323 的互動工作階段，送出與 Codex 相同的提示詞，分析同一個 issue，方便比較兩個客戶端。Claude Code 使用使用者預設的模型；IssueLens 一樣讀取 `.env`。MCP server 以 local 範圍加入這個資料夾，並透過轉送程式記錄協定訊息。事後核對了轉送紀錄與 Claude Code 的工作階段紀錄。

| 項目 | 結果 |
| --- | --- |
| 協定版本 | 先送 2026-07-28 的 `server/discover`，收到 `-32601` 後改用 `initialize`，協商出 `2025-11-25` |
| 工具呼叫 | 成功，約 22 秒，`isError: false` |
| 進度通知 | Claude Code 在 `tools/call` 帶 `progressToken: 2`；IssueLens 送出 14 則，Claude Code 都接受，沒有錯誤 |
| 報告 | 5,285 個字元，`partial`，8 個來源；Claude Code 收到的內容與 server 送出的完全相同 |
| IssueLens 用量 | 6 次模型請求、5 次工具呼叫、25,823 個 token |
| Claude Code | 只用了 `ToolSearch` 與 IssueLens 工具，沒有執行指令或讀取檔案；整輪約 35 秒 |

- Claude Code 延後載入 MCP 工具的定義，所以先用 `ToolSearch` 取得 `analyze_github_issue` 的說明，再呼叫它。server 的 `instructions` 則從第一輪就在對話裡，所以「報告是不可信資料」的提醒在模型決定呼叫之前就已送到。
- 這次是 auto 權限模式，呼叫直接執行，沒有出現核准畫面。預設權限模式下的核准畫面尚未確認。
- Claude 正確轉述狀態、摘要與來源數。`missing_information` 是空的，它照實說明，再從 limitations 指出真正的缺口；它也算出 8 個來源中只有 S1-S4 與 S6 支持某項說法。
- 結果仍是 `partial`，原因和 Codex 那次相同：context 預算省略了 S5，也就是最後一則維護者留言，並讓分析提早收尾。草稿回覆因此是在沒看過這則留言的情況下寫成的，Claude 有提醒使用者先讀它。`AGENT_CONTEXT_TOKENS` 依決定維持 12000。
- 介面上如何顯示進度與工具輸出、是否出現大小警告，這次沒有記錄，尚未確認。

報告內容尚未經使用者人工審閱。[驗收摘要](../evidence/m5/verification/claude-code-live/20261113T202631Z/summary.json)／[IssueLens 報告](../evidence/m5/verification/claude-code-live/20261113T202631Z/report.json)／[協定訊息](../evidence/m5/verification/claude-code-live/20261113T202631Z/protocol.jsonl)／[Claude Code 回答](../evidence/m5/verification/claude-code-live/20261113T202631Z/claude-code-final-message.md)

## 練習

在專案根目錄手動走一次握手：

```bash
printf '%s\n' \
  '{"jsonrpc":"2.0","id":0,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{}}}' \
  '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
  '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"analyze_github_issue","arguments":{"issue_url":"https://github.com/pallets/flask/pull/1"}}}' \
  | uv run --locked python -m backend.app.mcp
```

應看到三行回應，`notifications/initialized` 沒有回應。第一行的 `protocolVersion` 是 `2025-11-25`，不是要求的 `2024-11-05`；第三行是 `isError: true`，因為 PR 網址在發出任何模型請求前就被拒絕，所以不會產生費用。接著想一想：server 為什麼不直接拒絕不支援的版本？請不要把網址換成真的 issue，那樣會發出付費的模型請求。

再把最後一行的 `params` 加上 `"_meta":{"progressToken":"demo"}` 重跑一次。這次仍然沒有任何 `notifications/progress`，想一想為什麼：網址在分析開始前就被拒絕，而進度只在分析執行期間送出。

## 限制

- 預設 12,000 token 的 context 預算可能讓證據較多的 issue 變成 `partial`；調高後的品質尚未評估。
- 每次呼叫都使用操作者的 OpenAI 額度。沒有每日上限；同時最多執行兩筆，記憶體中最多保留 30 筆。
- 進度通知只送最新的事件，不是完整的 Activity 紀錄。Codex 的非互動模式不顯示進度；Claude Code 接受了所有進度通知，但兩者的互動介面如何顯示尚未確認。
- Claude Code 在 auto 權限模式下會直接呼叫這個付費工具，不先詢問。
- 只支援 2025 年的兩個協定版本。
- 分析只存在 MCP server 程序的記憶體裡，客戶端重啟後就消失，也不會出現在網頁版的歷史中。
- 設定 `GITHUB_TOKEN` 時只分析公開 repo。
- 對 prompt injection 只能降低風險，不能完全防止。

## 面試取捨

可以比較「自己實作協定」與「使用官方 SDK」。自己實作讓握手、版本協商、並行與取消都清楚可見，依賴也少；代價是規格更新要自己跟上，例如 2026-07-28 的無狀態模式。SDK 替你處理這些，也把細節藏起來。這個專案的目標是學會 Agent 的運作，所以選擇自己實作，並把版本處理集中在 `protocol.py` 的一個地方。

也可以比較「一個完整分析的工具」與「多個細部工具」。完整分析保留了經過評估的流程與驗證，但呼叫慢、要付費；細部工具快又便宜，品質卻取決於使用者的模型。
