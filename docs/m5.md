# M5: Use IssueLens in Claude Code and Codex

## Status

M5 exposes the IssueLens analysis to Claude Code and Codex as a local stdio MCP server with one tool, `analyze_github_issue`. Both clients ran real analyses through it, including from the installed package, and `v0.1.0` is public on GitHub. Installing from GitHub was checked with a handshake, the tool list, and one tool call that stopped at the missing-key check, without a real analysis. The user has not reviewed any of the reports yet.

## Goal and scope

Many developers work directly in Claude Code or Codex. M5 wraps the IssueLens analysis as an **MCP server** that both tools can call. The user pastes an issue URL into the conversation, the coding assistant calls IssueLens, and it gets back a cited analysis report.

MCP (Model Context Protocol) is a standard protocol that connects AI applications to external tools, built on JSON-RPC 2.0. IssueLens uses the local **stdio** transport: Claude Code or Codex starts the IssueLens process, sends requests on standard input, and reads responses from standard output, one line of JSON per message. [MCP specification](https://modelcontextprotocol.io/specification/2025-11-25) - [MCP in Claude Code](https://code.claude.com/docs/en/mcp) - [MCP in Codex](https://developers.openai.com/codex/mcp)

The first step covers:

- One tool, `analyze_github_issue(issue_url)`, which runs the existing agent in memory mode inside the MCP server process. The prompts, model, budgets, and seven GitHub tools stay the same, and M2 stays frozen.
- It runs on the user's own machine with the keys from the `.env` in the IssueLens directory.
- Cancellation, progress notifications, and the protocol versions the two clients actually use.

Out of scope for now: a remote service, fine-grained evidence-only tools, and private repositories. For the work that lets others install IssueLens without a clone, see [Packaging and release](#packaging).

The whole analysis is one tool because the value of IssueLens is its bounded, cited, and validated investigation. Tools that only read GitHub would offer what Claude Code can already do with `gh`. The cost is that every call uses OpenAI credit and waits for the whole analysis to finish.

## Setup

This section runs IssueLens from a checkout. To install it without a clone, follow the [README install steps](../README.md#use-it-in-claude-code-or-codex) instead.

You need the same environment as the web app: clone the project, run `uv sync --locked`, and set `OPENAI_API_KEY` in `.env` ([M1 setup](m1.md#setup)). `GITHUB_TOKEN` is optional. When it is set, IssueLens analyzes only public repositories, with the same rule as [M4](m4.md#public-repos-only).

In the commands below, replace `/path/to/IssueLens` with the absolute path of the project.

**Claude Code**

```bash
claude mcp add --scope user issuelens -- uv run --directory /path/to/IssueLens --locked issuelens-mcp
claude mcp list
```

`--scope user` makes the server available in every project. `claude mcp list` should show `issuelens: ... - ✔ Connected`. `issuelens-mcp` is the packaged command. Configurations added earlier with `python -m backend.app.mcp` still work. Claude Code's default tool timeout is about 28 hours, so it needs no change.

**Codex**

```bash
codex mcp add issuelens -- uv run --directory /path/to/IssueLens --locked issuelens-mcp
```

Codex's default tool timeout is 60 seconds, but one analysis can take up to 90 seconds, so the timeout must be raised. Open `~/.codex/config.toml` and add one line under `[mcp_servers.issuelens]`:

```toml
tool_timeout_sec = 180
```

Then run `codex mcp get issuelens` and check that the output shows `tool_timeout_sec: 180`. Codex ignores a misspelled key without an error, so this check catches it early. 180 seconds covers the 90-second job limit plus the queue time when two analyses are already running.

**Where the keys live**

The keys stay in the IssueLens `.env`. You do not need to write them into `~/.claude.json` or the Codex configuration, which are both plain-text files. Variables already in the MCP server's environment take precedence, and anything else is read from `.env`. A checkout reads the checkout's `.env`, and an installed copy reads `~/.config/issuelens/.env` (see [Step 2](#settings-file)). The MCP server ignores the web app's `DATABASE_URL` and OAuth settings in `.env`, and keeps analyses only in the memory of its own process.

**Context budget**

The local context budget for each model request defaults to 24,000 tokens (`AGENT_CONTEXT_TOKENS`, allowed range 2,000 to 32,000). This is a cap on IssueLens's own estimate, not the model's context window. Requests grow only with the actual evidence, and a higher cap does not make them fill it. The old default was 12,000, which is why both clients' live runs ended `partial`. For the reason for the change and its check, see [Context budget raised to 24,000](#context-budget). M2's prompts and reserves were tuned and evaluated at 12,000, and quality at 24,000 on other issues has not been re-evaluated. See the [Context Builder](m2.md#context-builder).

## Use

In a Claude Code or Codex conversation, type for example:

```text
Use IssueLens to analyze https://github.com/pallets/flask/issues/6146 and tell me what information is still missing.
```

The coding assistant first asks you to approve the tool call, then waits for the analysis, which usually takes 20 to 90 seconds. Each call makes up to 8 OpenAI requests and costs the same as one analysis in the web app.

## How it works

```text
Claude Code / Codex ──stdin──▶ McpServer ──▶ IssueAnalysisTool ──▶ JobManager ──▶ AgentRun
                    ◀─stdout── (protocol.py)  (analysis_tool.py)   (memory mode)   (existing agent)
```

The code is in [backend/app/mcp/](../backend/app/mcp/):

- `protocol.py` is the general protocol layer.
- `analysis_tool.py` defines the IssueLens tool and report.
- `__main__.py` handles stdio and startup.

### Connection and protocol versions

The 2025 versions negotiate the version with an `initialize` handshake. The 2026-07-28 version is stateless: each request carries its own version, and `server/discover` replaces the handshake. Observed with the two clients:

| Client | First message | Negotiated version |
| --- | --- | --- |
| Claude Code 2.1.323 | `server/discover` (2026-07-28), then `initialize` after method not found | `2025-11-25` |
| Codex 0.167.2 | `initialize` | `2025-06-18` |

IssueLens supports `2025-11-25` and `2025-06-18`. The two versions are the same for the methods this project uses: `initialize`, `ping`, `tools/list`, `tools/call`, and the cancellation notification. When a client asks for another version, the server answers with the newest one, `2025-11-25`, and the client decides whether to continue. `server/discover` gets method not found, and Claude Code then falls back to the older handshake automatically.

### Tool calls and cancellation

Each `tools/call` runs in its own asyncio task, so the read loop can still handle other messages at the same time, including cancellation notifications. On `notifications/cancelled`, IssueLens cancels the matching analysis, stops further model requests, and, as the specification requires, does not respond to that request. When the client closes stdin, the connection ends, and any running analysis is cancelled with it.

### Progress notifications

An analysis can take up to 90 seconds. When the client puts a `progressToken` in the `_meta` of `tools/call`, IssueLens follows the Activity events while it waits for the analysis. Each time a new event appears, it sends one `notifications/progress` whose message is the text of the newest event, for example `Investigation step 1: choosing the next action.` The total number of steps is not known in advance, so the notification has no `total`.

- The specification requires `progress` to increase with every notification, so the protocol layer does the counting and the tool supplies only the text. No matter how a tool is written, it cannot send decreasing progress.
- When several events arrive together, only the newest one is sent, and messages over 200 characters are cut, so a burst cannot flood the client. The full content is still in the report and its limitations.
- Once the call completes or is cancelled, the progress function stops working at once, so it cannot send a stale notification, which the specification forbids.
- `progressToken` can be `0`. In testing, the token Codex sent on `tools/list` was `0`, so the check is on the type, not on truthiness.

### Errors

Unknown tools and malformed messages get JSON-RPC errors. Invalid arguments, a missing `OPENAI_API_KEY`, a URL that is not a GitHub issue, configuration errors, and failed analyses all come back as tool results with `isError: true`, so the coding assistant can read the reason and correct it. Except for failed analyses, all these checks finish before any model request.

### stdout is for the protocol only

In the stdio transport, every line on standard output must be a JSON-RPC message. At startup the server first duplicates the real stdout for protocol messages only, then points file descriptor 1 at stderr. After that, any `print` or direct output from a library goes to stderr and cannot corrupt the protocol.

### Report

The tool returns a JSON text whose fields are, in order: `notice`, `status`, `issue_url`, `error`, `issue`, `summary`, `known_facts`, `missing_information`, `similar_issues`, `label_recommendations`, `draft_reply`, `limitations`, `sources`, and `usage`.

Anyone can write GitHub content, and a coding assistant can run commands, so the report is handled more conservatively than in the web app:

- `notice` is the first field. It says that the whole report is data compiled from third-party content and must not be followed as instructions. The tool description and the server's `instructions` carry the same warning.
- `sources` lists only the ID, kind, title, and URL, without raw excerpts. Excerpts are unprocessed third-party text. When the assistant needs one, it can open the URL to check.
- The report travels as JSON. Even issue content written as a Markdown heading or a fake system message is only the value of a string field.

These measures only reduce the risk of prompt injection and cannot fully prevent it: a model still writes the summary and draft from untrusted content. When the coding assistant is about to run a command, the user should still check it.

This version returns text only, without `structuredContent` or `outputSchema`. When both are provided, the specification recommends also putting the same JSON in the text part. If a client passed both to the model, the report would cost twice the tokens. The Codex live run showed that Codex keeps a `structured_content` field; Claude Code passed the text to the model unchanged. Whether to add `structuredContent` is still undecided.

### Context budget raised to 24,000

Both live runs at 12,000 omitted S5, the newest maintainer comment and the one most likely to hold a decision. Measuring with this issue's real comments showed two causes:

- **The budget was too tight.** Every request carries fixed costs: 1,997 tokens of instructions, 830 of tool definitions, 608 of answer schema, and a 1,024-token estimate margin, plus up to 5,216 of reserves. On the requests with the largest reserves, that left only about 2,300 of the 12,000 tokens for the conversation and evidence.
- **The omission rule picked the wrong target.** The Context Builder omits comments starting from the lowest priority, but each omission adds a notice of about 90 tokens, and it does not omit an excerpt shorter than that notice. S2 to S4 were only 36 to 49 tokens each, so the only comment whose omission saved space was S5, the highest priority (21), and omitting it saved only about 90 tokens. This was confirmed offline by feeding the real comments to the Context Builder again, without calling the model.

So the default became 24,000, and the omission rule stays unchanged for now (M2 is frozen). On 2026-11-13 (UTC), one real analysis of the same issue ran in process with the MCP server's settings loader and the same tool class:

| Item | 12,000 (Claude Code) | 24,000 |
| --- | --- | --- |
| Status | `partial` | `completed` |
| Omitted excerpts | S5 | None |
| Cited sources | 5 | 7, including S5 |
| IssueLens usage | 6 requests, 25,823 tokens | 6 requests, 25,874 tokens |
| Time | About 22 seconds | About 23 seconds |

- The summary, a second label (`discussion`), and the draft all reflect S5: the maintainer hesitates because provider links can feel like advertising, notes that Cloudflare is comparable in scale to the other platforms on the list, and says the donation page promises nothing in return. These points were checked against the comment text, but this is not the user's review.
- Usage was almost the same. The budget is a ceiling, so it does not make a small issue's requests bigger. The largest request in this run, reserves included, was 11,130 tokens.
- That figure would also fit within 12,000. In this run neither search found a candidate issue, while the search in the Claude Code run found two, so the runs took different paths. For this issue 12,000 sits right at the edge, and 24,000 leaves about 12,900 tokens of headroom. This run alone does not show that 12,000 always fails.
- Points to watch in human review: the draft asks the reporter to propose neutral inclusion criteria. That is the model's own suggestion, not something the maintainer asked for. The reason for `discussion` comes from S5, but it cites only S1 and S6.
- The checkpoint signature includes this budget, so a new Worker marks an analysis interrupted under 12,000 as not resumable. This is M3's existing behavior for any settings change.

## Packaging and release

The goal is that others can add IssueLens to Claude Code or Codex with one command, without cloning this repository, as long as they have `uv` and their own OpenAI key. The work had five steps:

| Step | Content | Status |
| --- | --- | --- |
| 1. Package | Build system and the `issuelens-mcp` command | Done |
| 2. Keys and settings | No longer depend on where the checkout's `.env` is | Done |
| 3. Clean-environment check | Install with `uvx` only, connect both clients, and run one real analysis | Done |
| 4. Instructions | English install steps in the README | Done |
| 5. Release | GitHub repository, license, and `v0.1.0` | Done; the GitHub install is verified only up to the handshake |

### Step 1: Package

`pyproject.toml` used to set `package = false`. uv installed only the dependencies and did not treat the project itself as a package, so the server could run only from a checkout with `python -m`. This step adds three things:

- **Build backend `uv_build`.** It is built into uv, so no separate build tool is needed. The code is in `backend/` at the repository root, not under `src/`, so `module-root = ""` points to it.
- **Command entry point `issuelens-mcp`.** `[project.scripts]` adds a command that can run directly after installation, mapped to `backend.app.mcp.__main__:main`.
- **Single version source.** The `serverInfo.version` reported to clients now comes from the installed package metadata, so only the `version` in `pyproject.toml` needs maintaining.

Every file under `backend/` is packaged, so `source-exclude` excludes `.env` and `.env.*`. Even if one is placed there by accident, it is not published. uv applies the same exclusions to the wheel.

`uv sync` now installs the project in editable mode: site-packages holds only a link to the source code, so code changes need no reinstall. Running from a checkout still reads the root `.env`, and the web app, Worker, and tests behave as before.

To check:

```bash
out=$(mktemp -d)
uv build --out-dir "$out"
python3 -m zipfile -l "$out"/issuelens-0.1.0-py3-none-any.whl
```

On success the wheel holds only the `backend/` code and `issuelens-0.1.0.dist-info/`, 33 entries in all. `entry_points.txt` contains `issuelens-mcp`, and `licenses/LICENSE` is the MIT license. The sdist adds only `README.md`, `pyproject.toml`, and `LICENSE`. There is no `.env`, evidence, tests, or frontend. Before Step 5 added the license, the wheel had 31 entries.

Verified on 2026-11-15:

- uv installed 38 packages (about 126 MB of cache). The handshake negotiated `2025-11-25` with version `0.1.0`, and the tool list included `analyze_github_issue`.
- The tool call returned the missing-key error, without any model or GitHub request.
- In a scratch copy, files placed at `backend/.env` and `backend/app/.env.local` stayed out of both the wheel and the sdist, while a `notes.txt` placed the same way was packaged.

<a id="settings-file"></a>
### Step 2: Keys and settings

An installed copy first has to decide where the keys live. The obvious approach is to set `OPENAI_API_KEY` in the shell, but the two clients pass different environments to an MCP server. A probe server that recorded only the variable **names** showed:

| Client | Variables passed to the server by default | Other ways to pass them |
| --- | --- | --- |
| Claude Code 2.1.323 | The whole shell environment, including names that contain `KEY`, `TOKEN`, or `SECRET` | `claude mcp add -e NAME=value`; the value is stored in the Claude Code configuration |
| Codex 0.169.0 | Only 9, such as `HOME`, `PATH`, and `USER` | `env = { NAME = "value" }` writes the value into `config.toml`; `env_vars = ["NAME"]` passes the named variables from the shell |

So Claude Code receives a key set in the shell, and Codex does not by default. Both pass `HOME`, so the installed copy reads a file in the home directory instead:

1. Variables already in the MCP server's environment take precedence, the same as the web app's rule that exported environment variables take precedence over `.env`.
2. Everything else comes from **one** `.env` file. If there is a `pyproject.toml` next to `backend/`, this is a checkout, and it reads the checkout's `.env`. Otherwise it is an installed copy and reads `~/.config/issuelens/.env`.
3. `XDG_CONFIG_HOME` is not used. Codex does not pass this variable, so if a user set it, the two clients would read different files.

This way the key does not go into either client's configuration file, and both clients read the same file. When the key is missing, the error message names the file to edit, for example `Set OPENAI_API_KEY in ~/.config/issuelens/.env or in the MCP server's environment`. The home directory appears as `~` because this text goes to the client's model, which does not need the account name.

Running `chmod 600 ~/.config/issuelens/.env` is recommended, so that only you can read the file.

Verified on 2026-11-15: the installed copy started with a scratch HOME and `uvx --from <wheel>`. The settings file held a dummy key, and the tool calls used a PR URL, which is rejected before any request, so nothing cost money.

| Case | Budget in the tool description | Tool call result |
| --- | --- | --- |
| No settings file | 8 requests | Missing key; the message points to `~/.config/issuelens/.env` |
| Settings file with a dummy key and `AGENT_MAX_ITERATIONS=3` | 3 | Passed the key check and reported the URL error |
| Same file, with `AGENT_MAX_ITERATIONS=5` also set in the environment | 5 | The environment variable wins |
| `issuelens-mcp` run from a checkout | 8 | Still reads the checkout's `.env` |

Three new offline checks cover this: a checkout reads its own `.env`, an installed copy reads the user settings file with environment variables taking precedence, and the error message shows only `~`. Breaking each rule one at a time made the matching check fail: an installed copy that still reads the `.env` next to the package, a message that shows the full home directory, and a settings file that overrides environment variables.

Also, two checks in `test_reasoning_settings.py` used a temporary folder without `pyproject.toml` to simulate a checkout. The new rule treats such a folder as an installed copy, so one of them read the settings file in the real home directory and failed. The temporary folders now always contain an empty `pyproject.toml`. The offline suite passed 345 checks and skipped 28, and Pyright passed. [Settings check](../evidence/m5/settings.json)

## Known limits

- The 24,000-token default context budget has been verified on only one issue. M2's evaluation and acceptance ran at 12,000. Issues with a lot of evidence produce larger requests and are more likely to hit the 90-second job limit.
- When the budget is tight, the Context Builder may omit the highest-priority comment, because omitting shorter comments saves no space. The rule belongs to the frozen M2 and has not been fixed.
- Every call uses the operator's OpenAI credit. There is no daily cap. At most two analyses run at once, and memory keeps at most 30.
- Progress notifications carry only the newest event, not the full Activity log. Codex's non-interactive mode does not show progress. Claude Code accepted every progress notification, but how either client's interactive UI displays progress is not confirmed.
- In auto permission mode, Claude Code calls this paid tool directly without asking first.
- Only the two 2025 protocol versions are supported.
- Analyses exist only in the memory of the MCP server process. They disappear when the client restarts and do not appear in the web app's history.
- With `GITHUB_TOKEN` set, IssueLens analyzes only public repositories.
- The measures against prompt injection only reduce the risk and cannot fully prevent it.
- The package's top-level name is `backend`. With `uvx`, each tool has its own environment, so there is no conflict. This project is not published on PyPI, so it keeps the name.
- The first start from GitHub has to clone the repository and download about 38 packages, plus Python when there is no Python 3.13 or later. A clean environment took 10.7 seconds, more than Codex's default 10-second startup limit. The README therefore requires `startup_timeout_sec = 30` and gives a warm-up command, but whether 30 seconds is enough has not been tested on a slow network.
- With `@v0.1.0`, every start contacts GitHub to check the tag, so the server cannot start offline.
- The GitHub install has been verified only up to the handshake and the tool list. No analysis has run with this install method yet.
- Passing environment variables was tested only with Claude Code and Codex started from a terminal. The environment when they start from an IDE or a desktop app, and the home directory and Codex default variables on Windows, are not confirmed.
- Installing also installs the web app and PostgreSQL dependencies. The MCP server does not use some of them, but it still loads `psycopg` at startup.

## Tradeoffs (interview discussion)

**Implementing the protocol ourselves or using the official SDK.** Implementing it ourselves keeps the handshake, version negotiation, concurrency, and cancellation visible, with few dependencies. The cost is that we must keep up with specification changes ourselves, such as the stateless mode in 2026-07-28. An SDK handles these for you, but it also hides the details. This project aims to learn how agents work, so it implements the protocol itself and keeps version handling in one place in `protocol.py`.

**One full-analysis tool or several fine-grained tools.** A full analysis keeps the evaluated process and its validation, but calls are slow and cost money. Fine-grained tools are fast and cheap, but the quality then depends on the user's model.

**Keeping the name `backend` or renaming it to `issuelens`.** Keeping it avoids changing 215 references and keeps the web app's `backend/` and `frontend/` layout. The cost is a package name too generic for anything but an isolated environment. Renaming is more standard but changes much more. This project installs through GitHub and is not on PyPI, so it keeps the name.

**Version pinning.** No version is the easiest, but every commit on `main` reaches users directly. A tag gives a fixed, readable version, but upgrades are manual. A full SHA is unaffected even if the tag moves and starts without the network, but it is hard to read and to upgrade.

**Where the keys live.** Writing them into the client configuration (`-e` or `env`) is simplest, but the value is stored in plain text in two different configuration files. Shell environment variables alone do not reach Codex by default. A user-level settings file adds one file to create, but both clients share it, and it stays out of the client configuration.
