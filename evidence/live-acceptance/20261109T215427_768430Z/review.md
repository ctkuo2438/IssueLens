# 留言讀取補強：同三案一次回歸

這份紀錄是助理初看，使用者人工審閱仍為 `pending`。模型與 GitHub 均為真實 API；每案只執行一次，保留原模型與預算。[原始報告](report.json)不因這份初看而改寫，[助理機器可讀註記](assistant-review.json)另存。

## 與原基準的留言差異

| 案例 | 原基準 | 本輪留言狀態與執行結果 |
| --- | --- | --- |
| [Flask #5804](https://github.com/pallets/flask/issues/5804) | 未呼叫留言工具，漏掉 8 則討論。 | 第二個工具呼叫即讀第一頁，取得 8 則，`comment_check.status=read`。一則長留言截短，任務仍 `partial`。 |
| [Flask #4032](https://github.com/pallets/flask/issues/4032) | 未呼叫留言工具，卻宣稱沒有討論可用。 | 第二個工具呼叫取得 2 則，`read`；最終回答引用維護者的最小重現要求，沒有再作原先的錯誤宣稱。任務 `completed`。 |
| [Werkzeug #2948](https://github.com/pallets/werkzeug/issues/2948) | metadata 為 0 則，未查留言。 | metadata 仍為 0，沒有查留言端點，保持 `not_read`。任務 `completed`；不是成功查得空頁。 |

#5804 的 S2、S9 提供歷史上的 #5812／3.2 處理方向；S3 說明回報者的問題在呼叫時機，而其回呼已經具有冪等性。頁面範圍完整不代表所有原文完整保存：S5 保留 350 Token 的摘錄，截短限制清楚記錄。

#4032 的 S2 要求最小 Flask 重現，S3 是回報者認為問題在 Werkzeug 並附連結。模型保留「連結內容未讀、根因未確認」，沒有把回報者推測當成已驗證原因。

#2948 有一句已知事實明確把零留言歸因於 metadata，其他文字歸因較簡略。結構化狀態仍忠實表示沒有查閱端點；有限句型檢查沒有保證所有數量敘述都清楚歸因。

## 留下的問題

#5804 與 #2948 都仍推薦 `python`，但本輪取得的目錄說明是「更新 Python 程式的 Pull Request」。#2948 的限制又說沒有新增標籤建議，實際列出 `standards` 與 `python`。這些問題不在本步的留言政策修正範圍。

#5804 草稿重問冪等處理是否足夠，雖然 S3 已說明它不足以解釋原問題。#2948 草稿把歷史需求表述成目前未提供的能力，卻沒有查原始碼或發布版本。讀取留言後仍可能誤用或忽略內容，不能把取得成功視為語意驗收通過。

三案本輪都未呼叫範本工具；先讀留言會占用原預算，模型其餘選擇也有變異。因此這次不能聲稱範本調查或全功能品質通過回歸。原 PNG `needs-info` 波動維持開放。

## 用量與覆蓋

三案都有被程式接受的最終 JSON，共 18 次模型請求、15 次工具呼叫、85,105 個回報 Token，35.67 秒。最大送出輸入估算 11,334／12,000，包含 1,024 Token 餘裕。

本輪沒有 Context Builder 摘錄省略、相同結果重用、最終答案驗證修正、失敗留言請求或跨頁讀取。那些分支由模擬 GitHub／模型的離線測試覆蓋，不能稱為真實 API 已驗證。

[原三案基準](../20261109T212458_183451Z/report.json)、原五筆虛構案例及歷史報告均核對雜湊未變，[驗證紀錄](../../m2-comments-verification.json)保存指紋。即時來源與模型選擇都可能變動，這不是控制其他條件的模型品質實驗，也沒有換算成正確率。M2 尚待其餘問題修正與使用者驗收。
